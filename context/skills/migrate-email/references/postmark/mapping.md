# Postmark to PostHog mapping

This file decides, field by field, whether PostHog can send a Postmark call site. A site moves only when every field it sets moves. Otherwise it stays on Postmark, and the reason names the first field or feature that keeps it there. `api.md` has the PostHog side in full, and the rewrite file for the site's language, which Step 7 names, has PostHog's names in that language.

Postmark fields are written in their HTTP names here, such as `HtmlBody`. Python and Ruby code uses snake case, such as `html_body`, and `postmark-python` names `From` as `sender`. PostHog fields are written in their Node.js names, such as `replyTo`. Use the name the rewrite file gives for the site's language, such as `reply_to` in Python.

**What Postmark's docs don't give.** Postmark's API reference and guides say what the API takes and answers, and its "Official libraries" page shows how each official library sends. They don't give a client's error classes, the other names of its methods and fields, the values it sends for a field the code leaves out, its timeouts, or its retries. Where a rule below needs one of those, read the Postmark client installed in the person's app: `postmark` in `node_modules`, `postmark-python` or `postmarker` in the virtualenv, `wildbit/postmark-php` in `vendor`, the `postmark` gem in the bundle, or the Go package in the module cache. The .NET package holds compiled code: read the client's source at the installed version instead, from the repository its package names. Name the file you read in the plan row. When the installed client doesn't settle it, the site stays, and the reason is `Postmark's <what the rule needs> not checked`.

## Fields

| Postmark | PostHog | A site stays on Postmark when |
|---|---|---|
| `From` | `from` | Never. `Name <address>` moves as it is. It needs a verified sender (Step 4) |
| `To` | `to` | It holds more than one address: a comma in the string, a list with more than one entry in Ruby, PHP, or `postmarker`, or a value the code builds at run time that you cannot tell holds one address. A list with one entry moves as that entry. `Name <address>` moves as the bare address: note in the plan row that the To line loses the name |
| `Subject` | `subject` | A send that is not a template send leaves it out, or sets a value that can be empty: Postmark sends an email without a subject, and PostHog's send requires one. A template send takes its subject from the template, as "Templates" says |
| `HtmlBody`, `TextBody` | `html`, `text` | Never |
| `TemplateId` or `TemplateAlias`, with `TemplateModel` | the template's email, with its layout, brought into the code and rendered with `TemplateModel`, sent as `subject`, `html`, and `text`. A template made in PostHog, by its `templateId` with `templateData`, only when the person asks for one | See "Templates" |
| `InlineCss` | none | Never on its own. It shapes how Postmark rendered the template's CSS: the email brought into the code carries that CSS, as "Templates" says |
| `Cc`, `Bcc` | none | Always. PostHog's send doesn't take it yet |
| `ReplyTo` | `replyTo`, one address or a list | An entry carries a name, there are more than 10, or the code builds the value at run time and you cannot tell that it holds bare addresses only. A site that leaves it out follows "Reply-to of the sender signature" below |
| `Attachments` | `attachments` | Step 3 says so under "Files". See "Attachments" below |
| `Headers` | none | Always: no PostHog SDK takes headers yet |
| `Metadata` | none | Always: no PostHog SDK takes tags yet |
| `Tag` | none | Always: no PostHog SDK takes tags yet |
| Open and link tracking: `TrackOpens`, `TrackLinks`, or neither | none: PostHog adds its open pixel, and counts clicks only for a template made in PostHog that is not marked sensitive | Postmark sent it with opens untracked and the person doesn't agree to PostHog's open pixel, or nobody can tell whether it tracked them, as Step 3's "Opens the provider didn't track" says. See "Tracking" below |
| `MessageStream: 'outbound'` | none | Never. `outbound` is the default transactional stream |
| `MessageStream` naming any other stream | none | Always: the stream has its own settings, suppressions, and webhooks at Postmark |

Count only the fields the code sets.

**Attachments.** Postmark takes a send's files in one list, `Attachments`, of `{ Name, Content, ContentType, ContentID }`, with `Content` a Base64 string, as its email API reference and its guide "Sending email with API" say. A template send takes `Attachments` too. A site with files that moves to a template made in PostHog stays, because the template form takes no files, as Step 7 says: the reason is `a template in PostHog takes no files`. Each file of a site that moves becomes one entry of PostHog's `attachments`, under the PostHog SDK's names, as its rewrite file gives them:

| Postmark | PostHog |
|---|---|
| `Name` | The filename. A file without one keeps the site, as Step 3 says |
| `Content`, a Base64 string | The content, in the form the rewrite file gives: the same Base64 string where the SDK reads one, such as Node.js, Ruby, and Python when the string is on one line with its padding, or its decoded bytes where the SDK takes bytes only, such as PHP, .NET, and Go |
| `ContentType` | The content type, as it is: a type with parameters, such as `text/calendar; method=REQUEST`, follows Step 3 under "Files". When the file has none, Postmark's docs don't say what it sent: set the type the filename's extension names, such as `application/pdf` for `.pdf`, and note `content type set from the filename` in the plan row. When the extension names none, the site stays, and the reason is `a file without a content type` |
| `ContentID`, such as `cid:logo.png` | The content ID, the bare ID the HTML shows with `<img src="cid:...">`: take off a leading `cid:`, and the `<` and `>` around the ID if it has them, so `cid:logo.png` becomes `logo.png`. A file without a `ContentID` gets no content ID |

Postmark takes no disposition: it shows a file inline when its `ContentID` matches a `cid:` in the HTML, as its guide says under "Inline image attachments", and PostHog shows a file with a content ID inline, as Step 7 says. So the content ID carries the disposition, and there is nothing else to keep.

Some clients build these fields from forms that Postmark's docs don't cover field by field. `postmarker` takes a file as a dict of Postmark's fields, as a tuple of `Name`, `Content`, `ContentType`, and an optional `ContentID`, as a `MIMEBase` part, as the path of a file on the app's disk, whose content type it detects, and through `Email.attach_binary(content=..., filename=...)` with raw bytes, as its docs say under "Emails". A Ruby send of a `Mail::Message` through the `postmark` gem sends the files of the message. Other clients have attachment classes and helpers of their own, such as one that reads a file from a path. For each such form, read the client installed in the person's app for the `Name`, `Content`, `ContentType`, and `ContentID` it sends, map those as the table says, and name the file you read in the plan row. When the installed client doesn't settle a field, the site stays, and the reason is `Postmark's handling of <the form> not checked`.

Postmark fetches no file: its API takes only a file's Base64 content, so a site never stays for a fetched file. A client that reads a file from a path reads it in the app, and so does the rewrite: read the same file, such as with `open(path, 'rb').read()`, and pass its bytes, with the filename and content type the client sent for it.

Postmark takes an email of up to 10 MB after Base64 encoding with its files, as its guide says under "Limitations", so every email Postmark took fits under PostHog's 40 MB. Its docs give no limit on the count, and PostHog takes at most 10 files, as Step 3 says. Postmark refused a file with the extension `vbs`, `exe`, `bin`, `bat`, `chm`, `com`, `cpl`, `crt`, `hlp`, `hta`, `inf`, `ins`, `isp`, `jse`, `lnk`, `mdb`, `pcd`, `pif`, `reg`, `scr`, `sct`, `shs`, `vbe`, `vba`, `wsf`, `wsh`, `wsl`, `msc`, `msi`, `msp`, or `mst`, with error code `411`, and PostHog refuses the extensions Step 3 lists. PostHog takes `.bin`, `.vba`, and `.wsl`, and an email from 10 MB up to 40 MB, which Postmark answered with status `413`, as its API reference says: where the site can send an email Postmark refused for one of these, that email now goes out. Note `<the email> Postmark refused now goes out` in the plan row.

**Tracking.** PostHog adds its open pixel to every email it sends, to count opens. A send in the code form is sensitive, so PostHog never rewrites its links and counts no clicks for it. A template made in PostHog that is not marked sensitive gets its links rewritten, as "Templates made in PostHog" says. No field changes this: `captureEngagement` decides only whether the email's events land on the recipient's person, so tracking never maps to it. Postmark tracks opens when the send's `TrackOpens` is `true`, or, when the send leaves it out or sets it to `null`, when its server's open tracking is on. It tracks links when the send's `TrackLinks` is anything but `None`, or, when the send leaves it out, when its server's link tracking is on. A new server tracks neither, until the person turns them on in its settings. `postmarker` sends `TrackLinks: "None"` when the code doesn't pass it, from `emails.send`, `emails.send_with_template`, and a message built with `client.emails.Email(...)` or `client.emails.EmailTemplate(...)`: links of those sends were not tracked. Another client can also send a value the code never set, as the paragraph below that starts "Opens follow the server's setting" says: read the installed client for it. Work out, for opens and for links, whether Postmark tracked them:

- Opens tracked: the site moves. When Postmark tracked its links too, and the site moves in the code form or to a template marked sensitive, note in the plan row that PostHog counts no clicks for it.
- Opens untracked: the site follows Step 3's "Opens the provider didn't track": it moves only when the person agrees to PostHog's open pixel, and otherwise stays with `open tracking off`.

Link tracking never adds a field, and keeps no site in the code form. A template site follows these bullets too, whether it moves into the code or to a template made in PostHog. A site that moves to a template made in PostHog also follows Step 3's rule on clicks Postmark didn't track, under "A template in PostHog".

Opens follow the server's setting when the request leaves out `TrackOpens` or sends it as `null`, and links when it leaves out `TrackLinks` or sends it as `null`: a value in the request sets tracking for that email, as Postmark's guide says under "Tracking opens" and "Tracking links". What the request held can differ from what the code set: a client can send a value the code never set, or leave out one it set. `postmarker` sends `TrackLinks: "None"` when the code leaves it out, as its reference gives, so its links were not tracked. For any other client, read the installed client for the `TrackOpens` and `TrackLinks` it sends for the site's message, as "What Postmark's docs don't give" says, and go by what it sends. When either one follows the server, ask the person once for each server the moved sites send from whether its open tracking and link tracking are on, or read them as `account.md` says under "Tracking settings". When a site's opens follow the server and the answer for open tracking is not given, nobody can tell whether Postmark tracked them: the site stays, and the reason is `open tracking not checked`, as Step 3's "Opens the provider didn't track" says. An unanswered link tracking setting keeps no site in the code form. For a site that moves to a template made in PostHog, it means nobody knows whether Postmark tracked its clicks.

**Test token and sandbox servers.** Postmark's test token, `POSTMARK_API_TEST`, checks a send and delivers nothing, and so does every send through a server whose delivery type is Sandbox. Where an environment of the app sends with one, such as tests, CI, or staging, a moved site would deliver real email there. Find the token each environment reads, and ask the person which of the servers are sandbox servers, or read `DeliveryType` from `GET /server`, as `account.md` says under "Tracking settings". PostHog has no test token and no sandbox: the key of any project, one kept for tests too, delivers real email, and a client without a key fails every send. So ask the person, for each such environment, which of these holds:

- The app already replaces its email sending there, at a seam of its own, such as a mailer interface or a fake that its tests inject. The moved site sends nothing there either, and the site moves.
- The person accepts that the environment delivers real email once the site moves. Note their answer in the plan, and the site moves.
- Otherwise, the site stays, and the reason is `<environment> sends with Postmark's test token` or `<environment> sends through a sandbox server`.

For each environment where the person accepted real delivery, write a note under the plan's sites table that starts with `before cutover:` and names what the person does, such as `before cutover: staging delivers real email from PostHog once deployed; check that its recipients are addresses you accept mailing`. Step 9 reads only the plan, and its "Before cutover" list is everything the person still has to do, so the note carries the item there. An environment whose app replaces its sending needs no note.

**Reply-to of the sender signature.** A sender signature at Postmark can hold a Reply-To address, and Postmark sets it on every send from that signature's `From` address that leaves out `ReplyTo`. A site that sets `ReplyTo` keeps its own. For the sites that leave it out, ask the person once for each `From` address whether its sender signature has a Reply-To address, as `account.md` says under "Sender signatures". When it has one, the moved send sets `replyTo` to it, under the rules of the `ReplyTo` row above, and the plan row says that it came from the signature. When the `From` address has no sender signature of its own, Postmark set no reply-to address. When the answer is not given, the site stays, and the reason is `sender signature reply-to not checked`.

A Postmark send has no idempotency key, so the moved site sends none either. PostHog's SDK makes one for each call and reuses it on its own retries.

## Calls

| Postmark call | A site stays on Postmark when |
|---|---|
| `POST /email`, and each client's method that sends to it, such as `sendEmail` in Node.js and PHP, `outbound.send`, `emails.send` (`postmarker`), `deliver` in Ruby, and `SendMessageAsync` in .NET | A field above keeps it |
| `POST /email/withTemplate`, and each client's method that sends to it, such as `sendEmailWithTemplate` in Node.js and `emails.send_with_template` (`postmarker`) | See "Templates" |
| `POST /email/batch`, `/email/batchWithTemplates`, and `/email/bulk`, and each client's method that sends to them, such as `emails.send_batch` and `EmailBatch` (`postmarker`) | Always: each sends several emails in one call. The one exception is a batch call whose argument is a list of exactly one message, written in the code, such as `emails.send_batch(message)`: that is one send. Classify it by that message's fields, and a template message by "Templates" |
| SMTP through `smtp.postmarkapp.com` or `smtp-broadcasts.postmarkapp.com` | Always. PostHog has no SMTP relay |
| A framework mailer (`postmark-rails`, a Django backend, Laravel or Symfony `postmark`, Swoosh, Bamboo, `nodemailer-postmark-transport`) | Always. PostHog has no mailer driver |
| A send in a language without a PostHog SDK that sends email, such as Java or Kotlin | Always. Step 7 lists the languages PostHog's SDKs cover |

## Servers

Each Postmark server has its own tokens, templates, tracking settings, and suppression lists. A site sends from the server its token belongs to. When the app reads more than one Postmark token, ask the person once which server each one belongs to, and record each site's server under the sites table.

PostHog keeps one suppression list per project. When the sites that move send from more than one server, Step 5 imports the `outbound` list of each of them into that one list. PostHog then refuses a moved send to an address that any of those servers suppressed, even when the site's own server never suppressed it or reactivated it. Tell the person so, and ask once whether the moved sites may share one suppression list. When they say no, ask which one server's sites move. The sites of every other server stay, and the reason is `server <name> keeps its own suppression list`.

## Code around the send

A Postmark client raises or returns an error for an error answer: Node.js's `sendEmail` rejects, as Postmark's "Official libraries" page shows, and the installed client says what any other one does, as "What Postmark's docs don't give" says. A raw HTTP call reads the status code or the `ErrorCode` in the answer. The rewrite file says under "The answer" how PostHog's SDK reports an error in its language. Keep the site failing the same way it did, as the Rewrite section says.

| Code | A site stays on Postmark when |
|---|---|
| A `catch`, `except`, or `rescue` that only logs or rethrows the error | Never |
| A branch on the HTTP status of Postmark's error | Never. Read PostHog's status code, or PostHog's error name for a `422`, as the Rewrite section says |
| A branch on an inactive recipient: `ErrorCode` `406`, or a Postmark error class that the installed client raises for it | Never. PostHog refuses a suppressed address with the code `recipient_suppressed` |
| A branch on another Postmark `ErrorCode`, or on the error's message text | Always. A catch of a Postmark error class is not such a branch: the Rewrite section maps it by the answers the class covers |
| A read of the inactive addresses from the error | Always |
| A check of `ErrorCode`, `Message`, or another field of a send's answer that tells a refusal | Never. Read PostHog's error instead, as the Rewrite section says |
| `MessageID` stored for a webhook handler or a status read | Always, when a webhook handler or the Messages or Bounces API uses it |
| `MessageID` logged or stored for the app's own use | Never. Use PostHog's message id |
| A send the code can cancel: a raw request with a `signal` a caller passes in or an `AbortController` it aborts, a .NET request with a cancellation token a caller can cancel, or a Go context a caller can cancel, passed to the Go package's send | Unless the PostHog send in that language takes the same cancellation, as Go's `Send(ctx, ...)` and .NET's `SendAsync(..., cancellationToken)` do: pass it there. Otherwise always: an email the old code cancelled would go out. A fixed deadline, such as `AbortSignal.timeout(...)`, moves as "HTTP" says under "Rewrite" |

## Templates

A template site moves by bringing the template into the code, as `template-to-code.md` says. The check needs the template's subject, HTML body, and text body, because the code has only its id or alias. `account.md` says how to get them. The code renders them with the site's `TemplateModel`, and the send sets the rendered `subject`, `html`, and `text`.

A template with a layout (its `LayoutTemplate` names one) renders inside that layout at `{{{ @content }}}`, so the layout and the template come into the code as one email: the layout's HTML with the template's HTML in place of `{{{ @content }}}`, and the same for the text body, all rendered with the same `TemplateModel`. The check needs the layout's content too. When several emails share a layout, write it once as a piece they share. When only one of the layout and the template has a text body, the docs don't say what Postmark sent as text, so the template stays on Postmark.

Postmark templates are Mustachio. In the code:

| Postmark | In the code |
|---|---|
| `{{name}}`, `{{ name }}` | The value, escaped. A missing or `null` value renders as nothing, and so does a list or an object. A number renders as its digits. A boolean renders as `True` or `False`, as Mustachio's source does: the docs don't say, so note it in the plan row |
| `{{person.first_name}}` | The nested value, escaped. A missing step of the path renders as nothing |
| `{{{name}}}`, `{{& name}}` | The value as it is, unescaped, under the rule of `template-to-code.md`. In the subject and the text, it is the plain value |
| `{{#paid}}…{{/paid}}`, on a value that is never a list | The part, rendered once when the value passes Mustachio's truth test below. Inside it, names are read from that value: `{{#person}}{{first_name}}{{/person}}` reads `person.first_name`, and `{{.}}` is the value itself |
| `{{^paid}}…{{/paid}}` | The part, rendered when the value fails the truth test |
| `{{name}}{{^name}}there{{/name}}`, Mustachio's only fallback | Two parts, each by its row above: the value, then `there` when the value fails the truth test. Write them apart, never as "the value or `there`": `false` renders as `Falsethere`, and `""` as `there` |
| `{{#each items}}…{{/each}}` | A loop over the list, in order. Nothing when the list is missing, `null`, or empty |
| Inside `{{#each items}}`: `{{.}}`, `{{name}}`, `{{#each .}}` | The current item, its field, or a loop over the item when it is a list itself. Mustachio has no index, first, or last |
| `{{../name}}`, `{{../../name}}` | The value one level out for each `../`. Out of a section, one level is the scope the section is in. Each step of a dotted name is a level too: inside `{{#person.address}}`, one `../` reads `person`, and `../../` the scope the section is in. Out of an `each` item, one level is the list, so `../../name` reads the scope the list is in. A `../` past the top stays at the top, in Mustachio's source |
| `{{! note }}` | Nothing |
| The layout's `{{{ @content }}}` | The template's HTML, or its text, in its place |
| The template's `Subject` | The send's `subject`, rendered with the same conversions and no escaping. A layout has no subject. A subject that can render empty keeps the template on Postmark, as the Fields table says |
| The template's `TextBody`, inside the layout's | The send's `text`, with no escaping. Mustachio keeps every line break around its tags, so keep the lines as they are. A template without a text body sends `html` only |

- Mustachio's truth test: a missing value, `null`, `false`, `""`, and an empty list fail it. Every other string, including `"0"` and `"false"`, `true`, a number other than `0`, and an object with keys pass it. Write that test out in the code, as `template-to-code.md` says. The docs don't say what `0` or an empty object does: a section or an inverted section whose value can be either keeps the template on Postmark, because which part Postmark sent can't be told.
- Inside a section or an `each`, a bare name reads only the section's value or the current item. Postmark's docs reach an outer value with `../` only, and don't say whether a bare name looks outside: a bare name that the value or the item doesn't always carry keeps the template on Postmark. So does a bare name inside an inverted section, which has no value to read it from: only `../` reads there.
- A section `{{#items}}` on a value that can be a list, an `{{#each}}` on a value that can be an object or a scalar, a path into a list by position, such as `{{items.0.name}}`, a partial (`{{> name}}`), and any other tag keep the template on Postmark. The docs show a list only with `each`, and Mustachio's source renders such a section once with the whole list as its value and fails such an `each`.
- `{{{ pm:unsubscribe }}}`, also inside a link as `href="{{{ pm:unsubscribe }}}"`, keeps the template on Postmark: Postmark fills it from its account with the stream's unsubscribe link.
- With `InlineCss` on, its default, write each `<style>` rule into the `style` attribute of the tags it matches, as Postmark did when it sent the email, and keep the `<style>` block for the rules a tag can't hold, such as `@media`. Do it once, while you write the email: the code adds no inliner. Postmark's docs don't say whether it kept the `<style>` block, so note in the plan row that the CSS was inlined in the code, for the person to compare a test send. Postmark inlined after it rendered the values, so a rule whose match can depend on a value, such as `.badge-paid` against `class="badge-{{status}}"`, keeps the template on Postmark. A site that sends `InlineCss: false` keeps the HTML as it is. What the request held can differ from what the code set: read the installed client for the `InlineCss` it sends for the site's template send, as "What Postmark's docs don't give" says, and go by what it sends.
- Postmark hosts no images for templates: its editor has no upload, and its docs name no image host. A template's images are on the person's own hosts, so none needs listing.
- A Postmark template holds no sender or reply-to address, and a template send always sets `From`. The send takes the site's own `From`, and its own `ReplyTo` or its sender signature's, as "Fields" says. Its subject comes only from the template: the template routes take no `Subject`.
- A template site follows "Tracking" like any other site, and Step 3's "Opens the provider didn't track" for opens Postmark didn't track.
- No single send fills Postmark's template language into its own content: `POST /email` and the batch route send `Subject`, `HtmlBody`, and `TextBody` as they are, so a `{{name}}` in them was mailed as written, and nothing about it changes. Only the Bulk API fills its own content with each message's `TemplateModel`, and a bulk call stays, as "Calls" says.

### Templates made in PostHog

Only for a template the person asks to make in PostHog, as Step 3 says. This skill never makes one: the person makes it from the Postmark template and gives you its template ID, and makes it transactional once a verified sender covers its address, as Step 3 says. Until they give the ID, the site stays on Postmark.

An email that carries a login code, a reset link, or another secret needs its PostHog template marked sensitive: PostHog then keeps no copy of each sent email's body or filled-in subject, and sends its links as they are, without its click redirect. Templates are not sensitive by default. When Postmark didn't track the site's links, or nobody knows whether it did, as `account.md` says under "Click tracking", ask the person to mark the template sensitive too, as Step 3 says under "A template in PostHog".

For a template with a layout, the person makes one PostHog template from both: the layout's HTML with the template's HTML in place of `{{{ @content }}}`, and the same for the text body. Tell them so when you ask them to make it.

Postmark's Mustachio becomes Liquid in the PostHog template. Values move under `variables`, and each name keeps its case:

| Postmark | PostHog |
|---|---|
| `{{name}}`, `{{ name }}` | `{{ variables.name }}` |
| `{{person.first_name}}` | `{{ variables.person.first_name }}` |
| `{{#paid}}…{{/paid}}`, when `paid` is always a boolean, `null`, or missing | `{% if variables.paid %}…{% endif %}` |
| `{{^paid}}…{{/paid}}`, when `paid` is always a boolean, `null`, or missing | `{% unless variables.paid %}…{% endunless %}` |
| `{{#person}}{{first_name}}{{/person}}`, when `person` is always an object with keys, `null`, or missing | `{% if variables.person %}{{ variables.person.first_name }}{% endif %}` |
| `{{#each items}}{{name}}{{/each}}`, when `items` is always a list | `{% for item in variables.items %}{{ item.name }}{% endfor %}` |
| `{{.}}` inside `{{#each items}}` | `{{ item }}` |
| `{{../company}}` inside a top-level `{{#person}}` section whose name has no dot, or `{{../../company}}` inside a top-level `{{#each items}}`, where `company` is a top-level key of `TemplateModel` | `{{ variables.company }}` |
| The template's `Subject` | The PostHog template's subject, with the same conversions |

- Mustachio escapes HTML in values, and so does PostHog's Liquid, so plain values render the same.
- Mustachio prints a boolean as `True` or `False`, and Liquid as `true` or `false`. Mustachio prints nothing for a list or an object, and Liquid prints its contents. A `{{name}}` whose value can be a boolean, a list, or an object keeps the template on Postmark.
- Mustachio skips a section whose value is false, empty, or missing, and Liquid treats `0`, an empty string, and an empty list as true. Read what the site sends for each section value. A value that is not always a boolean, `null`, or missing, such as a number, a string, or a list, keeps the template on Postmark. So does an object that can be empty.
- Liquid's `for` walks only a list. An `each` over a value that is not always a list, such as an object, keeps the template on Postmark.
- Inside `{{#each items}}`, a bare `{{name}}` reads the current item. It becomes `{{ item.name }}`, never `{{ variables.name }}`. A name that the item doesn't always carry keeps the template on Postmark, because Liquid won't look for it outside the loop.
- `{{{name}}}` and `{{& name}}` insert HTML as it is. PostHog's Liquid escapes it, so a template that uses them stays on Postmark. The layout's own `{{{ @content }}}` is the one exception: the person replaces it with the template.
- `{{{ pm:unsubscribe }}}` keeps the template on Postmark: it is Postmark's unsubscribe link.
- An inverted section `{{^items}}` on a list or an object, a section `{{#items}}` on a list without `each`, a name inside `{{#person}}` that the site doesn't put on `person`, and `../` that reads anything but a top-level key all keep the template on Postmark. Inside `{{#each}}`, one `../` reaches the list, not the model: Postmark needs `../../` for a top-level key there.
- The PostHog template carries its own sender, reply-to address, and subject. A Postmark template send always sets `From`: the site moves only when `From` is the same in every send, and the person makes the PostHog template send from it. The same holds for the reply-to address the send had, its own `ReplyTo` or its sender signature's. Otherwise it stays.
- A template site follows "Tracking" like any other site: opens Postmark didn't track, by the value its client sent or its server's setting, and an open tracking setting nobody checked follow Step 3's "Opens the provider didn't track". It also follows Step 3's rule on clicks Postmark didn't track. When it moves, the tracking fields are dropped, and so is `MessageStream: 'outbound'`. `Cc`, `Bcc`, `Attachments`, `Headers`, `Metadata`, `Tag`, and a `MessageStream` other than `outbound` keep any site, as the Fields table says.
- With `InlineCss` on, its default, Postmark moved the template's `<style>` rules into each tag. Tell the person to check how the PostHog template looks in its test send.

## Webhooks

Postmark stops sending events for a site that moves. PostHog records the events of a moved send on the person it names with `distinctId`, when engagement capture is on:

| Postmark `RecordType` | PostHog event |
|---|---|
| `Delivery` | `$workflows_email_delivered` |
| `Bounce` | `$workflows_email_bounced` |
| `SpamComplaint` | `$workflows_email_blocked` |
| `Open` | `$workflows_email_opened` |
| `Click` | `$workflows_email_link_clicked`, only for a template made in PostHog that is not marked sensitive. PostHog treats a send in the code form as sensitive: its links go out as they are, and it counts no clicks |
| `SubscriptionChange` | none |

Postmark has no event for an accepted send. PostHog records `$workflows_email_sent` for each moved send. A send to an inactive address got a `406` error from Postmark, and Postmark posted no webhook for it. PostHog refuses it with `recipient_suppressed`.

PostHog's events carry no Postmark `MessageID`, no `Metadata`, and no `Tag`. A site whose events a handler matches by message id, by a metadata value, or by tag stays on Postmark. For every other handler, such as one that matches by the recipient's address, the report tells the person which events it handles, which PostHog events take their place, and that a webhook destination in PostHog (Data pipelines, then Destinations) can post them to an endpoint. The handler itself keeps working for the sites that stay. Never change it.

A site whose emails a `SubscriptionChange` handler acts on stays, since PostHog has no event for it, and the reason is `its SubscriptionChange events feed a webhook handler`. A site whose emails a `Click` handler acts on moves only to a template made in PostHog that is not marked sensitive, since a send in the code form counts no clicks. Otherwise it stays, and the reason is `its clicks feed a webhook handler`.

## Calls that change the suppression list

Step 5 says what to do with each of these calls. They are not sends, and they stay on Postmark.

| Adds an address | Removes an address |
|---|---|
| `POST /message-streams/{stream}/suppressions`, and each client's method that calls it | `POST /message-streams/{stream}/suppressions/delete`, and each client's method that calls it. `PUT /bounces/{bounceid}/activate` too, which reactivates a hard bounce and takes its address off the list, and each client's method that calls it |

Only a call on the `outbound` stream of a server whose list Step 5 imports counts, as "Servers" says. A bounce activation counts when the bounce's `MessageStream` is `outbound`. When a call names no stream, read the installed client for the stream it calls, as "What Postmark's docs don't give" says. A call on any other stream changes a list the import leaves out.

## Rewrite

How a site that moves is written with PostHog's SDK. Step 7 says when to use each part, and the rewrite file for the site's language has the client and the send.

**The PostHog client.** Set `migratedFrom: 'postmark'` on the client that Step 7 configures, when its client options take it.

- Python: `postmark-python` is async. A site that awaits `client.outbound.send` moves to `AsyncPosthog` and `await posthog.emails.send(...)`, with `posthog[async]` installed, as the rewrite file says. A site on a client it calls without `await`, such as `postmarker`, moves to `Posthog`.

**The call.** The Postmark send becomes one PostHog send. Build its fields from the message the site built:

- Node.js `client.sendEmail({ ... })`: the fields of the message, also when the code builds it with a class of the library.

- Ruby `client.deliver(from:, to:, subject:, html_body:, text_body:, ...)`: the same fields.
- A Ruby send of a `Mail::Message` through the `postmark` gem, of a message alone, of a message with a template, or of a batch of one message: the fields of the `Mail::Message`. The gem can also set state on that message as it sends. Postmark's docs don't say what: read the installed `postmark` gem for what the call sets on the message, after a sent email and after an error, and name the file you read in the plan row. Then find every read of that state on a `mail` the site sends, wherever it sits: after the call, before it, such as a guard in a retry loop, in a caller that passed `mail` in, or in any code that gets the same `mail` later, such as from the site's return value or a variable that keeps it. A batch of one with any such read keeps the site: the batch route answered a refused message without an error, as "A batch of one" below says, so the read told a refusal from a sent email. After a send of a message alone, with or without a template, a read in the site's own method after the call reads PostHog's answer instead. After a send that returned, the email went out, and its message id is PostHog's. In an error path, it reads PostHog's error, as "Errors" says, such as `e.code == 'recipient_suppressed'` for an `ErrorCode` of `406`. Any other read keeps the site, and the reason is `reads the state the postmark gem set on the message`. Never set that state on `mail` in the rewrite.
- PHP `sendEmail($from, $to, $subject, $htmlBody, ...)`, as Postmark's "Official libraries" page begins it, and the client's other sends that take the fields as arguments: read each argument by its name, or by its position in the order the installed client declares, as "What Postmark's docs don't give" says. - .NET `new PostmarkMessage { ... }`, as Postmark's "Official libraries" page shows: the same fields. A constructor or a send that takes the fields as arguments: read each argument by its position, in the order the installed client declares, as "What Postmark's docs don't give" says, and an argument the client leaves out of the request sets nothing. A synchronous send: the rewrite file says what a synchronous .NET site does.
- Go: the fields of the message the package sends, under the names the installed package gives them.
- A raw HTTP body: its fields.
- A batch of one message: the fields of that message, sent with PostHog's send for one email.
- A template send, to `POST /email/withTemplate`, such as `sendEmailWithTemplate` in Node.js or `postmarker`'s `send_with_template`: its `From`, `To`, `ReplyTo`, and tracking fields, as for any message, and the rendered email, as "Templates brought into the code" says. A template send that takes its fields as arguments, such as PHP's: read each argument by its position, in the order the installed client declares.

When the app gets `css-inline` only through `postmarker`'s `css-inline` extra, add `css-inline` as its own dependency, at the version installed now, and note it as a new dependency under the sites table, so it stays when the person removes `postmarker` after the cutover. **HTTP.** A request to `https://api.postmarkapp.com/email` or `/email/withTemplate`, through `fetch`, axios, `requests`, `httpx`, `net/http`, Faraday, Guzzle, `HttpClient`, `reqwest`, `Req`, or `curl`, becomes the SDK's send in that language, as "The call" says. An axios `timeout` in Node.js, and a Ruby limit on the whole request, such as Faraday's `timeout` on another adapter, are limits the SDK can't keep, as Step 7 and `rewrite-ruby.md` say.
- `postmarker`: `PostmarkClient(server_token=..., timeout=...)`, which it passes to `requests`, as its docs say under "Usage": a number of seconds, or a pair that limits connecting and reading apart, which Step 7 keeps the site for.
- Any other Postmark client: a timeout the code sets on the client, or on the HTTP client it sends through. Postmark's docs don't give what it limits: read the installed client for what each one limits, the whole request, connecting, or each read or write, its unit, and the value of each limit the code leaves out, as "What Postmark's docs don't give" says. Then follow Step 7 and the rewrite file under "A deadline", as for a raw request with the same limits.
- Go: a context with a deadline passed to the package's send, or a `Timeout` on the `http.Client` it sends through.

A timeout the client sets by default, which the code never set, is not the site's own, as Step 7 says. Step 7 turns the send's retries off because the request never retried. A Postmark client that retried keeps that count instead: `postmarker`'s `max_retries`, 0 unless the code sets it, which it passes to `requests`' `HTTPAdapter`, as its docs say. For any other client, read the installed client for whether it retried, and how many times after the first try, as "What Postmark's docs don't give" says. The send's retries take that count, under the rewrite file's name for them under "A deadline".

PostHog's SDK retries a network error, a rate limit, and a server error only when it is a 503. Read the installed client for the statuses it retried, as "What Postmark's docs don't give" says. A server error it retried other than a 503 now fails at the first try. The site still moves. For each moved site whose Postmark client retried such an error, or whose client doesn't say which statuses it retried, write a note under the plan's sites table, `before cutover: <file>:<line> no longer retries a server error other than 503; check that its error path handles one`, which Step 9 carries into "Before cutover" as the test environments above say.

**Templates brought into the code.** The site renders the email, inside its layout, from `TemplateModel`, as "Templates" says, and sends `templateKey`, the rendered `subject`, `html`, and `text`, and the site's own `from` and `replyTo`. It sends no `templateId` and no `templateData`, and drops `TemplateId`, `TemplateAlias`, `TemplateModel`, and `InlineCss`.

**Templates made in PostHog.** The site sends `templateId` with the template ID the person gave, and `templateData` with the site's `TemplateModel`. It sends no `templateKey`, `subject`, `html`, `text`, `from`, or `replyTo`: the template holds them.

**Errors.** Postmark refused a send to an inactive address with error code `406`, and the site's error path ran. PostHog refuses it with `recipient_suppressed`, so the same path runs: the site needs no new branch. Keep the site failing the same way it did:

The bullets below change Postmark's error to PostHog's. When the same `try`, `begin`, or error check also covers a Postmark call that stays, such as a template or suppression call, keep Postmark's handler for that call and add PostHog's next to it. A kept branch that tells errors apart by a field PostHog's error also has, such as a status code, first checks that the error is not PostHog's, so PostHog's errors take only PostHog's branches and every other error, from Postmark or from another call in the same block, takes the kept branch as before: `not isinstance(e, EmailError)` in Python, `!e.is_a?(PostHog::EmailError)` in Ruby, `!($e instanceof \PostHog\EmailError)` in PHP, `ex is not PostHog.Emails.EmailException` in .NET, and no `errors.As` match for `*posthog.EmailError` in Go. In Node.js, a branch on a field takes both errors in one check instead, `err.posthog ? (<mapped check>) : (<old check>)`, as the Node.js bullet below says.

Never widen a catch. Where the code caught only one kind of Postmark error, catch PostHog's error, check its `code` or status code for that kind, and raise or return every other error as before. Postmark's docs give the answers of its API, by HTTP status and `ErrorCode`, and not which of them each of a client's error classes covers. So for each Postmark error class a site catches or checks, read the installed client, as "What Postmark's docs don't give" says, for the statuses and `ErrorCode`s it raises that class for, and for whether it also raises it for a network failure, a timeout, its own check of the message before any request, or an answer whose body it couldn't parse as Postmark's JSON. The catch then takes PostHog's errors for the answers the class covered, as mapped below, and raises every other error again. The answers map like this:

- A status of `422` is PostHog's error name `validation_error`, never a status, because PostHog's statuses for an invalid send differ from Postmark's. It covers `recipient_suppressed`, a `validation_error` with status `422`, too: where the site treats an inactive recipient apart, handle it first. For a site that moves to a template made in PostHog, a `422` also covered a template Postmark couldn't find, `ErrorCode` `1101` with status `422` in Postmark's API reference, which PostHog answers with status `404` and the code `not_found`, as its transactional email docs say: its branch covers `not_found` too, such as `err.name === 'validation_error' || err.code === 'not_found'`, and so does a branch on a class that covered `1101`.
- `ErrorCode` `406`, an inactive recipient, is the code `recipient_suppressed`.
- `ErrorCode` `300`, an invalid email request, is a `validation_error` with any code but `recipient_suppressed` and `sender_not_verified`: Postmark answered an inactive recipient with `406`, and its API reference lists no `300` for a sender it refused. So a branch on `300`, or on a class that covered `300` and not `406`, raises `recipient_suppressed` and `sender_not_verified` again first.
- A status of `401` is status 401.
- A status of `429` is status 429 with a code other than `quota_limited` and `upload_quota_exceeded`: PostHog answers a used-up sending quota with 429 and `quota_limited`, and a used-up allowance for file uploads with 429 and `upload_quota_exceeded`. No retry fixes either, so each takes the path of every other error, as Step 7 says.
- A status of `500` or `503` is that status.
- A network failure or a timeout that is left after PostHog's retries has the code `network_error`. A catch that let them go past it raises the error again when its code is `network_error`. A catch of one kind of network failure, such as a timeout and not a refused connection, keeps the site, as Step 7 says (`catches one kind of network failure`).
- An answer that holds no PostHog error code, such as a proxy's HTML page for a 502, has the code `api_error` in PostHog's SDK. A catch that took an answer its client couldn't parse takes `api_error`, and one that let it go past raises `api_error` again too. When the client doesn't settle it, the site stays, and the reason is `Postmark's handling of an answer it couldn't parse not checked`.
- A class the client raised for its own check of the message, before any request: where the old code handled a bad value, also catch the argument error that the rewrite file names, as Step 7 says.

Each language writes the catch like this:

- **Node.js.** `posthog.emails.send` never throws on an API error: it answers `{ data, error }`. Where `sendEmail` threw into a `catch`, or up to the caller, throw from the error so the same code runs: `if (error) throw Object.assign(new Error(error.message), { statusCode: error.statusCode, code: error.code, name: error.name, posthog: true })`. `statusCode` and `code` there stand for the fields that the installed client's error carries the HTTP status and the `ErrorCode` in: read it for their names, as "What Postmark's docs don't give" says, and give PostHog's error the same names, so the code reads them as before. `err.name` holds PostHog's error name. `err.posthog` marks PostHog's error, so another call's error in the same `try`, such as a payment call's `500`, takes the branches it took before. A branch on a Postmark class, an `instanceof` check, took only Postmark's errors: it becomes `err.posthog && (<mapped check>)`, such as `err.posthog && (err.statusCode === 429 && err.code !== 'quota_limited' && err.code !== 'upload_quota_exceeded')`. A branch on a field, such as `err.statusCode === 422` or `err.code === 406`, took any error with that field: it becomes `err.posthog ? (<mapped check>) : (<old check>)`, such as `err.posthog ? (err.name === 'validation_error') : (err.statusCode === 422)`. Keep the parentheses, so the mark covers a check with `||` whole. `err.code` now holds PostHog's code, a string. The `<mapped check>` of each branch, which goes inside the forms above, checks the answers it covered, as mapped above: for `ErrorCode` `406` it is `err.code === 'recipient_suppressed'`, for a status of `422` it is `err.name === 'validation_error'`, for `ErrorCode` `300` it is `err.name === 'validation_error' && err.code !== 'recipient_suppressed' && err.code !== 'sender_not_verified'`, for a status of `429` it is `err.statusCode === 429 && err.code !== 'quota_limited' && err.code !== 'upload_quota_exceeded'`, and for another status it is a check of `err.statusCode`. A site that passes a callback, such as `client.sendEmail(message, callback)`: read the installed client for how it calls the callback on success and on an error, and whether it also returns a promise, as "What Postmark's docs don't give" says. Call it the same way from PostHog's answer, such as for `callback(null, response)` on success and `callback(error, null)` on an error: `posthog.emails.send({ ... }).then(({ data, error }) => error ? callback(Object.assign(new Error(error.message), { statusCode: error.statusCode, code: error.code, name: error.name, posthog: true }), null) : callback(null, data))`, with the branches inside the callback mapped as above, and its read of `MessageID` becoming `id`. Where the client also returned its promise, and the code awaits or chains it too, build the error once, call the callback, and then throw that error or return `data`, so the awaited value and the `catch` stay as they were.
- **Python.** PostHog's SDK raises too. An `except` of a Postmark class becomes `except EmailError as e:`, with the PostHog exception the rewrite file names, that raises every error but the answers the class covered again first, as mapped above, such as `if e.code == 'network_error': raise` for a class that let network errors go past it, `if e.code != 'recipient_suppressed': raise` for one that covered only `406`, or `if not (e.status_code == 429 and e.code not in ('quota_limited', 'upload_quota_exceeded')): raise` for one that covered only a `429`. A read of the Postmark error's status becomes `e.status_code`, a check of it for `422` becomes `e.name == 'validation_error'`, and a check of its `ErrorCode` for `406` becomes `e.code == 'recipient_suppressed'`. Where the class covered the client's own check of the message, the argument errors are `TypeError` and `ValueError`.
- **Ruby.** A `rescue` of a Postmark class becomes `rescue PostHog::EmailError => e` that raises every error but the answers the class covered again first, as mapped above, such as `raise if e.code == 'network_error'` for a class that let network errors go past it, `raise unless e.name == 'validation_error'` for one that covered every `422`, `raise if ['recipient_suppressed', 'sender_not_verified'].include?(e.code)` and then `raise unless e.name == 'validation_error'` for one that covered only `300`, and `raise unless e.code == 'recipient_suppressed'` for one that covered only `406`. A read of the Postmark error's status becomes `e.status_code`, a check of it for `422` becomes `e.name == 'validation_error'`, and a read of its `ErrorCode` becomes `e.code`, as mapped above.
- **PHP.** A `catch` of a Postmark class becomes `catch (\PostHog\EmailError $e)` that throws every error but the answers the class covered again first, as mapped above, such as `if ($e->getErrorCode() === 'network_error') throw $e;` for a class that let network errors go past it. A read of the Postmark error's status becomes `getStatusCode()`, a check of it for `422` becomes `getErrorName() === 'validation_error'`, and a check of its `ErrorCode` for `406` becomes `getErrorCode() === 'recipient_suppressed'`.
- **.NET.** A `catch` of a Postmark exception becomes `catch (PostHog.Emails.EmailException ex) when (...)`, with a filter that takes only the answers the exception covered, as mapped above, such as `ex.Code != "network_error"` for one that let network errors go past it, and `&& ex.Code != "api_error"` for one that let an answer its client couldn't parse go past it too. A read of the error's message becomes `ex.Message`, a branch on a `422` becomes `ex.Name == "validation_error"`, and a check of its `ErrorCode` for `406` becomes `ex.Code == "recipient_suppressed"`.
- **Go.** Keep `if err != nil`, and read PostHog's `*posthog.EmailError` with `errors.As` where the code read Postmark's. A branch on one `ErrorCode` becomes a check of the error's `Code` or `StatusCode`, a branch on a `422` reads its `Name` for `validation_error`, and every other error goes on as before.
- **A raw HTTP call.** The code read the status or `ErrorCode` of the answer. Read PostHog's error the way the rewrite file says under "The answer", and keep each branch: a status of 400 or more, or an `ErrorCode` other than 0, becomes "there is an error", a branch on `422` reads PostHog's error name `validation_error`, and a branch on another status reads PostHog's status code, with a `429` branch that skips the codes `quota_limited` and `upload_quota_exceeded`.

**Checks of the answer.** Read the installed client for whether a single send raised on an error answer before the code read the answer, as "What Postmark's docs don't give" says. When it did, a check after the call, such as of the answer's `ErrorCode`, only ever saw a sent email: remove the check, keep the code it guarded on success, and let PostHog's error take the path Postmark's error took, as the bullets above say. When it didn't, the check becomes a check for PostHog's error, and the code it ran on a refusal runs on PostHog's error, as "A raw HTTP call" above says.

**A batch of one.** The batch route answers `200` even when it refuses the message, and puts the refusal in the message's `ErrorCode` in the answer's list: a refusal of that message, such as `300` (an invalid email request) or `406` (an inactive recipient). A failure of the whole request is an error answer, which the client raised or returned as for a single send: a bad token (`401`), a rate limit left after the retries (`429`), a request Postmark could not read, such as invalid JSON (`422` with code `402`), a server error (`500` or more), and a network failure. Code that read the list's first entry reads PostHog's result instead: its `ErrorCode` check becomes a check for PostHog's error, and its `MessageID` becomes PostHog's message id. A site that never read the entry went on after a refused message, and failed on every other error. Keep both: catch PostHog's error, log it and go on when its name is `validation_error`, which covers `recipient_suppressed`, and raise or return every other error the way the batch call did, as "Errors" says.

**The answer.** The message id of a moved send is PostHog's. Code that logged the answer's `MessageID`, under the name its client gives it, such as `message_id` in `postmark-python`, or stored it for the app's own use, takes PostHog's message id instead.

**The Postmark client.** Postmark's packages serve Postmark only, but each one also calls Postmark's other APIs, such as templates, suppressions, bounces, and the account API (`sdk-reference.md` lists them under "Other APIs"), and `postmark-rails` needs the `postmark` gem. Keep the package for any such call or mailer. Keep the Postmark client, its import, and its token while any site or other call still uses them. When nothing uses them, remove the import and the client, and keep the package and its token: the person removes them after the cutover.
