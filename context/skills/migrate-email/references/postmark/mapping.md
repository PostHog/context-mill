# Postmark to PostHog mapping

This file decides, field by field, whether PostHog can send a Postmark call site. A site moves only when every field it sets moves. Otherwise it stays on Postmark, and the reason names the first field or feature that keeps it there. `api.md` has the PostHog side in full, and the rewrite file for the site's language, which Step 7 names, has PostHog's names in that language.

Postmark fields are written in their HTTP names here, such as `HtmlBody`. Python and Ruby code uses snake case, such as `html_body`, and `postmark-python` names `From` as `sender`. PostHog fields are written in their Node.js names, such as `replyTo`. Use the name the rewrite file gives for the site's language, such as `reply_to` in Python.

## Fields

| Postmark | PostHog | A site stays on Postmark when |
|---|---|---|
| `From` | `from` | Never. `Name <address>` moves as it is. It needs a verified sender (Step 4) |
| `To` | `to` | It holds more than one address: a comma in the string, a list with more than one entry in Ruby, PHP, or `postmarker`, or a value the code builds at run time that you cannot tell holds one address. A list with one entry moves as that entry. `Name <address>` moves as the bare address: note in the plan row that the To line loses the name |
| `Subject` | `subject` | A send that is not a template send leaves it out, or sets a value that can be empty: Postmark sends an email without a subject, and PostHog's send requires one. A template send takes its subject from the template, as "Templates" says |
| `HtmlBody`, `TextBody` | `html`, `text` | Never |
| `TemplateId` or `TemplateAlias`, with `TemplateModel` | the template's email, with its layout, brought into the code and rendered with `TemplateModel`, sent as `subject`, `html`, and `text`. A template made in PostHog, by its `templateId` with `templateData`, only when the person asks for one | See "Templates" |
| `InlineCss` | none | Never on its own. It shapes how Postmark rendered the template's CSS: the email brought into the code carries that CSS, as "Templates" says |
| `Cc`, `Bcc` | none | Always. PostHog's send doesn't take it yet |
| `ReplyTo` | `replyTo`, one address or a list | An entry carries a name, there are more than 10, or the code builds the value at run time and you cannot tell that it holds bare addresses only. A site that leaves it out follows "Reply-to of the sender signature" below |
| `Attachments` | none | Always. PostHog's send doesn't take it yet |
| `Headers` | none | Always: no PostHog SDK takes headers yet |
| `Metadata` | none | Always: no PostHog SDK takes tags yet |
| `Tag` | none | Always: no PostHog SDK takes tags yet |
| Open and link tracking: `TrackOpens`, `TrackLinks`, or neither | none: PostHog adds its open pixel, and counts clicks only for a template made in PostHog that is not marked sensitive | Postmark sent it with opens untracked and the person doesn't agree to PostHog's open pixel, or nobody can tell whether it tracked them, as Step 3's "Opens the provider didn't track" says. See "Tracking" below |
| `MessageStream: 'outbound'` | none | Never. `outbound` is the default transactional stream |
| `MessageStream` naming any other stream | none | Always: the stream has its own settings, suppressions, and webhooks at Postmark |

Count only the fields the code sets.

**Tracking.** PostHog adds its open pixel to every email it sends, to count opens. A send in the code form is sensitive, so PostHog never rewrites its links and counts no clicks for it. A template made in PostHog that is not marked sensitive gets its links rewritten, as "Templates made in PostHog" says. No field changes this: `captureEngagement` decides only whether the email's events land on the recipient's person, so tracking never maps to it. Postmark tracks opens when the send's `TrackOpens` is `true`, or, when the send leaves it out or sets it to `null`, when its server's open tracking is on. It tracks links when the send's `TrackLinks` is anything but `None`, or, when the send leaves it out, when its server's link tracking is on. A new server tracks neither, until the person turns them on in its settings. `postmarker` sends `TrackLinks: "None"` when the code doesn't pass it, from `emails.send`, `emails.send_with_template`, and a message built with `client.emails.Email(...)` or `client.emails.EmailTemplate(...)`: links of those sends were not tracked. So does the .NET SDK: the constructor of `PostmarkMessage` and `TemplatedPostmarkMessage` sets `TrackLinks` to `LinkTrackingOptions.None`, so a .NET SDK message whose code never sets `TrackLinks` sends `None`, and its links were not tracked. That includes the positional `SendMessageAsync(from, to, subject, textBody, htmlBody)`, which builds a `PostmarkMessage` and never sets it. A .NET message that sets `TrackLinks = null` sends no value and follows the server, and so does a .NET send through a plain HTTP client that leaves the field out. Work out, for opens and for links, whether Postmark tracked them:

- Opens tracked: the site moves. When Postmark tracked its links too, and the site moves in the code form or to a template marked sensitive, note in the plan row that PostHog counts no clicks for it.
- Opens untracked: the site follows Step 3's "Opens the provider didn't track": it moves only when the person agrees to PostHog's open pixel, and otherwise stays with `open tracking off`.

Link tracking never adds a field, and keeps no site in the code form. A template site follows these bullets too, whether it moves into the code or to a template made in PostHog. A site that moves to a template made in PostHog also follows Step 3's rule on clicks Postmark didn't track, under "A template in PostHog".

Opens follow the server's setting whenever a site leaves out `TrackOpens` or sets it to `null`, in every SDK, `postmarker` and .NET included. In Go, `TrackOpens: false` follows it too: both Go packages leave a `false` out of the request, as they leave out an empty `TrackLinks`. The one exception is a PHP model send, `sendEmailModel` with a `PostmarkMessage` or `sendEmailWithTemplateModel` with a `TemplatedPostmarkMessage`: the model sets `TrackOpens` to `false` unless the code sets it to `true`, and sends that, so its opens were not tracked. Links follow it when a site leaves out `TrackLinks` or sets it to `null`, except in a `postmarker` send and a .NET SDK message that never sets it, whose links were not tracked. When either one follows the server, ask the person once for each server the moved sites send from whether its open tracking and link tracking are on, or read them as `account.md` says under "Tracking settings". When a site's opens follow the server and the answer for open tracking is not given, nobody can tell whether Postmark tracked them: the site stays, and the reason is `open tracking not checked`, as Step 3's "Opens the provider didn't track" says. An unanswered link tracking setting keeps no site in the code form. For a site that moves to a template made in PostHog, it means nobody knows whether Postmark tracked its clicks.

**Test token and sandbox servers.** Postmark's test token, `POSTMARK_API_TEST`, checks a send and delivers nothing, and so does every send through a server whose delivery type is Sandbox. Where an environment of the app sends with one, such as tests, CI, or staging, a moved site would deliver real email there. Find the token each environment reads, and ask the person which of the servers are sandbox servers, or read `DeliveryType` from `GET /server`, as `account.md` says under "Tracking settings". PostHog has no test token and no sandbox: the key of any project, one kept for tests too, delivers real email, and a client without a key fails every send. So ask the person, for each such environment, which of these holds:

- The app already replaces its email sending there, at a seam of its own, such as a mailer interface or a fake that its tests inject. The moved site sends nothing there either, and the site moves.
- The person accepts that the environment delivers real email once the site moves. Note their answer in the plan, and the site moves.
- Otherwise, the site stays, and the reason is `<environment> sends with Postmark's test token` or `<environment> sends through a sandbox server`.

For each environment where the person accepted real delivery, write a note under the plan's sites table that starts with `before cutover:` and names what the person does, such as `before cutover: staging delivers real email from PostHog once deployed; check that its recipients are addresses you accept mailing`. Step 9 reads only the plan, and its "Before cutover" list is everything the person still has to do, so the note carries the item there. An environment whose app replaces its sending needs no note.

**Reply-to of the sender signature.** A sender signature at Postmark can hold a Reply-To address, and Postmark sets it on every send from that signature's `From` address that leaves out `ReplyTo`. A site that sets `ReplyTo` keeps its own. For the sites that leave it out, ask the person once for each `From` address whether its sender signature has a Reply-To address, as `account.md` says under "Sender signatures". When it has one, the moved send sets `replyTo` to it, under the rules of the `ReplyTo` row above, and the plan row says that it came from the signature. When the `From` address has no sender signature of its own, Postmark set no reply-to address. When the answer is not given, the site stays, and the reason is `sender signature reply-to not checked`.

A Postmark send has no idempotency key, so the moved site sends none either. PostHog's SDK makes one for each call and reuses it on its own retries.

## Servers

Each Postmark server has its own tokens, templates, tracking settings, and suppression lists. A site sends from the server its token belongs to. When the app reads more than one Postmark token, ask the person once which server each one belongs to, and record each site's server under the sites table.

PostHog keeps one suppression list per project. When the sites that move send from more than one server, Step 5 imports the `outbound` list of each of them into that one list. PostHog then refuses a moved send to an address that any of those servers suppressed, even when the site's own server never suppressed it or reactivated it. Tell the person so, and ask once whether the moved sites may share one suppression list. When they say no, ask which one server's sites move. The sites of every other server stay, and the reason is `server <name> keeps its own suppression list`.

## Code around the send

Postmark's SDKs throw on an API error: Node.js, both Python SDKs, Ruby, PHP, and .NET. The Go community packages return an error. A raw HTTP call reads the status code or the `ErrorCode` in the answer. The rewrite file says under "The answer" how PostHog's SDK reports an error in its language. Keep the site failing the same way it did, as the Rewrite section says.

| Code | A site stays on Postmark when |
|---|---|
| A `catch`, `except`, or `rescue` that only logs or rethrows the error | Never |
| A branch on the HTTP status: `err.statusCode`, `e.http_status`, `e.status_code`, `getHttpStatusCode()` | Never. Read PostHog's status code, or PostHog's error name for a `422`, as the Rewrite section says |
| A branch on an inactive recipient: `InactiveRecipientsError`, `InactiveRecipientException`, `Postmark::InactiveRecipientError`, or `ErrorCode` `406` | Never. PostHog refuses a suppressed address with the code `recipient_suppressed` |
| A branch on another Postmark `ErrorCode`, or on the error's message text | Always. A catch of `InvalidEmailRequestError` or Python's `ValidationException` is not such a branch: the Rewrite section maps it |
| A read of the inactive addresses from the error (`recipients`, `inactive_recipients`) | Always |
| A check of `ErrorCode`, `Message`, or .NET's `Status` in a send's answer | Never. Read PostHog's error instead, as the Rewrite section says |
| `MessageID` stored for a webhook handler or a status read | Always, when a webhook handler or the Messages or Bounces API uses it |
| `MessageID` logged or stored for the app's own use | Never. Use PostHog's message id |
| A send the code can cancel: a raw request with a `signal` a caller passes in or an `AbortController` it aborts, a .NET request with a cancellation token a caller can cancel, or a Go context a caller can cancel, such as the one passed to `SendEmail(ctx, ...)` | Unless the PostHog send in that language takes the same cancellation, as Go's `Send(ctx, ...)` and .NET's `SendAsync(..., cancellationToken)` do: pass it there. Otherwise always: an email the old code cancelled would go out. A fixed deadline, such as `AbortSignal.timeout(...)`, moves as "HTTP" says under "Rewrite" |

## Templates

A template site moves by bringing the template into the code, as `template-to-code.md` says. The check needs the template's subject, HTML body, and text body, because the code has only its id or alias. `account.md` says how to get them. The code renders them with the site's `TemplateModel`, and the send sets the rendered `subject`, `html`, and `text`.

A template with a layout (its `LayoutTemplate` names one) renders inside that layout at `{{{ @content }}}`, so the layout and the template come into the code as one email: the layout's HTML with the template's HTML in place of `{{{ @content }}}`, and the same for the text body, all rendered with the same `TemplateModel`. The check needs the layout's content too. When several emails share a layout, write it once as a piece they share. When only one of the layout and the template has a text body, the docs don't say what Postmark sent as text, so the template stays on Postmark.

Postmark templates are Mustachio. In the code:

| Postmark | In the code |
|---|---|
| `{{name}}`, `{{ name }}` | The value, escaped. A missing or `null` value renders as nothing, and so does a list or an object. A number renders as its digits. A boolean renders as `True` or `False`, as Mustachio's source does: the docs don't say, so note it in the plan row |
| `{{person.first_name}}` | The nested value, escaped. A missing step of the path renders as nothing |
| `{{{name}}}`, `{{& name}}` | The value as it is, unescaped, under the rule of `template-to-code.md`. In the subject and the text, it is the plain value |
| `{{#paid}}…{{/paid}}`, on a value that is never a list | The part, rendered once when the value passes Mustachio's truth test below. Inside it, names are read from that value: `{{#person}}{{first_name}}{{/person}}` reads `person.first_name`, and `{{.}}` is the value itself |
| `{{^paid}}…{{/paid}}` | The part, rendered when the value fails the truth test |
| `{{name}}{{^name}}there{{/name}}`, Mustachio's only fallback | Two parts, each by its row above: the value, then `there` when the value fails the truth test. Write them apart, never as "the value or `there`": `false` renders as `Falsethere`, and `""` as `there` |
| `{{#each items}}…{{/each}}` | A loop over the list, in order. Nothing when the list is missing, `null`, or empty |
| Inside `{{#each items}}`: `{{.}}`, `{{name}}`, `{{#each .}}` | The current item, its field, or a loop over the item when it is a list itself. Mustachio has no index, first, or last |
| `{{../name}}`, `{{../../name}}` | The value one level out for each `../`. Out of a section, one level is the scope the section is in. Each step of a dotted name is a level too: inside `{{#person.address}}`, one `../` reads `person`, and `../../` the scope the section is in. Out of an `each` item, one level is the list, so `../../name` reads the scope the list is in. A `../` past the top stays at the top, in Mustachio's source |
| `{{! note }}` | Nothing |
| The layout's `{{{ @content }}}` | The template's HTML, or its text, in its place |
| The template's `Subject` | The send's `subject`, rendered with the same conversions and no escaping. A layout has no subject. A subject that can render empty keeps the template on Postmark, as the Fields table says |
| The template's `TextBody`, inside the layout's | The send's `text`, with no escaping. Mustachio keeps every line break around its tags, so keep the lines as they are. A template without a text body sends `html` only |

- Mustachio's truth test: a missing value, `null`, `false`, `""`, and an empty list fail it. Every other string, including `"0"` and `"false"`, `true`, a number other than `0`, and an object with keys pass it. Write that test out in the code, as `template-to-code.md` says. The docs don't say what `0` or an empty object does: a section or an inverted section whose value can be either keeps the template on Postmark, because which part Postmark sent can't be told.
- Inside a section or an `each`, a bare name reads only the section's value or the current item. Postmark's docs reach an outer value with `../` only, and don't say whether a bare name looks outside: a bare name that the value or the item doesn't always carry keeps the template on Postmark. So does a bare name inside an inverted section, which has no value to read it from: only `../` reads there.
- A section `{{#items}}` on a value that can be a list, an `{{#each}}` on a value that can be an object or a scalar, a path into a list by position, such as `{{items.0.name}}`, a partial (`{{> name}}`), and any other tag keep the template on Postmark. The docs show a list only with `each`, and Mustachio's source renders such a section once with the whole list as its value and fails such an `each`.
- `{{{ pm:unsubscribe }}}`, also inside a link as `href="{{{ pm:unsubscribe }}}"`, keeps the template on Postmark: Postmark fills it from its account with the stream's unsubscribe link.
- With `InlineCss` on, its default, write each `<style>` rule into the `style` attribute of the tags it matches, as Postmark did when it sent the email, and keep the `<style>` block for the rules a tag can't hold, such as `@media`. Do it once, while you write the email: the code adds no inliner. Postmark's docs don't say whether it kept the `<style>` block, so note in the plan row that the CSS was inlined in the code, for the person to compare a test send. Postmark inlined after it rendered the values, so a rule whose match can depend on a value, such as `.badge-paid` against `class="badge-{{status}}"`, keeps the template on Postmark. A site that sends `InlineCss: false`, or `false` for PHP's `$inlineCss`, keeps the HTML as it is. A PHP `TemplatedPostmarkMessage` built with `'InlineCss' => false` still sends `true`, because its constructor treats `false` as unset: only `setInlineCss(false)` turns it off.
- Postmark hosts no images for templates: its editor has no upload, and its docs name no image host. A template's images are on the person's own hosts, so none needs listing.
- A Postmark template holds no sender or reply-to address, and a template send always sets `From`. The send takes the site's own `From`, and its own `ReplyTo` or its sender signature's, as "Fields" says. Its subject comes only from the template: the template routes take no `Subject`.
- A template site follows "Tracking" like any other site, and Step 3's "Opens the provider didn't track" for opens Postmark didn't track.
- No single send fills Postmark's template language into its own content: `POST /email` and the batch route send `Subject`, `HtmlBody`, and `TextBody` as they are, so a `{{name}}` in them was mailed as written, and nothing about it changes. Only the Bulk API fills its own content with each message's `TemplateModel`, and a bulk call stays, as "Calls" says.

### Templates made in PostHog

Only for a template the person asks to make in PostHog, as Step 3 says. This skill never makes one: the person makes it from the Postmark template and gives you its template ID, and makes it transactional once a verified sender covers its address, as Step 3 says. Until they give the ID, the site stays on Postmark.

An email that carries a login code, a reset link, or another secret needs its PostHog template marked sensitive: PostHog then keeps no copy of each sent email's body or filled-in subject, and sends its links as they are, without its click redirect. Templates are not sensitive by default. When Postmark didn't track the site's links, or nobody knows whether it did, as `account.md` says under "Click tracking", ask the person to mark the template sensitive too, as Step 3 says under "A template in PostHog".

For a template with a layout, the person makes one PostHog template from both: the layout's HTML with the template's HTML in place of `{{{ @content }}}`, and the same for the text body. Tell them so when you ask them to make it.

Postmark's Mustachio becomes Liquid in the PostHog template. Values move under `variables`, and each name keeps its case:

| Postmark | PostHog |
|---|---|
| `{{name}}`, `{{ name }}` | `{{ variables.name }}` |
| `{{person.first_name}}` | `{{ variables.person.first_name }}` |
| `{{#paid}}…{{/paid}}`, when `paid` is always a boolean, `null`, or missing | `{% if variables.paid %}…{% endif %}` |
| `{{^paid}}…{{/paid}}`, when `paid` is always a boolean, `null`, or missing | `{% unless variables.paid %}…{% endunless %}` |
| `{{#person}}{{first_name}}{{/person}}`, when `person` is always an object with keys, `null`, or missing | `{% if variables.person %}{{ variables.person.first_name }}{% endif %}` |
| `{{#each items}}{{name}}{{/each}}`, when `items` is always a list | `{% for item in variables.items %}{{ item.name }}{% endfor %}` |
| `{{.}}` inside `{{#each items}}` | `{{ item }}` |
| `{{../company}}` inside a top-level `{{#person}}` section whose name has no dot, or `{{../../company}}` inside a top-level `{{#each items}}`, where `company` is a top-level key of `TemplateModel` | `{{ variables.company }}` |
| The template's `Subject` | The PostHog template's subject, with the same conversions |

- Mustachio escapes HTML in values, and so does PostHog's Liquid, so plain values render the same.
- Mustachio prints a boolean as `True` or `False`, and Liquid as `true` or `false`. Mustachio prints nothing for a list or an object, and Liquid prints its contents. A `{{name}}` whose value can be a boolean, a list, or an object keeps the template on Postmark.
- Mustachio skips a section whose value is false, empty, or missing, and Liquid treats `0`, an empty string, and an empty list as true. Read what the site sends for each section value. A value that is not always a boolean, `null`, or missing, such as a number, a string, or a list, keeps the template on Postmark. So does an object that can be empty.
- Liquid's `for` walks only a list. An `each` over a value that is not always a list, such as an object, keeps the template on Postmark.
- Inside `{{#each items}}`, a bare `{{name}}` reads the current item. It becomes `{{ item.name }}`, never `{{ variables.name }}`. A name that the item doesn't always carry keeps the template on Postmark, because Liquid won't look for it outside the loop.
- `{{{name}}}` and `{{& name}}` insert HTML as it is. PostHog's Liquid escapes it, so a template that uses them stays on Postmark. The layout's own `{{{ @content }}}` is the one exception: the person replaces it with the template.
- `{{{ pm:unsubscribe }}}` keeps the template on Postmark: it is Postmark's unsubscribe link.
- An inverted section `{{^items}}` on a list or an object, a section `{{#items}}` on a list without `each`, a name inside `{{#person}}` that the site doesn't put on `person`, and `../` that reads anything but a top-level key all keep the template on Postmark. Inside `{{#each}}`, one `../` reaches the list, not the model: Postmark needs `../../` for a top-level key there.
- The PostHog template carries its own sender, reply-to address, and subject. A Postmark template send always sets `From`: the site moves only when `From` is the same in every send, and the person makes the PostHog template send from it. The same holds for the reply-to address the send had, its own `ReplyTo` or its sender signature's. Otherwise it stays.
- A template site follows "Tracking" like any other site: opens Postmark didn't track, by the site's own field, PHP's model default, or its server's setting, and an open tracking setting nobody checked follow Step 3's "Opens the provider didn't track". It also follows Step 3's rule on clicks Postmark didn't track. When it moves, the tracking fields are dropped, and so is `MessageStream: 'outbound'`. `Cc`, `Bcc`, `Attachments`, `Headers`, `Metadata`, `Tag`, and a `MessageStream` other than `outbound` keep any site, as the Fields table says.
- With `InlineCss` on, its default, Postmark moved the template's `<style>` rules into each tag. Tell the person to check how the PostHog template looks in its test send.

## Webhooks

Postmark stops sending events for a site that moves. PostHog records the events of a moved send on the person it names with `distinctId`, when engagement capture is on:

| Postmark `RecordType` | PostHog event |
|---|---|
| `Delivery` | `$workflows_email_delivered` |
| `Bounce` | `$workflows_email_bounced` |
| `SpamComplaint` | `$workflows_email_blocked` |
| `Open` | `$workflows_email_opened` |
| `Click` | `$workflows_email_link_clicked`, only for a template made in PostHog that is not marked sensitive. PostHog treats a send in the code form as sensitive: its links go out as they are, and it counts no clicks |
| `SubscriptionChange` | none |

Postmark has no event for an accepted send. PostHog records `$workflows_email_sent` for each moved send. A send to an inactive address got a `406` error from Postmark, and Postmark posted no webhook for it. PostHog refuses it with `recipient_suppressed`.

PostHog's events carry no Postmark `MessageID`, no `Metadata`, and no `Tag`. A site whose events a handler matches by message id, by a metadata value, or by tag stays on Postmark. For every other handler, such as one that matches by the recipient's address, the report tells the person which events it handles, which PostHog events take their place, and that a webhook destination in PostHog (Data pipelines, then Destinations) can post them to an endpoint. The handler itself keeps working for the sites that stay. Never change it.

A site whose emails a `SubscriptionChange` handler acts on stays, since PostHog has no event for it, and the reason is `its SubscriptionChange events feed a webhook handler`. A site whose emails a `Click` handler acts on moves only to a template made in PostHog that is not marked sensitive, since a send in the code form counts no clicks. Otherwise it stays, and the reason is `its clicks feed a webhook handler`.

## Calls that change the suppression list

Step 5 says what to do with each of these calls. They are not sends, and they stay on Postmark.

| Adds an address | Removes an address |
|---|---|
| `POST /message-streams/{stream}/suppressions`, and each SDK's spelling of it, such as `createSuppressions` in Node.js and PHP, `create_suppressions` in Ruby, or `CreateSuppressions` in .NET | `POST /message-streams/{stream}/suppressions/delete`, and each SDK's spelling of it, such as `deleteSuppressions` in Node.js and PHP, `delete_suppressions` in Ruby, or `DeleteSuppressions` in .NET. `PUT /bounces/{bounceid}/activate` too, which reactivates a hard bounce and takes its address off the list: `activateBounce` in Node.js and PHP, `activate_bounce` in Ruby, or `ActivateBounceAsync` in .NET |

Only a call on the `outbound` stream of a server whose list Step 5 imports counts, as "Servers" says. A bounce activation counts when the bounce's `MessageStream` is `outbound`. PHP and .NET use `outbound` when the call names no stream. A call on any other stream changes a list the import leaves out.

## Rewrite

How a site that moves is written with PostHog's SDK. Step 7 says when to use each part, and the rewrite file for the site's language has the client and the send.

**The PostHog client.** Set `migratedFrom: 'postmark'` on the client that Step 7 configures, when its client options take it.

- Python: `postmark-python` is async. A site that awaits `client.outbound.send` moves to `AsyncPosthog` and `await posthog.emails.send(...)`, with `posthog[async]` installed, as the rewrite file says. A site on `postmark.sync.ServerClient` or `postmarker` moves to `Posthog`.

**The call.** The Postmark send becomes one PostHog send. Build its fields from the message the site built:

- Node.js `client.sendEmail({ ... })`, or a `new postmark.Message(...)`: the fields of the message.
- Python `client.outbound.send({ ... })` (keys `sender`, `to`, `html_body`, or the HTTP names), and `postmarker` `client.emails.send(From=, To=, ...)`: the same fields.
- Ruby `client.deliver(from:, to:, subject:, html_body:, text_body:, ...)`: the same fields.
- PHP `sendEmail($from, $to, $subject, $htmlBody, $textBody, $tag, $trackOpens, $replyTo, $cc, $bcc, $headers, $attachments, $trackLinks, $metadata, $messageStream)`: read each argument by its position or its name. A `null` argument sets nothing.
- .NET `new PostmarkMessage { ... }`: the same fields. The positional forms `new PostmarkMessage(from, to, subject, textBody, htmlBody, headers, metadata, messageStream)` and `SendMessageAsync(from, to, subject, textBody, htmlBody, headers, metadata, messageStream)` take the text body before the HTML body, unlike PHP. Read each argument by its position, and a `null` or left-out argument sets nothing. The `SendMessage` with the same arguments is synchronous: the rewrite file says what a synchronous .NET site does.
- Go `postmark.Email{ ... }`: the same fields.
- A raw HTTP body: its fields.
- A batch of one message: the fields of that message, sent with PostHog's send for one email.
- A template send, such as `sendEmailWithTemplate`, `send_with_template`, `deliver_with_template`, .NET `TemplatedPostmarkMessage`, or `POST /email/withTemplate`: its `From`, `To`, `ReplyTo`, and tracking fields, as for any message, and the rendered email, as "Templates brought into the code" says. PHP `sendEmailWithTemplate($from, $to, $templateIdOrAlias, $templateModel, $inlineCss, ...)` takes the rest from `$tag` on in `sendEmail`'s order.

**The fields.**

- `From` moves as it is, with its name.
- `To` becomes one bare address. When a helper takes a list or a comma-separated string of recipients and every caller passes one address, change the parameter to one address and update the callers. Never send one email per address in a loop.
- A `ReplyTo` with several addresses becomes a list of bare addresses: split a comma-separated string.
- A site without `ReplyTo` whose sender signature has a Reply-To address gets it as `replyTo`, as "Fields" says.
- `HtmlBody` becomes `html`, and `TextBody` becomes `text`.
- A `postmarker` client built with `inline_css` moved the CSS of each `<style>` block into the `style` attributes of the tags before it sent `HtmlBody`, in every send of it that carries `HtmlBody`, such as `emails.send`, a message built with `client.emails.Email(...)`, and a batch of one message, as `postmarker`'s docs say under "CSS inlining". The moved send does the same, with the `css-inline` package that option needs: `html=css_inline.CSSInliner(load_remote_stylesheets=False).inline(html_body)` for `inline_css=True`, or `inliner.inline(html_body)` with the `CSSInliner` the code passed as `inline_css`. Never leave out `load_remote_stylesheets=False`: `postmarker`'s docs say its inliner loads no stylesheet from a `<link>` tag, and an inliner that loads them fetches every `<link>` URL in the email's HTML from the app's server. Read the installed `postmarker` for any other option its own inliner sets, pass the same, and name the file you read in the plan row. When the app gets `css-inline` only through `postmarker`'s `css-inline` extra, add `css-inline` as its own dependency, at the version installed now, and note it as a new dependency under the sites table, so it stays when the person removes `postmarker` after the cutover. A template send is not inlined by the client: Postmark inlined it, as "Templates" says.
- `MessageStream: 'outbound'` is dropped, as the Fields table says.
- `TrackOpens` and `TrackLinks` are dropped, and the send gets no `captureEngagement` for them, as "Tracking" says.
- A send with rendered content gets a `templateKey`, as Step 7 says.

**HTTP.** A request to `https://api.postmarkapp.com/email` or `/email/withTemplate`, through `fetch`, axios, `requests`, `httpx`, `net/http`, Faraday, Guzzle, `HttpClient`, `reqwest`, `Req`, or `curl`, becomes the SDK's send in that language, as "The call" says. A site's own deadline is a timeout that the code sets on that request, or on the Postmark client the site sends through. The site keeps it, as Step 7 says under "Set up the client". These set one:

- A raw request: `signal: AbortSignal.timeout(...)` on `fetch`, `timeout=` in `requests` or `httpx`, Guzzle's `timeout`, `HttpClient.Timeout` in .NET, an `http.Client` with a `Timeout` or a context with a deadline in Go, Faraday's `timeout` on its default `net_http` adapter, and `CURLOPT_TIMEOUT` or `--max-time` in curl. An axios `timeout` in Node.js, and a Ruby limit on the whole request, such as Faraday's `timeout` on another adapter, are limits the SDK can't keep, as Step 7 and `rewrite-ruby.md` say.
- postmark.js: the client option `timeout`, in seconds, such as `new postmark.ServerClient(token, { timeout: 10 })`. From version 5, postmark.js ends the whole request at it. Before version 5, it passed it to axios as axios's `timeout`, a limit the SDK can't keep, as Step 7 says.
- `postmark-python`: `ServerClient(token, timeout=...)`, and `postmarker`: `PostmarkClient(server_token=..., timeout=...)`, in seconds. A `postmarker` `timeout` given as a pair limits connecting and reading apart, which Step 7 keeps the site for.
- Ruby: `http_open_timeout:` and `http_read_timeout:` on `Postmark::ApiClient.new`, in seconds, 60 each by default. The gem never sets `Net::HTTP`'s write timeout, which stays at its 60 seconds. So when every one of the two that the code sets is 60, such as only `http_read_timeout: 60`, open, read and write all stay at 60, and 60 is the deadline. Any other value in either is a mix the SDK can't keep, and the site stays, as `rewrite-ruby.md` says under "A deadline".
- PHP: the second argument of `new PostmarkClient($token, $timeout)`, in seconds.
- .NET: a `PostmarkClientBase.ClientFactory` the code sets, whose client sends through an `HttpClient` with a `Timeout`.
- Go: a context with a deadline passed to `SendEmail(ctx, ...)`, or a `Timeout` on the client's `HTTPClient`.

A timeout the SDK sets by default is not the site's own, as Step 7 says, such as postmark.js's 180 seconds, `postmark-python`'s 5, or the 60 seconds of Ruby, PHP, and .NET. Step 7 turns the send's retries off because the request never retried. A Postmark client that retried keeps that count instead: `postmark-python`'s `retries`, 3 unless the code sets it, the `max_retries` the code sets on `postmarker`'s `PostmarkClient`, and one less than the `max_retries` the code sets on `Postmark::ApiClient.new`, which counts every try, the first one included. The send's retries take that count, under the rewrite file's name for them under "A deadline".

PostHog's SDK retries a network error, a rate limit, and a server error only when it is a 503. `postmark-python`, unless the code sets `retries=0`, also retried a 500, and the Ruby gem, when the code sets `max_retries` above 1, every status from 500 up. Such a server error now fails at the first try. The site still moves. For each moved site whose Postmark client retried, write a note under the plan's sites table, `before cutover: <file>:<line> no longer retries a server error other than 503; check that its error path handles one`, which Step 9 carries into "Before cutover" as the test environments above say.

**Templates brought into the code.** The site renders the email, inside its layout, from `TemplateModel`, as "Templates" says, and sends `templateKey`, the rendered `subject`, `html`, and `text`, and the site's own `from` and `replyTo`. It sends no `templateId` and no `templateData`, and drops `TemplateId`, `TemplateAlias`, `TemplateModel`, and `InlineCss`.

**Templates made in PostHog.** The site sends `templateId` with the template ID the person gave, and `templateData` with the site's `TemplateModel`. It sends no `templateKey`, `subject`, `html`, `text`, `from`, or `replyTo`: the template holds them.

**Errors.** Postmark refused a send to an inactive address with error code `406`, and the site's error path ran. PostHog refuses it with `recipient_suppressed`, so the same path runs: the site needs no new branch. Keep the site failing the same way it did:

Never widen a catch. Where the code caught only one kind of Postmark error, catch PostHog's error, check its `code` or status code for that kind, and raise or return every other error as before. The kinds map like this: `ApiInputError`, `ValidationException`, `InvalidEmailRequestError`, and a status of `422` are PostHog's error name `validation_error`, never a status, because PostHog's statuses for an invalid send differ from Postmark's. `recipient_suppressed` is a `validation_error` too, with status `422`: where the site treats an inactive recipient apart, handle it first. `ApiInputError` and a status of `422` also covered inactive recipients, so their branch covers `recipient_suppressed` as well. `InvalidEmailRequestError` and Python's `ValidationException` never did: their branch is `validation_error` with any code but `recipient_suppressed`, and it raises `recipient_suppressed` again first. `InvalidEmailRequestError`, in Node.js and Ruby, was Postmark's code `300` only, and a sender Postmark refused was a plain `ApiInputError`: its branch also raises `sender_not_verified` again first. `InvalidAPIKeyError` and `InvalidAPIKeyException` are status 401. `RateLimitExceededError` and `RateLimitException` are status 429 with any code but `quota_limited`: PostHog answers a used-up sending quota with 429 and `quota_limited`, which no retry fixes, so it takes the path of every other error, as Step 7 says. `InternalServerError`, in Node.js and Ruby, is status 500 only, Node.js's `ServiceUnavailablerError` is 503, and Python's `ServerException` is 500 or 503. An inactive recipient is the code `recipient_suppressed`. A network error that is left after PostHog's retries has the code `network_error`. A catch of Postmark's API errors only, such as Python's `PostmarkAPIException` or `postmarker`'s `ClientError`, Ruby's `Postmark::HttpServerError`, or PHP's `PostmarkException`, let network errors and timeouts go past it: raise the error again when its code is `network_error`. An answer that holds no PostHog error code, such as a proxy's HTML page for a 502, has the code `api_error` in PostHog's SDK. Postmark's docs don't say whether a catch of its API errors took an answer whose body its client couldn't parse as Postmark's JSON. So read the Postmark client installed in the person's app, such as in `node_modules`, the virtualenv, `vendor`, or the gem bundle, for what it raises when it can't parse an answer's body, and name the file you read in the plan row. The .NET package holds compiled code: read the client's source at the installed version instead, from the repository its package names. When that error went past the site's catch, the catch raises `api_error` again too. A catch of a Postmark class that the client raises only for such an answer becomes a catch of PostHog's error with the code `api_error`, which also takes an answer without a code. A class that a language bullet below names keeps that bullet's rule. When the client doesn't settle it, the site stays, and the reason is `Postmark's handling of an answer it couldn't parse not checked`. A catch of one kind of network failure keeps the site, as Step 7 says; the language bullets name Postmark's classes that do that.

- **Node.js.** `posthog.emails.send` never throws on an API error: it answers `{ data, error }`. Where `sendEmail` threw into a `catch`, or up to the caller, throw from the error so the same code runs: `if (error) throw Object.assign(new Error(error.message), { statusCode: error.statusCode, code: error.code, name: error.name })`. `err.statusCode` keeps holding the HTTP status, and `err.name` holds PostHog's error name. `err.code` now holds PostHog's code, a string: a branch on `err.code === 406` or on `instanceof InactiveRecipientsError` becomes `err.code === 'recipient_suppressed'`, a branch on `instanceof ApiInputError`, or on `err.statusCode === 422`, becomes `err.name === 'validation_error'`, a branch on `instanceof InvalidEmailRequestError` becomes `err.name === 'validation_error' && err.code !== 'recipient_suppressed' && err.code !== 'sender_not_verified'`, a branch on `instanceof RateLimitExceededError` becomes `err.statusCode === 429 && err.code !== 'quota_limited'`, and a branch on `instanceof` another Postmark error class becomes a check of `err.statusCode` as mapped above. A site that passes a callback, such as `client.sendEmail(message, callback)` or `sendEmailWithTemplate(message, callback)`, got `callback(null, response)` on success and `callback(error, null)` on an error. Call it the same way from PostHog's answer: `posthog.emails.send({ ... }).then(({ data, error }) => error ? callback(Object.assign(new Error(error.message), { statusCode: error.statusCode, code: error.code, name: error.name }), null) : callback(null, data))`, with the branches inside the callback mapped as above, and its read of `MessageID` becoming `id`. Postmark also returned its promise, which resolved with the answer and rejected on an error. Where the code awaits or chains it too, build the error once, call the callback, and then throw that error or return `data`, so the awaited value and the `catch` stay as they were.
- **Python.** PostHog's SDK raises too. `except PostmarkException` becomes `except EmailError`, with the PostHog exception the rewrite file names. `except PostmarkAPIException` and `postmarker`'s `except ClientError` become `except EmailError` that raises again first when the code is `network_error`, and when it is `api_error` too if the installed client let an answer it couldn't parse go past the catch, as "Errors" says. `e.http_status` becomes its status code, and `e.error_code == 406` becomes a check of its code for `recipient_suppressed`. A catch of one subclass becomes `except EmailError as e:` that checks for the same kind and raises every other error again: `InactiveRecipientException` checks `e.code == 'recipient_suppressed'`, `e.http_status == 422` checks `e.name == 'validation_error'`, `ValidationException` checks `e.name == 'validation_error' and e.code != 'recipient_suppressed'`, `RateLimitException` checks `e.status_code == 429 and e.code != 'quota_limited'`, and `ServerException` checks `e.status_code in (500, 503)`. `PostmarkException` also covered the SDK's own check of the message (`InvalidEmailException`): where the old code handled a bad value, also catch `TypeError` and `ValueError`, as Step 7 says. `except TimeoutException` told a timeout from other network failures: the site stays, as Step 7 says (`catches one kind of network failure`).
- **Ruby.** `rescue Postmark::Error` caught a timeout (`Postmark::TimeoutError`) and a malformed answer (`Net::HTTPBadResponse` or `Net::HTTPHeaderSyntaxError`, which the gem raises as `Postmark::HttpClientError`), but a connection failure, such as `SocketError` or `Errno::ECONNREFUSED`, went past it, because the gem raises it as it is. So it told one kind of network failure from another, and so does a rescue of `Postmark::TimeoutError` or `Postmark::HttpClientError`: the site stays, as Step 7 says (`catches one kind of network failure`). `rescue Postmark::HttpServerError` becomes `rescue PostHog::EmailError => e` with `raise if e.code == 'network_error'` first, and `raise if e.code == 'api_error'` too if the installed gem let an answer it couldn't parse go past the rescue, as "Errors" says. A rescue of one class, such as `Postmark::ApiInputError` or `Postmark::InactiveRecipientError`, becomes `rescue PostHog::EmailError => e` with `raise unless` the check of that kind first: `raise unless e.name == 'validation_error'` for `ApiInputError`, `raise if ['recipient_suppressed', 'sender_not_verified'].include?(e.code)` and then `raise unless e.name == 'validation_error'` for `Postmark::InvalidEmailRequestError`, and `raise unless e.code == 'recipient_suppressed'` for `InactiveRecipientError`. `e.status_code` keeps its name, except that a check of it for `422` becomes `e.name == 'validation_error'`, and `e.error_code` becomes `e.code`.
- **PHP.** `catch (PostmarkException $e)` caught API errors only: Guzzle's network errors went past it. It becomes `catch (\PostHog\EmailError $e)` with `if ($e->getErrorCode() === 'network_error') throw $e;` first, and the same for `'api_error'` if the installed client let an answer it couldn't parse go past the catch, as "Errors" says. `getHttpStatusCode()` becomes `getStatusCode()`, a check of it for `422` becomes `getErrorName() === 'validation_error'`, and a check of `getPostmarkApiErrorCode()` for `406` becomes `getErrorCode() === 'recipient_suppressed'`.
- **.NET.** `catch (PostmarkValidationException ex)` caught API errors only: network errors went past it, such as an `HttpRequestException`. It becomes `catch (PostHog.Emails.EmailException ex) when (ex.Code != "network_error")`, with `&& ex.Code != "api_error"` too if the installed client let an answer it couldn't parse go past the catch, as "Errors" says. `ex.Response.Message` becomes `ex.Message`, a branch on the `422` answer becomes `ex.Name == "validation_error"`, and a check of `ex.Response.ErrorCode` for `406` becomes `ex.Code == "recipient_suppressed"`.
- **Go.** Both return an error. Keep `if err != nil`, and read PostHog's `*posthog.EmailError` with `errors.As` where the code read Postmark's. A branch on one `ErrorCode` becomes a check of the error's `Code` or `StatusCode`, a branch on a `422` reads its `Name` for `validation_error`, and every other error goes on as before.
- **A raw HTTP call.** The code read the status or `ErrorCode` of the answer. Read PostHog's error the way the rewrite file says under "The answer", and keep each branch: a status of 400 or more, or an `ErrorCode` other than 0, becomes "there is an error", a branch on `422` reads PostHog's error name `validation_error`, and a branch on another status reads PostHog's status code, with a `429` branch that skips the code `quota_limited`.

**Checks of the answer.** A single send threw on any answer but `200` before the code read it: .NET's `SendMessageAsync` throws `PostmarkValidationException`, and PHP's `sendEmail` throws `PostmarkException`. A check after the call, such as `response.Status != PostmarkStatus.Success` or `getErrorCode() != 0`, only ever saw a sent email. Remove the check, keep the code it guarded on success, and let PostHog's error take the path Postmark's exception took, as the bullets above say.

**A batch of one.** The batch route answers `200` even when it refuses the message, and puts the refusal in the message's `ErrorCode` in the answer's list: a refusal of that message, such as `300` (an invalid email request) or `406` (an inactive recipient). A failure of the whole request threw, or returned an error in Go, as a single send does: a bad token (`401`), a rate limit left after the retries (`429`), a request Postmark could not read, such as invalid JSON (`422` with code `402`), a server error (`500` or more), and a network failure. Code that read the list's first entry reads PostHog's result instead: its `ErrorCode` check becomes a check for PostHog's error, and its `MessageID` becomes PostHog's message id. A site that never read the entry went on after a refused message, and failed on every other error. Keep both: catch PostHog's error, log it and go on when its name is `validation_error`, which covers `recipient_suppressed`, and raise or return every other error the way the batch call did, as "Errors" says.

**The answer.** The message id of a moved send is PostHog's. Code that logged `MessageID` (`message_id`, `getMessageID()`), or stored it for the app's own use, takes PostHog's message id instead.

**The Postmark client.** Postmark's packages serve Postmark only, but each one also calls Postmark's other APIs, such as templates, suppressions, bounces, and the account API (`sdk-reference.md` lists them under "Other APIs"), and `postmark-rails` needs the `postmark` gem. Keep the package for any such call or mailer. Keep the Postmark client, its import, and its token while any site or other call still uses them. When nothing uses them, remove the import and the client, and keep the package and its token: the person removes them after the cutover.
