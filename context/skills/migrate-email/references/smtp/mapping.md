# SMTP to PostHog mapping

This file decides, field by field, whether PostHog can send an SMTP call site. A site moves only when every field it sets moves. Otherwise it stays on SMTP, and the reason names the first field or feature that keeps it there. `api.md` has the PostHog side in full, and the rewrite file for the site's language, which Step 7 names, has PostHog's names in that language.

Fields are written in their Nodemailer names here, such as `replyTo`. A site in another language sets the same part of the message under another name: `msg["Reply-To"]` in Python, `addReplyTo` in PHPMailer, `message.ReplyTo` in MailKit. `sdk-reference.md` lists the part each field sets. PostHog fields are written in their Node.js names: use the name the rewrite file gives for the site's language, such as `reply_to` in Python.

Fields set in the transporter's `defaults`, the second argument of `createTransport`, are fields of every site that sends through that transporter. So are the settings of a `Mail.defaults` block or a shared client object.

| PHPMailer `action_function` | none | Always. `send()` calls it with each recipient's result, such as to mark a queued message sent, and the moved send would skip it |

When you can't read the condition, the site stays |

A send through SMTP has no idempotency key, so the moved site sends none either.

**Tracking.** Every moved site sends in the code form, so PostHog counts its opens and no clicks, as Step 7 says, and no field changes that. An SMTP server tracks neither opens nor clicks on its own, but the provider behind the host may, by an account, domain or server setting, as `account.md` says under "Open tracking". Whether a site's emails had an open pixel decides the rest, as Step 3 says under "Opens the provider didn't track":

- No open pixel: a host with no tracking provider behind it, such as the company's own mail server, and a provider behind the host whose open tracking was off or never set up, such as Amazon SES with neither a configuration set that records opens nor the account's engagement tracking, which the set the sends use can turn off, as `account.md` says. Step 3 asks the person whether PostHog may add its pixel, and the reason when it may not is `open tracking off`.
- Nobody knows whether the host tracked opens: the reason is `open tracking not checked`.
- Opens tracked: the site moves. When the host tracked its clicks too, note in the plan row that PostHog counts no clicks for it.

## Attachments

An SMTP client adds a file in its own way, and some fill in its parts from a path. Each file of a site that moves becomes one entry of PostHog's `attachments`, under the PostHog SDK's names, as its rewrite file gives them: its filename, its content, its content type, and its content ID. Step 3 says under "Files" when a site with files stays in any case. This section maps each part, and names the options that keep a site on SMTP.

**Filename.** A name the code sets moves as it is: Nodemailer's `filename`, the `filename` of a Python `Content-Disposition`, the key of Ruby `mail`'s `attachments['report.pdf']` or `add_file`'s `filename:`, PHPMailer's `$name`, Symfony's `$name`, gomail's `Rename`, go-mail's `WithFileName`, MailKit's `FileName`, System.Net.Mail's `name` or `ContentDisposition.FileName`, lettre's `Attachment::new(filename)` or `new_inline_with_name`, or the `filename` in a `:mimemail` part's `disposition_params`. A file the code reads from a path and doesn't name gets its name from the client. For gomail it is the file's base name, such as `report.pdf` for `files/report.pdf`, as its `Rename` option says. For the other clients, read how the installed client names it, as "Where the docs say nothing" says. A file with neither a name nor a path has no filename to give PostHog, and the site stays, as Step 3 says. This covers Nodemailer's `filename: false`, a Nodemailer `content` with no `filename`, which Nodemailer names `attachment-<n>.<ext>`, and lettre's `Attachment::new_inline(content_id)`.

**Content.** PostHog takes the file's bytes, in the form the rewrite file gives for the language:

- Bytes, such as a Node.js `Buffer`, Python `bytes`, a Ruby binary `String`, a PHP string, a .NET `byte[]`, a Go `[]byte`, a Rust `Vec<u8>`, or the body of a `:mimemail` part, move as the same bytes.
- A string the client decodes moves as the decoded bytes, decoded the same way in the moved code. This covers Nodemailer's `content` with `encoding: 'base64'` or `'hex'`, and a Ruby `mail` hash with `encoding:`, whose `content:` Mail takes as already encoded, as its docs say. Decode it with `Buffer.from(content, 'hex')` or `Base64.decode64(content)`, for example. When the SDK takes that form as it is, such as Node.js's Base64 string, pass it unchanged.
- A text string with no encoding moves as its bytes in the charset the client wrote: UTF-8 for Nodemailer. Pass the bytes in the form the rewrite file says, such as `text.b` in Ruby. Python's `add_attachment(text)` changes the text as it writes it, such as its line endings and a newline at the end, as its content manager docs say, so build the same part in the moved code, with `add_attachment` on an `EmailMessage` of its own, and pass the part's `get_payload(decode=True)`. Its content type is `text/<subtype>` with the `charset` it took, `utf-8` by default: pass that parameter, and note it as Step 3 says for a content type with parameters.
- A path to a file on the app's own disk moves as the file's content, read in the moved code. The SMTP client read the file inside the app's process, so the provider behind the host fetched nothing and Step 3's rule on a fetch doesn't apply. This covers Nodemailer's `path`, Ruby's `add_file`, PHPMailer's `addAttachment` and `addEmbeddedImage`, Symfony's `new File($path)`, gomail's `Attach` and `Embed`, go-mail's `AttachFile`, `EmbedFile` and `AttachFromEmbedFS`, MailKit's `Attachments.Add(path)` and `LinkedResources.Add(path)`, and System.Net.Mail's `Attachment(path)`. Read it where the client read or checked it, inside the same `try` as that call, and keep the bytes from there to the send, such as with `fs.readFile`, `File.binread`, `file_get_contents`, `os.ReadFile`, the same `embed.FS`'s `ReadFile`, or `File.ReadAllBytes`. Nodemailer streams the file from disk at the send, as its docs say, so read it right before the send. MailKit's `Attachments.Add(path)` throws `FileNotFoundException` at the add, PHPMailer's `addAttachment` answers `false` there for a file it can't read, and Ruby's `add_file` reads the file there, as their docs say, so read it in place of that call: a file the code deletes before the send is then already read, and the code's own check of the old call runs on the failed read, such as `if (!$mail->addAttachment(...))`. For any other client, read in the installed client where it opens the file, as "Where the docs say nothing" says. Where the client left out a file it couldn't read, leave it out the same way. Step 3's size check applies to the file.
- A URL keeps the site, as Step 3 says: the client fetched it, and PostHog fetches no file. This covers Nodemailer's `href`, and a `path` that is a URL in any client, such as `https://...`. The reason is `the provider fetches <file>`. PHPMailer's `addAttachment` takes no URL, as its docs say.
- A `data:` URI in Nodemailer's `path` moves as its decoded bytes. Its media type is the content type when the file sets none.
- A stream or a reader is read to its end in the moved code before the send. This covers a Nodemailer `content` stream, Symfony's `fopen` handle, go-mail's `AttachReader` and `EmbedReader`, MailKit's `Add(fileName, stream)`, and System.Net.Mail's `Attachment(stream, ...)`. Read it with `Buffer.concat((await stream.toArray()).map((c) => (typeof c === 'string' ? Buffer.from(c, enc) : c)))`, where `enc` is the encoding the code set on the stream, `'utf8'` when it set none, or with `stream_get_contents`, `io.ReadAll` or `CopyTo` a `MemoryStream`, for example. When Step 3's size check can't bound it, the site stays with the reason `files can pass 40 MB`.
- gomail's `SetCopyFunc` writes the content. Call its function in the moved code with an in-memory buffer, such as a `bytes.Buffer`, and pass what it wrote. An error it returns fails the moved send the way it failed the old one.

**Content type.** A type the code sets moves as it is, with every parameter, as Step 3 says. This covers Nodemailer's `contentType`, Python's `maintype` and `subtype` with their `params`, a Ruby `mail` `mime_type:`, PHPMailer's `$type`, Symfony's `$contentType`, go-mail's `WithFileContentType`, MailKit's `ContentType`, System.Net.Mail's `mediaType` or `ContentType`, lettre's `.body(content, content_type)`, and a `:mimemail` part's type and subtype with its `content_type_params`. When the code sets none, the client picks one. Nodemailer, Ruby `mail`, PHPMailer, Symfony and go-mail take it from an extension, as their docs say: the filename's, except PHPMailer's `addAttachment` and `addEmbeddedImage`, which take the path's, not `$name`'s. Nodemailer and go-mail fall back to `application/octet-stream`. Set the type that extension gives, such as `application/pdf` for `.pdf` or `text/calendar` for `.ics`, and note it in the plan row. When the extension is missing or not a common one, read how the installed client picks the type, as "Where the docs say nothing" says. Python's `MIMEImage` with no `_subtype` guesses the type from the image's bytes, which a file's extension doesn't settle, so the site stays, and the reason is `a content type the client guesses`.

**Content ID and disposition.** PostHog's send takes no disposition: a file with a content ID shows inline, and the HTML refers to it with `<img src="cid:...">`. The content ID is the bare ID the HTML shows after `cid:`:

- Nodemailer's `cid`, PHPMailer's `$cid`, go-mail's `WithFileContentID`, MailKit's `ContentId`, System.Net.Mail's `ContentId` on a `LinkedResource`, or on an `Attachment` whose `ContentDisposition.Inline` is `true`, and lettre's content ID move as they are.
- Python's `cid=` and a `Content-ID` header, and a `:mimemail` part's `Content-ID` header, move without their `<` and `>`, as the HTML shows them, such as `make_msgid()[1:-1]`.
- Python's `make_msgid()` and MailKit's `MimeUtils.GenerateMessageId()` end the ID in the host's name when the code passes no domain, and the code doesn't show that name's length. Pass them a fixed short domain in the moved code, such as the sender's domain, so the bare ID keeps Step 3's limit of 78 characters. The HTML takes the same new ID.
- Symfony: the HTML names an inline part `cid:<name>`, and Symfony puts a random Content-ID in its place at the send, as its docs say. The content ID is that name, and the HTML keeps `cid:<name>`. A part whose `setContentId(...)` ID the HTML names takes that ID.
- gomail's `Embed(path)` shows in the HTML as `cid:` and the file's base name, as gomail's example shows. The content ID is that base name, or the `Rename` name.
- Ruby `mail`'s `attachments.inline['logo.png']`, whose Content-ID the code reads through the file's `url`: set a fixed content ID in the moved code, such as the filename when it keeps Step 3's rules, and write `cid:<that ID>` where the code read `url`. When that HTML is built where the moved code can't change it, the site stays, and the reason is `a content ID the client sets`.
- go-mail's `EmbedFile` and `EmbedReader` with no `WithFileContentID` set a Content-ID of their own, which the HTML names. Read in the installed client which ID they set, as "Where the docs say nothing" says, and pass it as the content ID.

A file whose disposition isn't the one PostHog gives it keeps the site, and the reason is `a file's disposition PostHog doesn't set`. That is an inline file with no content ID, such as PHPMailer's `$disposition` set to `'inline'` on an `addAttachment`, or System.Net.Mail's `ContentDisposition.Inline = true` with no `ContentId`. It is also a file with a content ID that the code sends as an attachment, such as Nodemailer's `contentDisposition: 'attachment'` beside a `cid`, or a Nodemailer `cid` on a file that isn't an image, which Nodemailer sends as an attachment, as its docs say. A Nodemailer file with a `message/*` content type stays for the same reason, since Nodemailer sends it inline.

**What keeps a site.** A file option this section doesn't map keeps the site. The reason names the option:

| SMTP | Why |
|---|---|
| Nodemailer's `raw`, or a MIME part the code writes by hand, such as a Python `MIMEBase` or `MIMEApplication` with a header other than `Content-Type`, `Content-Disposition`, `Content-Transfer-Encoding` and `Content-ID`, which map as the parts above say, a lettre `SinglePart` that isn't an `Attachment` or a body, or a `:mimemail` part with a header other than `Content-ID` | The file is a MIME part the code built, and PostHog takes fields |
| A header on the file, such as Nodemailer's `headers`, Python's `headers=`, gomail's `SetHeader`, go-mail's `WithFileDescription`, or a header added to MailKit's entity | No PostHog SDK takes headers yet, as the `headers` row says |
| Nodemailer's `httpHeaders` | It goes with `href`, which stays |
| A way to add a file this section doesn't name | Read nothing into it: the reason is `a file this mapping doesn't name` |

A file's transfer encoding moves without it, such as Nodemailer's `contentTransferEncoding`, PHPMailer's `$encoding`, go-mail's `WithFileEncoding`, or a `:mimemail` part's `transfer_encoding`. It is how the bytes travel, and the mail app decodes the same file.

**Limits.** An SMTP server takes a message up to its own size limit, which the provider behind the host sets and the client doesn't check. Nodemailer takes any number of files, and a `data:` URI of up to 50 MB encoded, as its docs say. PostHog takes at most 10 files, and an email of up to 40 MB after Base64 encoding with its files, as Step 3 says. Step 3's checks decide.

**Templates.** SMTP stores no templates, so no stored template carries files. A template package can. `email-templates` can add its config's `message.attachments` to a send, as "Rewrite" says, and those files map as this section says.

**Where the docs say nothing.** Some clients fill in a part that their docs don't describe: the filename of a file read from a path, outside gomail; the content type of an uncommon extension; the Content-ID of go-mail's `EmbedFile`; and what each client does with a file it can't read. Read the installed client in the app's dependencies, such as `node_modules`, the virtualenv, the bundle, `vendor`, or the Go module cache. Find the code that fills in the part, set the same value in the moved code, and name the file you read in the plan row. The installed .NET clients, `System.Net.Mail` and MailKit, ship no source. A file whose name or type they would fill in keeps the site, and the reason is `a file part the client fills in`. When you can't find the code for any client, the site stays with the same reason.

| MailKit `Send`, `System.Net.Mail` `Send`, or an async send in a method that is not `async`, such as one it blocks on with `.Wait()` or `.GetAwaiter().GetResult()`, or doesn't await and doesn't return as the method's `Task` | A method that returns the send's `Task` with no result, such as `Task SendEmail() => client.SendMailAsync(message)`, isn't such a site: it moves, as `rewrite-dotnet.md` says. One that returns a `Task<T>` with the send's result is judged by "Code around the send". Otherwise `rewrite-dotnet.md` decides by the method: it has no synchronous send, so the site stays, and the reason is `synchronous .NET send`, unless the person agrees to make the method and its callers `async`. Ask in Step 3, before Step 4 sets up a sender for it, and only when nothing else keeps the site, such as a `SmtpClient.Timeout` the code set |
| `System.Net.Mail` `SendAsync(message, userToken)` | Always. It reports the send's result and its error to a `SendCompleted` handler instead of throwing them, and the moved send would skip that handler. The reason is `System.Net.Mail SendAsync with SendCompleted` |
| Elixir `:gen_smtp_client.send_blocking` with a `:mimemail.encode` body | A field above keeps it |
| Elixir `:gen_smtp_client.send/2` or `send/3` | Always. It sends in a process of its own and answers `{:ok, pid}` before the send ends, which callers may monitor or match: PostHog's send blocks the caller and answers the result. The reason is `gen_smtp send in its own process` |
| Rust `lettre` `send` | A field above keeps it |
| A send that names several recipients in `to`, or sends one message to a list in one call | Always. A loop that calls the send once per recipient is one site whose `to` is one address, and it moves |
| A framework mailer: Django `send_mail` or `EmailMessage` with the SMTP backend, Flask-Mail, Flask-Mailman, Rails Action Mailer, Laravel `Mail`, Symfony Mailer through the framework, Swoosh, Bamboo, NestJS `MailerService` | Always. PostHog has no mailer driver |
| A send in a language without a PostHog SDK that sends email, such as Java's Jakarta Mail or Kotlin | Always. Step 7 lists the languages PostHog's SDKs cover |

A Nodemailer transporter with a non-SMTP or third-party transport is not an SMTP site: `sdk-reference.md` says so under "Not SMTP". List its sends among the other calls.

## Code around the send

SMTP clients report an error in two ways. Node.js, Python, Ruby, PHPMailer with exceptions on, Symfony Mailer, and .NET throw. PHPMailer with exceptions off answers `false`, and Go, Elixir, and Rust answer an error value. The rewrite file says under "The answer" how PostHog's SDK reports an error in its language. Keep the site failing the same way it did, as the Rewrite section says.

| Code | A site stays on SMTP when |
|---|---|
| A `catch`, `except`, or `rescue` of the client's error, or a check of its error value, with no branch on one kind of error | Never. A branch on any error moves |
| A branch on an invalid send that takes every permanent refusal of the sender, the recipient, and the message, and nothing else. See the list below | Never. It becomes a branch on PostHog's error name `validation_error`, never on a status code, as the Rewrite section says |
| A branch on any other kind of SMTP error: a failed login (`EAUTH`, `SMTPAuthenticationError`, `AuthenticationException`, reply `535`), or a temporary refusal (`Net::SMTPServerBusy`, `err.permanent === false`, a `4xx` reply such as `421` or `451` that the code retries), and a branch on a refusal that the list below keeps | Always. These SMTP failures have no PostHog counterpart, and a catch of every PostHog error would widen the branch. This holds for a branch in a caller the site's error reaches, too: follow a thrown or returned error up to the code that handles it, and check its branches on `code`, `responseCode`, `permanent`, or the error class |
| A branch on one kind of network failure, such as a connection or timeout error (`ECONNECTION`, `ETIMEDOUT`, `SMTPServerDisconnected`, `SMTPConnectError`, `SMTPTimeoutError`, `Net::OpenTimeout`) | Always, as `7-rewrite.md` says under "Rewrite each site", with its exception for the timeout of a deadline the site keeps. An invalid send is the server refusing the sender, a recipient, or the message for good, with a `5xx` reply. A branch on it becomes a branch on `validation_error` only when it takes all three kinds and nothing else:

- Ruby: `rescue Net::SMTPFatalError, Net::SMTPSyntaxError`, both together. The gem raises them for `5xx` replies only, `SMTPSyntaxError` for `50x` ones such as a malformed address and `SMTPFatalError` for the rest, and a failed login raises `Net::SMTPAuthenticationError` instead.
- Node.js: `err.code === 'EENVELOPE' || err.code === 'EMESSAGE'`, with a check that `err.responseCode >= 500`.
- Python, `smtplib` or `aiosmtplib`: one catch of `SMTPSenderRefused`, `SMTPRecipientsRefused` (and `aiosmtplib`'s `SMTPRecipientRefused`), and `SMTPDataError` together, with a check for a `5xx` code.
- .NET: MailKit's `SmtpCommandException` whose `ErrorCode` is any of `SenderNotAccepted`, `RecipientNotAccepted`, and `MessageNotAccepted`, with `(int)e.StatusCode >= 500`.
- Any language: a check of a `5xx` reply code in `err.responseCode`, `e.smtp_code`, `e.StatusCode`, lettre's `error.status()`, or the error text, that a failed login, which answers `535`, doesn't pass.

A branch on a refusal keeps the site, as the row for other SMTP errors says, when:

- It takes one kind only, such as a refused recipient: `SMTPRecipientsRefused` alone, Ruby's `Net::SMTPFatalError` or `Net::SMTPSyntaxError` alone, since each lets the other's replies pass, MailKit's `RecipientNotAccepted`, `System.Net.Mail`'s `SmtpFailedRecipientException` or `SmtpFailedRecipientsException`, or one reply code, such as `550`. PostHog's `validation_error` also covers a sender it hasn't verified and an invalid subject, so the branch would run for those too.
- It has no `5xx` check. `smtplib`'s and `aiosmtplib`'s refusal classes, Nodemailer's `EENVELOPE` and `EMESSAGE`, and the .NET refusal exceptions carry any reply code, a temporary `4xx` refusal such as `450` or `451` too, so such a branch, such as a requeue on `SMTPDataError`, also took temporary refusals.

## Templates

SMTP stores no templates, so no site here has `template` content. The app renders its HTML in its own code, and the site sends it as `html` or `text`: the code form fits. Classify such a site by its other fields, and its body as the `text`, `html` row says. Step 3's question about templates stored at the provider has nothing to ask for SMTP.

A site whose send names a template stored at the provider behind the host through a header, such as SendGrid's `X-SMTPAPI` with a template id, stays for its header.

Two Node.js packages render inside the send. Their sites move when the moved code renders the same content first. The `subject` and `text`, `html` rows judge what the send ends up with after that render, not the message the site passes:

- **`nodemailer-express-handlebars`.** A site that sends `template` and `context` moves. When the message also sets `html`, the plugin renders nothing and the message goes out as it is: send its own `html` and `text`, and render nothing. Otherwise the moved code renders the view with the plugin's own options, `viewEngine`, `viewPath`, and `extName` (`.handlebars` when unset or empty), and sends the result as `html`, as the Rewrite section shows. A `text_template` renders into `text` the same way. The plugin renders no subject: the message's own `subject` is the subject. Keep the plugin on the transporter while any site that stays uses it.
- **`email-templates`.** A site moves when the `Email` config sets `send: true` and `preview: false`. The moved code prepares `locals` and the message as `send` does, calls `email.renderAll(template, locals, message)`, and sends its `subject`, `html`, and `text`, as the Rewrite section shows. When neither the template's subject file nor the message's `subject` gives a subject, the site stays as `no subject`. The config's `message` fields, such as `from` and `attachments`, are fields of the site too. When the config leaves `send` or `preview` to their defaults, the site stays, with the reason `email-templates sends only outside development and test`: the moved send would send from every environment.

Rendered content is classified the same way as any `html`: it moves as it is once the `text`, `html` row lets it.

## Webhooks

SMTP has no webhooks, so moving a site stops no SMTP event. The provider behind the host may post delivery events to a handler of the app (`sdk-reference.md`, "Webhooks"). That handler stops getting events for a site that moves. PostHog records the events of a moved send on the person it names with `distinctId`, when engagement capture is on:

| Event of the provider behind the host | PostHog event |
|---|---|
| Sent, processed, or accepted | `$workflows_email_sent` |
| Delivered | `$workflows_email_delivered` |
| Bounced, hard or permanent | `$workflows_email_bounced` |
| Spam complaint | `$workflows_email_blocked` |
| Opened | `$workflows_email_opened` |
| Clicked | none: a send in the code form counts no clicks |
| Dropped or suppressed | none. PostHog refuses the send instead, such as with `recipient_suppressed` |
| Deferred, soft bounce, unsubscribe, and other events | none |

PostHog's events carry no Message-ID of the SMTP message, no id of the provider behind the host, and no header the send set. A site whose events a handler matches by the Message-ID, by that provider's message id, or by a header stays on SMTP. A site whose emails a handler acts on for another event the table maps to none, such as a deferral, a soft bounce, or an unsubscribe, stays, as in Resend's mapping, and the reason is `its <event> events feed a webhook handler`. A site whose clicks a handler acts on stays too, since its moved sends would count none, and the reason is `its clicks feed a webhook handler`. For every other handler, the report tells the person which events it handles, which PostHog events take their place, and that a webhook destination in PostHog (Data pipelines, then Destinations) can post them to an endpoint. The handler itself keeps working for the sites that stay. Never change it.

When the app has no such handler, the report says that SMTP sends no delivery events, and that the moved sends get PostHog's events on the person.

## Rewrite

How a site that moves is written with PostHog's SDK. Step 7 says when to use each part, and the rewrite file for the site's language has the client and the send.

**The PostHog client.** Set `migratedFrom: 'smtp'` on the client that Step 7 configures, when its client options take it.

**The call.** The SMTP send and its connection become one PostHog send. Build its fields from the message the site built:

- Nodemailer `sendMail(message)`: the fields of `message`, with the transporter's `defaults`.
- Python `EmailMessage`: `msg["From"]`, `msg["To"]`, `msg["Reply-To"]`, and `msg["Subject"]`; `set_content(text)` is `text`, and `add_alternative(html, subtype="html")` is `html`. With `MIMEMultipart`, each `MIMEText(body, "plain")` and `MIMEText(body, "html")` part is `text` and `html`.
- Ruby `mail`: `from`, `to`, `reply_to`, `subject`, `text_part`, `html_part`, and `body`, which is `text` unless its content type is `text/html`.
- PHPMailer: `setFrom`, `addAddress`, `addReplyTo`, `Subject`, `Body` (`html` after `isHTML(true)`, else `text`), and `AltBody` (`text`). Symfony `Email`: `from`, `to`, `replyTo`, `subject`, `html`, and `text`.
- Go gomail: `SetHeader("From")`, `SetHeader("To")`, `SetHeader("Subject")`, `SetBody`, and `AddAlternative`, by content type. go-mail: `From`, `To`, `ReplyTo`, `Subject`, `SetBodyString`, and `AddAlternativeString`.
- MailKit: `From`, `To`, `ReplyTo`, `Subject`, and the `BodyBuilder`'s `TextBody` and `HtmlBody`. `System.Net.Mail`: `From`, `To`, `ReplyToList`, `Subject`, and `Body` (`html` when `IsBodyHtml`, else `text`), with a `text/html` or `text/plain` `AlternateView` as the other one.
- Elixir `gen_smtp`: the `From`, `To`, and `Subject` headers and the `text/plain` and `text/html` parts of the `:mimemail.encode` tuple.
- Rust `lettre`: `from`, `to`, `reply_to`, `subject`, and the body, or the plain and HTML bodies of `MultiPart::alternative_plain_html`.

**The fields.**

- `{ name: 'Example', address: 'hello@mail.example.com' }` and every other name and address pair in `from` becomes `'Example <hello@mail.example.com>'`. Put the name in double quotes when it holds a comma, a quote, or another special character: `'"Acme, Inc." <hello@mail.example.com>'`. A quoted name that is already in a `from` string, such as `'"Acme" <hello@mail.example.com>'`, keeps its quotes. A `from` without a name becomes the bare address. PHPMailer's `setFrom(address, name)`, MailKit's `MailboxAddress(name, address)`, and the other clients' name and address pairs become the same form.
- `to` becomes a bare address. A list with one entry becomes that entry. When a helper takes a list of recipients and every caller passes one address, change the parameter to one address and update the callers. Never send one email per address in a loop.
- A `Buffer` in `text` or `html` becomes its string. A `path` to a file becomes the file's content, read with the same encoding.
- Each file becomes one entry of `attachments`, with its filename, content, content type, and content ID, as "Attachments" says.
- A send with rendered content gets a `templateKey`, as Step 7 says.

**Template renderers.**

- `nodemailer-express-handlebars`: create the view engine once next to the PostHog client, as the plugin does, and render the view before the send:

  ```js
  import { create } from 'express-handlebars'
  import path from 'node:path'

  const viewEngine = create(hbsOptions.viewEngine)
  const html = await viewEngine.renderView(path.join(hbsOptions.viewPath, 'welcome' + (hbsOptions.extName || '.handlebars')), context)
  ```

  `hbsOptions` is the object the code passed to the plugin. When its `viewEngine` is already an engine with `renderView`, use it as it is. Share that object between the plugin and the moved code rather than copying it. `express-handlebars` is a peer dependency of the plugin: when the app doesn't list it in its own dependencies, add it with the project's package manager, at the version the lockfile already holds, since pnpm, for one, doesn't resolve a package the app doesn't list.
- `email-templates`: `send` merges the site's `locals` under the config's `views.locals`, so a config value wins, and the site's `message` over the config's `message`, so a site value wins, and `renderAll` does neither by itself. Do the same, with `siteMessage` set to `{}` when the site passes no message, as `send` does, then render: `const message = _.defaultsDeep({}, _.omit(siteMessage, 'attachments'), _.omit(email.config.message, 'attachments'))`, then `const { subject, html, text } = await email.renderAll(template, _.defaultsDeep({}, email.config.views.locals, locals), message)`, with lodash's `defaultsDeep` and `omit`, which `email-templates` uses. `defaultsDeep` would merge two lists of files entry by entry, so `attachments` stays out of it. The docs this skill cites don't say how `send` combines the config's `attachments` with the site's: read `send` in the installed `email-templates`, set `message.attachments` to the list it builds, name the file you read in the plan row, and map each file as "Attachments" says. When the app doesn't list `lodash` in its own dependencies, add it with the project's package manager: pnpm, for one, doesn't resolve a dependency of a dependency from the app's code. `renderAll` renders only the parts the message doesn't already hold. Then one PostHog send with those and the other `message` fields.

**Errors.** Keep the site failing the same way it did:

- **Node.js.** `posthog.emails.send` never throws on an API error: it answers `{ data, error }`. Where the awaited `sendMail` threw into a `catch`, or the promise rejected to its caller, throw from the error so the same path runs: `if (error) throw Object.assign(new Error(error.message), { name: error.name, code: error.code, statusCode: error.statusCode })`. Never put PostHog's HTTP status in `responseCode`: SMTP code reads it as an SMTP reply, where `4xx` is temporary and `5xx` is permanent. A log line that read `err.responseCode` reads `err.statusCode`. A check of an invalid send, as the list in "Code around the send" says, such as `(err.code === 'EENVELOPE' || err.code === 'EMESSAGE') && err.responseCode >= 500`, becomes `err.name === 'validation_error'`. A callback `(err, info) => { ... }` becomes the same code run with `err` from `error` and `info` from `data`. `info.messageId` becomes `data.id`. PostHog's answer holds only the id, so a site whose code reads a field of `info` that "Code around the send" doesn't convert, such as `info.envelope` or `info.response`, stays on SMTP, and the reason names the field.
- **Python.** PostHog's SDK raises too. A catch of every invalid send, as the list in "Code around the send" says, such as `except (SMTPSenderRefused, SMTPRecipientsRefused, SMTPDataError)` with its `5xx` check, becomes `except EmailError as e:` that checks `e.name == "validation_error"` and raises every other error again.
- **Python `aiosmtplib`.** Its errors are its own, not `smtplib`'s. `aiosmtplib.SMTPException` is the base of every error class its API reference lists, a refused connection and a timeout included, so `except aiosmtplib.SMTPException` becomes `except EmailError` with no connection check. Otherwise the site stays, and the reason is `catches one kind of network failure`. Its refusals of the sender, a recipient, or the message are not `OSError`s.
