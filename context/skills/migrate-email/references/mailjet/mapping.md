# Mailjet to PostHog mapping

This file decides, field by field, whether PostHog can send a Mailjet call site. A site moves only when every field it sets moves. Otherwise it stays on Mailjet, and the reason names the first field or feature that keeps it there. `api.md` has the PostHog side in full, and the rewrite file for the site's language, which Step 7 names, has PostHog's names in that language.

PostHog fields are written in their Node.js names here, such as `replyTo`. Use the name the rewrite file gives for the site's language, such as `reply_to` in Python. Mailjet fields are written in their v3.1 names, which the SDKs that take the JSON body send as they are. Go's structs and the .NET builder set them under their own names, and the v3 Send API has the older names in the last column.

**Attachments.** Mailjet takes a send's files in two lists of `{ ContentType, Filename, Base64Content }`: `Attachments`, the files the email carries, and `InlinedAttachments`, the files its HTML shows inline, which also take an optional `ContentID`. The v3 Send API names them `Attachments` and `Inline_attachments`, each of `{ Content-type, Filename, Content }`, with no content ID. Mailjet's pages spell the v3 fields more than one way: its v3 reference names the content `Content` and its v3 guide's samples `content`, its Ruby sample names the type `Content-Type` and the inline list `inline-attachments`, and Go's v3 struct takes `ContentType` and `Content`. Each spelling the code uses is the same field. Files in `Globals` are added to the message's. A stored template holds no files: Mailjet's reference divides a template's content among a text part, an HTML part, MJML content, and headers, so a template site's files come only from its message. Each file of a site that moves becomes one entry of PostHog's `attachments`, under the PostHog SDK's names, as its rewrite file gives them:

| Mailjet | PostHog |
|---|---|
| `Filename` | The filename, as it is. Mailjet requires one for each file |
| `ContentType`, or `Content-type` or `Content-Type` on v3 | The content type, as it is: a type with parameters, such as `text/calendar; method=REQUEST`, follows Step 3 under "Files". Mailjet requires one for each file |
| `Base64Content`, or `Content` or `content` on v3 | The content, in the form the rewrite file gives: the same Base64 string where the SDK reads one, or its decoded bytes where the SDK takes bytes only |
| `ContentID` of an inline file | The content ID, the same bare ID the HTML shows with `<img src="cid:...">` |
| An inline file without `ContentID`, and every v3 inline file | The content ID is the file's `Filename`, which the HTML shows with `cid:<Filename>`. It must keep PostHog's rules for a content ID, as Step 3 says under "Files" |

A file in `Attachments` carries no content ID, so it stays a file the email carries, and an inline file stays inline: there is no other disposition to keep. Mailjet fetches no file: the code reads each file and passes its Base64 content, so a site never stays for a fetched file. Mailjet's reference lists no file type it refuses, and PostHog refuses some, as Step 3 says. Mailjet takes a request of up to 15 MB, files and content included, so its files fit under PostHog's 40 MB. Its reference gives no limit on the count, and PostHog takes at most 10 files, inline files included, as Step 3 says. A template made in PostHog takes no files, as Step 7 says: a site with files that the person wants on such a template stays, and the reason is `a template in PostHog takes no files`.

**Tracking.** PostHog adds its open pixel to every email it sends, and counts clicks only for a template made in PostHog that is not marked sensitive, as Step 7 says. No field maps to tracking. Mailjet tracks opens as the send's `TrackOpens` says, and clicks as its `TrackClicks` says, within the account's settings. The account sets each one to `Enabled`, `Disabled`, or `Anonymous`, and a send never gets more than that. For each one the send leaves out or sets to `account_default`, use the account's setting: `Enabled` reads as `enabled`, `Disabled` as `disabled`, and `Anonymous` as `anon`. A send that sets `enabled` or `anon` reads as the account's setting when that setting is lower: `Disabled` turns it into `disabled`, and `Anonymous` turns `enabled` into `anon`. A contact can also refuse open tracking, which lowers it for that contact alone: Mailjet tracks their opens anonymously, or not at all where the account has no anonymous tracking. For the clicks note on a code send, `TrackClicks` `anon` reads as `enabled`. Then work out, for opens and for clicks, whether Mailjet tracked them:

- Opens `enabled`, and no contact of the account refused open tracking: the site moves.
- Opens `disabled`, and no contact of the account refused open tracking: the site's emails had no open pixel, so the person decides whether PostHog may add one, as Step 3 says under "Opens the provider didn't track".
- Opens `anon`: the site stays, and the reason is `anonymous open tracking`: PostHog's send has no anonymous open tracking.
- Opens `enabled` or `disabled`, and a contact of the account refused open tracking: the site stays, and the reason is `a contact refused open tracking`: PostHog would track that contact's opens.
- When Mailjet tracked the clicks of a site that moves, note in the plan row that PostHog counts no clicks for it, unless it moves to a template made in PostHog that is not marked sensitive.
- A site that moves to a template made in PostHog that is not marked sensitive gets every click counted on the person. That matches Mailjet only when its clicks were `enabled` and no contact of the account refused click tracking. When its clicks were `disabled` or `anon`, a contact refused click tracking, or the person didn't give the account's click setting or its contacts' click consent, ask the person to mark the template sensitive, which sends its links as they are. When they don't, the site stays, and the reason is `click tracking off`, `anonymous click tracking`, `a contact refused click tracking`, or `click tracking not checked`, as Step 3 says.
- A `TemplateID` site follows these rules like any other site, whether it is brought into the code or moves to a template made in PostHog.

Ask the person once for each Mailjet account the sites send from for its open and click tracking settings, and whether any contact refused open or click tracking, as `account.md` says under "Tracking settings". When the account's open tracking setting is not given, nobody can tell whether Mailjet tracked the opens of a site that doesn't set `TrackOpens: disabled`, and when its contacts' open consent is not given, nobody can tell whether a contact refused. Each such site of that account that the rules above don't already keep stays, and the reason is `open tracking not checked`, as Step 3 says under "Opens the provider didn't track".

The fields next to `Messages`:

| Mailjet | A site stays on Mailjet when |
|---|---|
| `Globals` | A field in it keeps the site, as in the table above |
| `SandboxMode` | It is `true`, or the code sets it at run time: a sandbox call is a check, not a send |
| `AdvanceErrorHandling` | Never: it changes only how Mailjet reports an error. The moved site sends nothing for it |

The client can also turn off every request, as `sdk-reference.md` says. Mailjet's SDK pages name three ways: Node's `.request(body, params, false)`, a PHP `Client` with `false` as its third argument, and Python's `Client(..., dry_run=True)`. Read the installed client for any other way it has, such as a `perform_api_call` setting on a node-mailjet 3.x client or the Ruby gem, a `'call'` key in the options of a PHP `post`, or an argument of .NET's send that sets `SandboxMode` for the call, and for where it reads it. A site whose client is set that way, or whose code or config sets it at run time, stays like `SandboxMode`: its call is a check, not a send. A PHP `post` on a `Client` made with `false` stays too, unless the installed client shows that the `post`'s own options send it.

A Mailjet send has no idempotency key, so the moved site sends none either. PostHog's SDK makes one for each call and reuses it on its own retries.

## Code around the send

A Mailjet SDK reports an error in one of three ways: it throws, it answers a response whose status the code reads, or, in Go, it answers an error value. Mailjet's SDK pages show how their samples read a failed send: Node.js `.catch`es an error and reads `err.statusCode`, Python reads `result.status_code`, since an HTTP error such as `400` doesn't raise, and catches `TimeoutError` and `CriticalApiError` for network errors, PHP reads `$response->success()`, .NET `PostAsync` reads `IsSuccessStatusCode` and `StatusCode`, and Go checks `if err != nil`. For most SDKs they don't say which failed answers throw, with which class, or what a network error does, and they show no error handling for Ruby or .NET `SendTransactionalEmailAsync`. So before the rewrite, read the installed client, as `sdk-reference.md` says under "Clients and sends", and the code's own checks, which show what it expected, and name the file you read in the plan row. When the installed client isn't there to read, such as when the app's dependencies aren't installed and the person can't install them, or doesn't settle what a site's error handling needs, the site stays, and the reason is `mailjet client not checked`. Any SDK can also answer a success whose message entry has `Status: 'error'`, and code may read that. A raw HTTP call does what its client does, with the options the code gives it: the Rewrite section lists which clients throw on a failed status. The rewrite file says under "The answer" how PostHog's SDK reports an error in its language. Keep the site failing the same way it did, as the Rewrite section says.

| Code | A site stays on Mailjet when |
|---|---|
| A `catch`, `rescue`, or `except` that reads the error's HTTP status, such as `err.statusCode`, its Mailjet `ErrorCode`, `ErrorIdentifier`, or `ErrorMessage`, the answer it carries, or its text | It branches on a Mailjet `ErrorCode`, `ErrorIdentifier`, or error text. A branch on the HTTP status moves: a branch on `400` reads PostHog's error name `validation_error`, and a branch on another status reads PostHog's status code |
| A check of `result.status_code`, `$response->success()`, `getStatus()`, `IsSuccessStatusCode`, or `StatusCode` | Never. Read PostHog's error instead, as the Rewrite section says |
| A check of `Messages[0].Status`, or a read of `Messages[0].Errors` | It branches on a Mailjet `ErrorCode` or error text. A check of `Status` alone moves: Mailjet sets `error` on a message it refused as invalid, so it becomes a branch on PostHog's error name `validation_error`. In .NET `SendTransactionalEmailAsync`, it moves only as that client's bullet under "Rewrite" says |
| Go: a type switch or `errors.As` on an error type of Mailjet's module | It branches on a Mailjet `ErrorCode` or error text. A branch on the type or on its status moves, as the Rewrite section says |
| `MessageID` or `MessageUUID` stored for a webhook handler or a status read | Always, when a handler or the message API uses it |
| `MessageID` or `MessageUUID` logged or stored for the app's own use | PostHog's message id is a string. `MessageID` is a number: a site that stores it where only a number fits, such as an integer column, or passes it on where callers expect a number, stays, and the reason is `stores the numeric MessageID`. Otherwise use PostHog's message id |

## Templates

A site that sends `TemplateID` moves by bringing the template into the code, as `template-to-code.md` says. The check needs the template's content, because the code has only its number. `account.md` says how to get it. A site that sets `TemplateLanguage: true` with its own `Subject`, `TextPart`, and `HTMLPart` moves the same way, with no content to get: the code renders that content before the send, where Mailjet rendered it after. Either way, the send sets the rendered `subject`, `html`, and `text`.

Without `TemplateLanguage: true`, Mailjet reads no `{{...}}` or `{% ... %}`, so the content goes out as it is written, and the moved send renders none of it. Mailjet's v3 docs fill `[[var:name]]` from `Vars` without `Mj-TemplateLanguage`, so render a `[[var:...]]` tag with the site's values either way, and note it in the plan row when `TemplateLanguage` isn't set: the v3.1 docs don't say whether Mailjet filled it then.

Mailjet's template language, in the code:

| Mailjet | In the code |
|---|---|
| `{{var:name}}`, `{{ var:name }}`, `[[var:name]]` | The value of `Variables`, escaped in the HTML part (see below). A boolean prints as `true` or `false`, as Mailjet's loop example shows, whatever the language prints. A value the site leaves out is a template error |
| `{{var:user.first_name}}` | The nested value, the same way. A left-out step of the path is a template error |
| `{{var:name:"there"}}`, `{{var:name:there}}`, `[[var:name:"there"]]` | The value, or `there` when the site leaves the value out. `""` is a value: it prints as nothing, and the default doesn't replace it. The docs don't say what `null` does: use the default for it, and note it in the plan row |
| `{% if var:a %}…{% elseif var:b %}…{% else %}…{% endif %}` | A branch that tests each value for Mailjet's truth, below, in order. `var:a:default` in a test uses the default when the value is left out. A left-out value without a default is a template error |
| `=`, `==`, `===`, `!=`, `<>`, `>`, `<`, `>=`, `<=` | The same comparison: `=`, `==`, and `===` all test equal, and `!=` and `<>` not equal. When the code can pass a number on one side and a string on the other, the docs don't say how Mailjet compares them, so the template stays |
| `and`, `or`, `xor`, `not`, and parentheses | The same logic. `xor` is true when exactly one side is true |
| `+`, `-`, `*`, `/`, `div`, `mod` | The same arithmetic: `/` divides with decimals, `div` keeps the integer part, and `mod` is the remainder. Spaces count: `var:x - 1` subtracts, and `var:x-1` is a value named `x-1` |
| `{% for item in var:items %}…{% endfor %}` | A loop over the list in order, or over the values of an object in the order the code put them in. A loop over a left-out value is a template error |
| Inside the loop: `{{ item }}`, `{{ item.name }}`, `{% for x in item.list %}` | The current item, its field, or a loop inside it. Mailjet has no index, first, or last value, and a `{{var:name}}` inside the loop still reads the send's value |
| `{% set name = value %}`, then `{{ name }}` | A local value in the code, set where the template sets it and changed where it sets it again. A value the site passes under the same name doesn't replace it |
| `Upper(x)`, `Lower(x)`, `Capitalize(x)` | The value in upper case, in lower case, or with its first letter in upper case and the rest as it is |
| `Round(x, n)`, `Int(x)` | The number rounded to `n` decimals, or its integer part. The docs don't say how a value halfway between rounds: round it away from zero, and note it in the plan row |
| `FormatNumber(format, n)`, `FormatNumberLocale(format, n, locale)` | The number written with the format: `0` is a digit always shown, `#` a digit shown only when it counts, `,` the thousands separator, and `.` the decimal point. `FormatNumber` uses `en_US`, `,` for thousands and `.` for decimals, as does `en_GB`. `fr_FR` uses a space for thousands and `,` for decimals, as the docs show `1 000,00`. Any other locale keeps the template on Mailjet |
| `UrlEncode(x)` | The value encoded for a URL. The docs don't say whether a space becomes `+` or `%20`: use `%20`, and note it in the plan row |
| `Escape(x)` | The value escaped as HTML, wherever it stands |
| `{{mj:contact.email}}`, `{{mj:contact.local_part}}`, `{{mj:contact.domain}}` | The `to` address, the part before its `@`, and the part after it |
| `{{mj:sender.email}}`, `{{mj:sender.local_part}}`, `{{mj:sender.domain}}` | The `from` address and its parts, the same way |
| `{{mj:template.ID}}`, `{{mj:template.name}}` | The template's number and name, written as they are |
| The template's `Headers.Subject`, or the site's `Subject` | The send's `subject`, rendered with the same language and no escaping |
| The template's `Html-part` | The send's `html`. `MJMLContent` is not used: the HTML part is already rendered from it |
| The template's `Text-part` | The send's `text`, with no escaping. An empty `Text-part` sends `html` only. The docs don't say what text Mailjet made from the HTML for a template with `IsTextPartGenerationEnabled`: note it in the plan row |
| The template's `Headers.From`, `Headers.Reply-to` | The send's `from` and `replyTo`, as the "Fields" table writes `From` and `ReplyTo` |

**Escaping.** Mailjet's docs never say it escapes a value, and its `Escape` function is there to escape one, so Mailjet inserted each value as it is. In the HTML part, a value the code builds as HTML itself goes in as it is, under the rule of `template-to-code.md`. Escape every other value, and note each one that carries text from a user, a form, or another service in the plan row. Never escape a value in the text part or the subject, unless the template passes it through `Escape`.

**Mailjet's truth.** The docs show `false` as false, and `true` and any other string as true, `"false"` included. They don't say what `0`, `""`, `null`, an empty list, or an empty object do. A test of a value alone, such as `{% if var:coupon %}`, that the code can pass as one of those keeps the template on Mailjet. A comparison, such as `var:count > 0` or `var:coupon != ""`, moves. Write the test out in the code, as `template-to-code.md` says.

**Template errors.** Mailjet checked the template language after it took the call, and the call answered as for any send. A left-out value without a default was a template error: Mailjet blocked the email, with a `blocked` event and the error `error in template language`. Since October 2025, a value that the template's variable schema declares renders as empty or `false` when the send leaves it out, and the email goes out, while a value it doesn't declare still blocks it. The docs don't say how to read that schema, so these files can't tell whether such a send went out. So a value without a default that the site can leave out keeps the template on Mailjet, and the reason is `<name> can be missing`. A site that always passes it moves. With `TemplateErrorDeliver: true`, Mailjet sent the email anyway: the site moves, the left-out value renders as nothing, and the plan row notes it, because the docs don't say what Mailjet printed in its place. `TemplateErrorReporting` mailed the error to an address: the report names that address, so the person knows those copies stop.

- **What keeps a template on Mailjet.** A tag Mailjet fills from the account, in any part: `[[UNSUB_LINK_EN]]` and every other `[[UNSUB_LINK...]]`, `[[UNSUB_ALL_LINK_EN]]`, `[[WORKFLOW_EXIT_LINK_EN]]`, `[[PERMALINK]]`, `[[SHARE_...]]`, `{{mj:unsub_link}}`, `{{mj:share_...}}`, and any other `[[...]]` tag without `var:`. A value only Mailjet holds: `{{segment:...}}`, `HasOpenedSince`, `HasClickedSince`, and any other `mj:` value, such as `mj:contact.ID`, `mj:contact.name`, or `mj:sender.name`. A function the table doesn't name. A header in `Headers` other than `From`, `Subject`, and `Reply-to`.
- **Contact properties.** `{{data:name}}` and `[[data:name]]` print a contact property stored at Mailjet, which the code doesn't have, so they keep the template on Mailjet. They move only when the person names the value of the app that the property holds, such as a first name the app stores and copies to Mailjet, and the code at the site can read it: it then prints that value, or its default, or nothing when the app has none, never a template error. Note it in the plan row.
- **Images.** Images uploaded to Mailjet's gallery or editor have URLs on a subdomain of `mjt.lu`, such as `https://<id>.mjt.lu/tplimg/...`. The docs don't name the host, so treat any image on a Mailjet host as one. Keep them, and list them, as `template-to-code.md` says.
- **The site's fields and the template's settings.** The template's `Headers` are defaults: a `From`, `Subject`, or `ReplyTo` that the site sets replaces the template's, as Mailjet did. A `From` or `Reply-to` header that holds the template language keeps the template: the docs say only the subject takes it. A `Reply-to` header with a name keeps it, as the "Fields" table says for `ReplyTo`.
- **Tracking.** A site brought into the code follows "Tracking" above, like any other site.

### Templates made in PostHog

Only for a template the person asks to make in PostHog, as Step 3 says. The person makes it from the Mailjet template and gives you its template ID, and makes it transactional once a verified sender covers its address, as Step 3 says. Until they give the ID, the site stays on Mailjet.

An email that carries a login code, a reset link, or another secret needs its PostHog template marked sensitive: PostHog then keeps no copy of each sent email's body or filled-in subject, and a clicked link keeps only the site's address. Templates are not sensitive by default.

A site that sends `TemplateID` without `TemplateLanguage: true` gets no `{{...}}` or `{% ... %}` filled in. Its template moves as it is, apart from each `[[var:...]]` tag, which converts as the table below says, with the site's `Variables` as `templateData`, and the plan row notes it, as "Templates" says for the code. A template that holds `{{` or `{%` keeps the site on Mailjet: Mailjet sent them as written, and PostHog's Liquid would read them. A site whose template has no `[[var:...]]` sends no `templateData`.

With `TemplateLanguage: true`, Mailjet's template language becomes Liquid in the PostHog template. Values move under `variables`, and each name keeps its case:

| Mailjet | PostHog |
|---|---|
| `{{var:name}}`, `[[var:name]]` | `{{ variables.name }}` |
| `{{var:user.first_name}}` | `{{ variables.user.first_name }}` |
| `{{var:name:"there"}}`, `{{var:name:there}}`, `[[var:name:"there"]]` | `{{ variables.name \| default: 'there' }}` |
| `{% if var:paid %}…{% elseif var:due %}…{% else %}…{% endif %}`, when `paid` and `due` are booleans | `{% if variables.paid %}…{% elsif variables.due %}…{% else %}…{% endif %}` |
| `{% for item in var:items %}{{ item.name }}{% endfor %}`, when `items` is a list | `{% for item in variables.items %}{{ item.name }}{% endfor %}` |
| `{{ item }}` inside `{% for item in var:items %}` | `{{ item }}` |
| `==`, `!=`, `>`, `<`, `>=`, `<=`, `and`, `or` in a condition that has one test, or joins its tests with only `and` or only `or` | The same, without the parentheses that hold whole tests or one value |
| The template's `Subject` header, or the site's `Subject` | The PostHog template's subject, with the same conversions |

Write the `\|` above as a plain `|`. The table escapes it.

- Liquid treats `0`, an empty string, and an empty list as true. Read what the site sends for each value an `if` or `elseif` tests alone. A value that is not always a boolean, `null`, or missing keeps the template on Mailjet. A comparison, such as `var:count > 0`, converts as it is.
- Inside a loop, the loop's own name reads the current item: `{{ item.name }}` stays `{{ item.name }}`, never `{{ variables.name }}`, and `{{ item }}` stays `{{ item }}`. Mailjet has no bare name that reads the item: a `{{var:name}}` inside the loop still reads the send's value, and becomes `{{ variables.name }}`.
- Liquid takes no parentheses in a condition: PostHog's renderer refuses `{% if (variables.a == true) and (variables.b == true) %}` with `invalid range syntax`. It also reads `and` and `or` from the right, so `a and b or c` means `a and (b or c)`. In a condition that has one test, or joins its tests with only `and` or only `or`, drop each pair of parentheses that holds whole tests or one value: `(var:count > 0)` and `(var:count) > 0` become `variables.count > 0`, and `(var:a == true) and (var:b == true)` becomes `variables.a == true and variables.b == true`. Keep parentheses inside a quoted string, such as `"Pro (annual)"`. A condition that mixes `and` with `or`, or whose parentheses make a test or a group of tests one side of a comparison, such as `(var:a > 1) == false` or `(var:paid or var:credited) == false`, keeps the template on Mailjet.
- Mailjet's `for` also walks the values of an object, and Liquid's `for` doesn't. A loop over a value that is not always a list keeps the template on Mailjet.
- PostHog's Liquid escapes HTML in every value. When the code passes a value that holds HTML, such as a rendered block or a link tag, or a default in the template holds HTML, such as `{{var:name:"<b>friend</b>"}}`, the template stays on Mailjet.
- `{{data:...}}`, `{{mj:...}}`, and `{{segment:...}}` read data stored at Mailjet, so a template that uses them stays on Mailjet.
- Any function, such as `Upper`, `Lower`, `Capitalize`, `Round`, `Int`, `FormatNumber`, `FormatNumberLocale`, `UrlEncode`, `Escape`, `HasOpenedSince`, or `HasClickedSince`, keeps the template on Mailjet. So do `{% set %}`, the operators `=`, `===`, `<>`, `xor`, `not`, `div`, `mod`, and arithmetic.
- A value without a default that the site can leave out keeps the template on Mailjet, as "Template errors" says above, unless the site sets `TemplateErrorDeliver: true`: Liquid prints nothing for it, where Mailjet may have blocked the email.
- Liquid's `default` also replaces an empty string and `false`, and Mailjet prints its default only when the value is not set. When the code can pass `false` for such a value, the template stays on Mailjet. When the code can pass an empty string, the email shows the fallback. Note it in the report.
- The PostHog template carries its own sender, reply-to address, and subject. A site that sets `From`, `ReplyTo`, or `Subject` next to `TemplateID` moves only when the value is the same in every send, and the person puts it into the PostHog template. Otherwise it stays.
- A template site follows "Tracking" like any other site, and stays where it says. When it moves, the tracking fields are dropped.

## Webhooks

Mailjet's Event API stops getting events for a site that moves. PostHog records the events of a moved send on the person it names with `distinctId`, when engagement capture is on:

| Mailjet event | PostHog event |
|---|---|
| `sent` | `$workflows_email_delivered`: Mailjet's `sent` means the receiving server took the email |
| `bounce` | `$workflows_email_bounced` |
| `spam` | `$workflows_email_blocked` |
| `open` | `$workflows_email_opened` |
| `click` | `$workflows_email_link_clicked`, only for a template made in PostHog that is not marked sensitive. PostHog treats a send in the code form as sensitive: its links go out as they are, and it counts no clicks |
| `blocked` | none. PostHog refuses the send instead, such as with `recipient_suppressed` |
| `unsub` | none |

PostHog also records `$workflows_email_sent` when it sends, which has no Mailjet event.

PostHog's events carry no Mailjet `MessageID`, `Message_GUID`, `CustomID`, or `Payload`. A site whose events a handler matches by message id, by `CustomID`, or by `Payload` stays on Mailjet. For every other handler, such as one that matches by `email`, the report tells the person which events it handles, which PostHog events take their place, and that a webhook destination in PostHog (Data pipelines, then Destinations) can post them to an endpoint. The handler itself keeps working for the sites that stay. Never change it.

A site whose emails a handler acts on for an event that has no PostHog event in the table, `blocked` or `unsub`, stays, and the reason is `its <event> events feed a webhook handler`. A site whose emails a `click` handler acts on moves only to a template made in PostHog that is not marked sensitive, since a send in the code form counts no clicks. Otherwise it stays, and the reason is `its clicks feed a webhook handler`.

## Calls that change the suppression list

The import takes hard bounces and spam reports, as `account.md` says. Mailjet records both itself, and these files know of no API call that adds one. A call that deletes a contact may remove its spam report: treat it as a call that removes an address, as Step 5 says. A call that unsubscribes a contact from a list, or sets `IsExcludedFromCampaigns`, changes a list the import leaves out, so it is not one of these calls.

## Rewrite

How a site that moves is written with PostHog's SDK. Step 7 says when to use each part, and the rewrite file for the site's language has the client and the send.

**The PostHog client.** Set `migratedFrom: 'mailjet'` on the client that Step 7 configures, when its client options take it.

**The call.** The Mailjet send becomes one PostHog send. Build its fields from the one message the site built, with `Globals` merged in:

- Node.js `mailjet.post('send', ...).request({ Messages: [msg] })`, Python `send.create(data={'Messages': [msg]})`, Ruby `Mailjet::Send.create(messages: [msg])`, PHP `$mj->post(Resources::$Email, ['body' => ['Messages' => [$msg]]])`, and a raw HTTP body: the fields of `msg`.
- Go `SendMailV31(&mailjet.MessagesV31{Info: []mailjet.InfoMessagesV31{msg}})`: the fields of `msg`. A `*mailjet.RecipientV31` becomes its `Email`, with its `Name` as for `From`.
- .NET `TransactionalEmailBuilder`: each `With...` call sets the field of its name. A `MailjetRequest` with a send resource: the fields of its one message, by their v3 names on the v3 Send API.
- The v3 Send API: `FromEmail` and `FromName`, `To` or the one `Recipients` entry, `Subject`, `Text-part`, `Html-part`, and the other fields by their v3 names.

**HTTP.** A raw request to `/v3.1/send` or `/v3/send` becomes the SDK's send in that language, as "The call" says. A request or Mailjet client with its own deadline keeps it, as Step 7 says under "Set up the client". These are the site's own deadline:

- On a raw request: `signal: AbortSignal.timeout(5000)`, got's `timeout`, `requests.post(..., timeout=5)`, httpx `timeout=`, Guzzle's `'timeout'`, Faraday's `timeout` on its default `net_http` adapter, Ruby `Net::HTTP`'s `read_timeout`, a Go `http.Client` `Timeout` or a context with a deadline, .NET's `HttpClient.Timeout`, and curl's `--max-time` or `CURLOPT_TIMEOUT`.
- On Mailjet's client, as its SDK pages show: Python's `timeout=` on `Client(...)` or on one call, such as `send.create(...)`; the timeout of the HTTP client the code gives PHP's `Client`, such as Guzzle's `'timeout'`, from 2.0; Go's `http.Client` with a `Timeout` given to `SetClient`; and .NET's `Timeout` on the `HttpClient` that `MailjetClient` takes, such as one set in `AddHttpClient<IMailjetClient, MailjetClient>`. Read the installed Python client for what its `timeout=` limits, such as each wait on the network as `requests` does, and follow Step 7 for that kind of limit, as the next bullet says.
- A limit that Mailjet's pages don't describe, but the installed client takes: read the installed client for the option and what it limits, such as a timeout method of a PHP 1.x client, a context the Go module takes for the send, or a `read_timeout` on a Ruby gem connection that the code builds itself, and whether the installed version reads it. When it doesn't read the option, the site never had it. When it does, follow Step 7 for that kind of limit: a limit the PostHog SDK in that language keeps moves with the site, and one it can't keep keeps the site. When the installed client doesn't settle what it limits, the site stays, and the reason is `mailjet client not checked`.
- An axios `timeout`, and so the `timeout` in node-mailjet's client `options`, such as `new Mailjet({ apiKey, apiSecret, options: { timeout: 5000 } })`, which Mailjet's Node.js page says passes through to axios, is a limit the SDK can't keep, and so is Faraday's `timeout` on another adapter. A `timeout` that a node-mailjet 3.x client takes is the same when the installed client passes it to axios too, and otherwise follows the bullet above. Each such site stays, as Step 7 and `rewrite-ruby.md` say.
- A client's default that the code never set, such as node-mailjet's 30 seconds since v7, or .NET `HttpClient`'s 100, is not one.
- A connect limit set apart from the request's keeps the site, as Step 7 says. On Mailjet's clients that includes a `connect_timeout` on the HTTP client the code gives PHP's `Client`, a `(connect, read)` pair given to Python's `timeout=` where the installed client hands it to `requests` as it is, and a connect limit that the installed client takes apart from its timeout, such as a PHP 1.x `setConnectionTimeout` or a Ruby connection's `open_timeout`. A connect limit that the client sets itself when the code doesn't is a default, not the site's.
- Mailjet's own retries count with the deadline. Mailjet's Python page says its client retries a `429` and `5xx` answers. Read the installed client for how many times, and for retries in the other clients. Such a site keeps its timeout for each request and the same number of retries, through the retry option the rewrite file names under "A deadline", instead of none. When the installed client doesn't settle the number, the site stays, and the reason is `mailjet client not checked`.

A request that a caller can cancel, such as a `signal` a caller passes in or an `AbortController` it aborts, a Go context, or a .NET cancellation token, keeps it only where the PostHog send takes the same cancellation, as Go's `Send(ctx, ...)` and .NET's `SendAsync(..., cancellationToken)` do: pass it there. Otherwise the site stays, as in Node.js, whose send takes no signal, and the reason is `the code can cancel the send`.

**The fields.**

- `From: { Email: 'hello@mail.example.com', Name: 'Example' }` becomes `'Example <hello@mail.example.com>'`. A name that holds a comma, a quote, or another special character goes in double quotes, such as `'"Acme, Inc." <hello@mail.example.com>'`, with each quote inside it escaped. A `From` without a `Name` becomes the bare address.
- `To` becomes a bare address. A list with one entry becomes that entry. When a helper takes a list of recipients and every caller passes one address, change the parameter to one address and update the callers. Never send one email per address in a loop.
- `TextPart` becomes `text`, and `HTMLPart` becomes `html`, rendered first when the site sets `TemplateLanguage: true`.
- `ReplyTo: { Email }` becomes `replyTo` with the bare address.
- `Attachments` and `InlinedAttachments`, with the files of `Globals`, become `attachments`, each file as "Attachments" under "Fields" says.
- `TrackOpens` and `TrackClicks` are dropped, and the send gets no `captureEngagement` for them, as "Tracking" says.
- A send with rendered content gets a `templateKey`, as Step 7 says.

**Templates brought into the code.** The site renders the email from `Variables`, as "Templates" says, and sends `templateKey`, the rendered `subject`, `html`, and `text`, and the `from` and `replyTo` that the site sets, or else the template's `From` and `Reply-to` headers. It sends no `templateId` and no `templateData`. A site with `TemplateLanguage: true` and its own content renders that content the same way before the send. A site that picks its `TemplateID` from a map, such as one template per locale, brings each template in it into the code, and picks the email the same way: it moves only when every one of them moves. A left-out value renders as "Template errors" under "Templates" says.

**Templates made in PostHog.** The site sends `templateId` with the template ID the person gave, and `templateData` with the site's `Variables`. It sends no `templateKey`, `subject`, `html`, `text`, `from`, or `replyTo`: the template holds them. A site that picks its `TemplateID` from a map, such as one template per locale, sends each template in it: it moves only when every one has a PostHog template ID, and the map then holds those IDs.

**Errors.** Keep the site failing the same way it did, and never widen a catch: a catch of one error class or one status becomes a catch of PostHog's error that checks for the same kind of error, and raises or returns every other error as before. A branch on Mailjet's answer to an invalid send, a `400` or a message with `Status: 'error'`, becomes a branch on PostHog's error name `validation_error`, never on a status code, as Step 7 says. A branch on another status, such as `429` or `401`, reads PostHog's status code. A branch that tries again or waits on `429` also checks for a code other than `quota_limited`: PostHog answers a used-up quota with `429` and that code, and a retry doesn't clear a quota. A network error that is left after PostHog's retries comes back as PostHog's error with the code `network_error`. Where Mailjet's network error went past the old branch, let PostHog's go past the new one.

- **Node.js.** `posthog.emails.send` never throws on an API error: it answers `{ data, error }`. Where `.request()` threw into a `catch`, as Mailjet's samples `.catch` it and as the installed client shows for the failed statuses and the network errors it rejects on, throw from the error so the same `catch` runs: `if (error) throw Object.assign(new Error(error.message), { statusCode: error.statusCode, name: error.name, code: error.code })`. `err.statusCode` keeps holding the HTTP status, and a network failure, which has none, has `err.code` `network_error`, so a branch on `err.statusCode === 429` still takes only that status. A check of `err.statusCode === 400` becomes a check of `err.name === 'validation_error'`. A read of the error's other fields, such as its Mailjet `ErrorMessage` or the answer it carries, becomes a read of `err.message`. Where the installed client resolved some failed statuses or network errors instead, the code saw them in the result: follow the bullet below for a client that answers a failed status as a response for those.
- **Ruby.** PostHog's SDK raises too. Read the installed gem for the class it raises on an API error, its subclasses for some statuses, and the attribute that holds the HTTP status, as `sdk-reference.md` says. A `rescue` of the class the gem raised for every API error, such as `Mailjet::CommunicationError` where the installed gem raises that, becomes a `rescue` of the PostHog error the rewrite file names, and a read of the HTTP status the gem's error held, such as an `e.code`, becomes `e.status_code`: PostHog's `e.code` is its own error code, not the HTTP status. A `rescue` of one subclass becomes a `rescue` of the PostHog error that checks for the same kind of error, and raises every other error again: a subclass for `400`, such as `Mailjet::BadRequest`, checks the name `validation_error`, and one for another status, such as `401`, checks that status code. Where the installed gem let the HTTP library's own error through on a network failure, the old `rescue` of its class saw only API errors, so the new one first raises again an error whose `code` is `network_error`. Where it raised its class for a network failure too, `network_error` takes the same branch as every other error.
- **Ruby, a refused send the gem answers.** Where the installed gem answers some refused sends in the body without raising, such as a recipient refused as an invalid address on the v3.1 Send API, and raises its `400` error for other invalid sends, PostHog raises `validation_error` for both. So such a site moves only when the old code ended both the same way: what ran for a send the gem answered, which is the site's check of the answer's `Status`, or the code after the send when it checked none, is what ran for the gem's `400` error, whether in a `rescue` of it, of the gem's error class, or of every error, or, with no `rescue`, by raising out of the site. Raising out of the site counts as the same only when both raised the same error. Then a `rescue` that checks the name `validation_error` runs that. When they differ, such as a `Status` check that returns `false` while the `400` error raises out of the site, or a site that checks no `Status` while its `400` error reaches a `rescue` that retries, the site stays, and the reason is `can't tell Mailjet's invalid-send paths apart`. A site that checks no `Status` and rescues nothing follows "A site that read no result" instead. Where the installed gem raises on every refused send of the site's Send API, a `rescue` of its `400` error maps straight to `validation_error`, and a site that rescues nothing keeps raising every PostHog error.
- **Python, where the installed client raises on failed statuses.** Mailjet's Python page says an HTTP error such as `400` answers a response, which the next bullet covers. Read the installed `mailjet_rest` for the statuses it raises on instead, such as a `401` or a status its retries gave up on, and for the class of each, as `sdk-reference.md` says. A `result.status_code` branch on a status the client raised on never ran: drop that status from it. Where the client raises on every failed status, as PostHog's SDK does, a site that catches nothing keeps raising, and a `result.status_code` check after the call saw only successes: keep the code after it as the success path. A catch of a Mailjet class the client raised for every error becomes a catch of the PostHog error the rewrite file names. A catch of a class it raised for some statuses only checks PostHog's error for the same statuses, a `400` as the name `validation_error` and any other as the status code, and raises every other error again. A catch of a class it raised only for network failures checks the code `network_error`. A catch of a class the installed client never raised for the send, such as one for a status its own retries took and then reported under another class, never ran: the site stays, and the reason is `catches a Mailjet error its client never raised`. A read of the error's HTTP status reads PostHog's status code, and a read of the answer it carries or its text reads its message.
- **Python, the client's retries.** Mailjet's Python page says its client retries a `429` and `5xx` answers before it answers or raises. Write the send as the rewrite file says, with the retries PostHog's SDK makes itself, and add no retry loop around it. The plan row notes the statuses the installed client retried, so that the person knows such an error may now reach the site's handling sooner.
- **Python, PHP, and .NET `PostAsync`, where the client answers a failed status.** The code read Mailjet's status: `result.status_code`, `$response->success()`, `getStatus()`, `IsSuccessStatusCode`, or `StatusCode`. PostHog's SDK raises or throws instead. Put the send in a `try`, and catch the PostHog error the rewrite file names. A failed status, such as `status_code != 200` or `!$response->success()`, becomes that catch, and it takes the branch the status check took. A branch on `400` checks PostHog's error name `validation_error` in the catch, and a branch on another status, such as 429, checks PostHog's status code. The catch handles every other error the way the old code handled a status it didn't branch on. Where the installed client raised its network errors past the status check, as Mailjet's Python page says its client does, the catch raises PostHog's error again when its code is `network_error`. Where it raised on some statuses past the check too, as the Python bullet above says, the catch also raises PostHog's error again for those statuses, unless a catch of the old code took them: then it runs that catch's branch. In PHP, read the installed client and its HTTP client for what the call lets through on a network failure. Where it answered every failed status itself and let only the HTTP client's network exceptions through, such as Guzzle's, a catch of `GuzzleException`, `TransferException`, or Guzzle 6's `RequestException` around its call checks the code `network_error` and raises every other error again, and so does a catch of PSR-18's `ClientExceptionInterface` or `NetworkExceptionInterface` where the installed HTTP client throws it for every network failure. A catch of `ConnectException` alone, or of Guzzle 7's `RequestException`, took one kind of network failure, so the site stays, as Step 7 says. A catch of `BadResponseException`, `ClientException`, or `ServerException` never ran there: drop it. A read of `result.json()`, `result.text`, `getData()`, or `GetErrorMessage()` for the error becomes the error's message. A catch of a Mailjet class around the send that the installed client raised only for network failures checks the code `network_error`, and for any status the class also took, that status code, and raises every other error again.
- **Python, every version.** A catch of only `TimeoutError` or only `CriticalApiError` took one kind of network failure, a timeout or a failed connection, as Mailjet's Python page shows, so the site stays, as Step 7 says.
- **.NET `SendTransactionalEmailAsync`.** Read the installed package for what the call does with each failed status, as `sdk-reference.md` says. Where it returns the response for every invalid send, the code saw `Messages[0].Status` `"error"`, which follows "Any language" below. Where it throws its own exception for every invalid send, such as one that holds the HTTP status, a `catch` of it becomes a `catch` of PostHog's error that checks the name `validation_error` for a `400`, and the status code for any other status it branched on. Where it does both for invalid sends, such as returning the response when the answer holds `Messages` and throwing when it doesn't, PostHog's SDK throws `validation_error` for both, so the site moves only when the old code ended both the same way: what ran for a `Status` of `"error"`, or the code after the send when the site didn't check `Status`, is what ran for the exception with the status `400`, whether in a `catch` of that exception, in a general `catch (Exception)`, or, with no handler, by leaving the site. Then the `catch` runs that for the name `validation_error`. When they differ, such as a site that checks no `Status` and goes on while the exception leaves the site or reaches a handler that does something else, the site stays, and the reason is `can't tell Mailjet's invalid-send paths apart`. For every other error, the `catch` runs what ran for the exception with that status, with the status it held read as PostHog's status code, and throws it again when nothing caught it. Where a network error went past both before, as the ".NET, every client" bullet says, the `catch` throws again when the code is `network_error`.
- **Go.** PostHog's `Send` answers an error value too, always a `*posthog.EmailError`. Keep `if err != nil`: it took Mailjet's network errors too. A type switch or `errors.As` on an error type of Mailjet's module reads `*posthog.EmailError` with `errors.As` instead, and keeps each branch. Read the installed module for the statuses each type stands for, as `sdk-reference.md` says. A branch on a type that stands for a `400`, such as one that holds the answer's `Messages[].Errors`, checks the name `validation_error`, and for each other status the type stands for, such as a `403`, that status code. A branch on a type that stands for every other status takes every PostHog error that no other branch takes and whose code is not `network_error`, and a check of its status, such as 429, reads PostHog's `StatusCode`. Every other error goes on as before.
- **Raw HTTP whose client answers a failed status as a response.** These are `fetch`, `requests`, `httpx`, Ruby's `Net::HTTP`, Go's `net/http`, PHP's `curl_exec`, `curl` without `--fail`, Guzzle with `'http_errors' => false`, .NET `HttpClient` without `EnsureSuccessStatusCode()`, and a throwing client with an option that turns the throw off for every failed status, such as axios's `validateStatus: () => true` or `validateStatus: null`, or `throwHttpErrors: false` in got or ky. An option that turns it off for some failed statuses only, such as `validateStatus: s => s < 500`, kept the throw for the rest, which PostHog's status codes don't match one to one: the site stays, and the reason is `its client throws on only some failed statuses`. A call to `/v3.1/send` raised on a status only where the code checked it, such as `!res.ok`, `raise_for_status()`, or `resp.StatusCode >= 300`. That check becomes PostHog's error, as for Python above. The HTTP client raised its own error on a network failure. When the old catch took that too, such as `except requests.RequestException` or a `catch` around `fetch`, the new catch takes `network_error` too. When it took only the status error, such as `requests.HTTPError`, raise `network_error` again. PHP's `curl_exec` raised nothing on a network failure: it returned `false`, and `curl_getinfo` gave the status `0`. So a check that the status `0` meets, such as `!== 200` or `< 200`, took a network failure too, and the catch takes `network_error` the same way. A check that `0` doesn't meet, such as `>= 300` or `>= 400`, let a network failure go on as if the send worked: the catch logs `network_error` and goes on. A check that only `curl_exec` returned `false` took only the network failure, so the catch runs its code for `network_error` alone, and handles every other error as the site's status check did, or logs it and goes on when the site checked no status.
- **Raw HTTP whose client throws on a failed status.** These are `axios`, `got`, `ky`, Guzzle, Faraday with `raise_error`, and .NET `HttpClient` followed by `EnsureSuccessStatusCode()`, each without an option that turns the throw off. The call failed on every API error and every network failure, whether the code read the answer or not. Keep that: every PostHog error fails the site. In Node.js, throw from `error` as the Node.js bullet says. In Python, Ruby, PHP, and .NET, PostHog's SDK raises on its own. A catch of the client's error becomes a catch of PostHog's error that takes the same failures. Guzzle's `GuzzleException` or `TransferException`, Guzzle 6's `RequestException`, and `Faraday::Error` took network failures too. A catch of .NET's `HttpRequestException` follows the ".NET, every client" bullet below. Guzzle 7's `BadResponseException` took failed statuses only, so that catch raises PostHog's error again when its code is `network_error`; `ClientException` also checks a 4xx status code, and `ServerException` a 5xx one, and each raises every other error again. Guzzle 7's `RequestException` took some network failures, such as a failed receive, but not a failed connection, its `ConnectException`, and a catch of `ConnectException` alone, in Guzzle 6 or 7, took only a failed connection. Each of these Guzzle catches keeps its site, as Step 7 says for one kind of network failure. A read of the client's status in that catch, such as axios's `err.response.status` or got's `err.response.statusCode`, reads PostHog's status code, and a branch on `400` reads PostHog's error name `validation_error`. Never log the error and go on here.
