# Mailjet to PostHog mapping

This file decides, field by field, whether PostHog can send a Mailjet call site. A site moves only when every field it sets moves. Otherwise it stays on Mailjet, and the reason names the first field or feature that keeps it there. `api.md` has the PostHog side in full, and the rewrite file for the site's language, which Step 7 names, has PostHog's names in that language.

PostHog fields are written in their Node.js names here, such as `replyTo`. Use the name the rewrite file gives for the site's language, such as `reply_to` in Python. Mailjet fields are written in their v3.1 names, which every SDK sends as they are. The .NET builder sets them with `With...` methods, and the v3 Send API has the older names in the last column.

## Fields

A Mailjet send is a list of messages. A site with more than one entry in `Messages` stays (see "Calls"). The table is for the fields of its one message, after the fields of `Globals` are merged into it.

| Mailjet | PostHog | A site stays on Mailjet when | v3 name |
|---|---|---|---|
| `From` | `from` | Never. `{ Email, Name }` becomes `'Name <email>'`, with the name in double quotes when it holds a comma, a quote, or another special character. It needs a verified sender (Step 4) | `FromEmail`, `FromName` |
| `Sender` | none | Always. PostHog's send doesn't take it yet | `Sender` |
| `To` | `to` | It holds more than one address. A list with one entry moves as that entry. `{ Email, Name }` moves as the bare address: note in the plan row that the To line loses the name | `To`, or `Recipients` |
| `Subject` | `subject` | Never | `Subject` |
| `TextPart`, `HTMLPart` | `text`, `html` | They hold a tag that Mailjet fills from the account, such as `[[UNSUB_LINK_EN]]` or `[[PERMALINK]]`, as "Templates" says. With `TemplateLanguage: true`, see "Templates" | `Text-part`, `Html-part` |
| `TemplateID` with `Variables` | the template's email, brought into the code and rendered with `Variables`, sent as `subject`, `html`, and `text`. A template made in PostHog, by its `templateId` with `templateData`, only when the person asks for one | See "Templates" | `Mj-TemplateID`, `Vars` |

See "Tracking" below. `disabled` counts as set: it turns that tracking off for the send, whatever the account's setting | `Mj-trackopen` set to `1` (`disabled`), `2` (`enabled`), or `0` (`account_default`), or not set. `Mj-trackclick` set to any value, or not set |
| `TrackOpens` set to `anon` | none | Always. PostHog's send has no anonymous open tracking | `Mj-trackopen` set to `3` |

**Tracking.** PostHog adds its open pixel to every email it sends, and counts clicks only for a template made in PostHog that is not marked sensitive, as Step 7 says. No field maps to tracking. Mailjet tracks opens as the send's `TrackOpens` says, and clicks as its `TrackClicks` says, within the account's settings. The account sets each one to `Enabled`, `Disabled`, or `Anonymous`, and a send never gets more than that. For each one the send leaves out or sets to `account_default`, use the account's setting: `Enabled` reads as `enabled`, `Disabled` as `disabled`, and `Anonymous` as `anon`. A send that sets `enabled` or `anon` reads as the account's setting when that setting is lower: `Disabled` turns it into `disabled`, and `Anonymous` turns `enabled` into `anon`. A contact can also refuse open tracking, which lowers it for that contact alone: Mailjet tracks their opens anonymously, or not at all where the account has no anonymous tracking. For the clicks note on a code send, `TrackClicks` `anon` reads as `enabled`. Then work out, for opens and for clicks, whether Mailjet tracked them:

- Opens `enabled`, and no contact of the account refused open tracking: the site moves. When Mailjet tracked its clicks too, note in the plan row that PostHog counts no clicks for it, unless it moves to a template made in PostHog that is not marked sensitive.
- Opens `disabled`: the site stays, and the reason is `open tracking off`: PostHog would add an open pixel the email never had.
- Opens `anon`: the site stays, and the reason is `anonymous open tracking`: PostHog's send has no anonymous open tracking.
- Opens `enabled`, and a contact of the account refused open tracking: the site stays, and the reason is `a contact refused open tracking`: PostHog would track that contact's opens.
- A site that moves to a template made in PostHog that is not marked sensitive gets every click counted on the person. That matches Mailjet only when its clicks were `enabled` and no contact of the account refused click tracking. When its clicks were `disabled` or `anon`, a contact refused click tracking, or the person didn't give the account's click setting or its contacts' click consent, ask the person to mark the template sensitive, which sends its links as they are. When they don't, the site stays, and the reason is `click tracking off`, `anonymous click tracking`, `a contact refused click tracking`, or `account tracking not checked`.
- A `TemplateID` site follows these rules like any other site, whether it is brought into the code or moves to a template made in PostHog.

Ask the person once for each Mailjet account the sites send from for its open and click tracking settings, and whether any contact refused open or click tracking, as `account.md` says under "Tracking settings". When the answers for open tracking are not given, each site of that account that the rules above don't already keep stays, and the reason is `account tracking not checked`.

The fields next to `Messages`:

| Mailjet | A site stays on Mailjet when |
|---|---|
| `Globals` | A field in it keeps the site, as in the table above |
| `SandboxMode` | It is `true`, or the code sets it at run time: a sandbox call is a check, not a send |
| `AdvanceErrorHandling` | Never: it changes only how Mailjet reports an error. The moved site sends nothing for it |

The client can also turn off every request, as `sdk-reference.md` says: Node's `.request(body, params, false)`, node-mailjet 3.x's `perform_api_call: false` in the options of `.post`, or in those of `connect` for a `.post` given no options, a PHP `post` with `'call' => false` in its options, or with no options on a `Client` with `false` as its third argument, Ruby's `perform_api_call` set to `false`, Python's `Client(..., dry_run=True)`, and .NET's `SendTransactionalEmailAsync` or `SendTransactionalEmailsAsync` with `isSandboxMode` `true`, by position or by name. A site whose client is set that way, or whose code or config sets it at run time, stays like `SandboxMode`: its call is a check, not a send.

A Mailjet send has no idempotency key, so the moved site sends none either. PostHog's SDK makes one for each call and reuses it on its own retries.

## Code around the send

Mailjet's SDKs report an error in three ways. The Node.js and Ruby SDKs, and Python's from `mailjet-rest` 1.8.0, throw. Python's before 1.8.0, PHP's, and .NET `PostAsync` answer a response, and the code reads its status. Read the Python version as `sdk-reference.md` says. When the lockfile and the manifest don't name it, or name only a range that allows versions in more than one of its bands, ask the person once which version production runs. When they can't tell, every Python site stays, and the reason is `mailjet-rest version not checked`. The Go SDK answers an error value. Any SDK can also answer a success whose message entry has `Status: 'error'`, and code may read that. A raw HTTP call does what its client does, with the options the code gives it: the Rewrite section lists which clients throw on a failed status. The rewrite file says under "The answer" how PostHog's SDK reports an error in its language. Keep the site failing the same way it did, as the Rewrite section says.

| Code | A site stays on Mailjet when |
|---|---|
| A `catch`, `rescue`, or `except` that reads `err.statusCode`, `err.ErrorMessage`, `err.ErrorCode`, `err.response`, `e.code`, Python's `e.status_code` or `e.response_body`, or the error's text | It branches on a Mailjet `ErrorCode`, `ErrorIdentifier`, or error text. A branch on the HTTP status moves: a branch on `400` reads PostHog's error name `validation_error`, and a branch on another status reads PostHog's status code |
| A check of `result.status_code`, `$response->success()`, `getStatus()`, `IsSuccessStatusCode`, or `StatusCode` | Never. Read PostHog's error instead, as the Rewrite section says |
| A check of `Messages[0].Status`, or a read of `Messages[0].Errors` | It branches on a Mailjet `ErrorCode` or error text. A check of `Status` alone moves: Mailjet sets `error` on a message it refused as invalid, so it becomes a branch on PostHog's error name `validation_error` |
| Go: a type switch or `errors.As` on `*mailjet.APIFeedbackErrorsV31` or `*mailjet.ErrorInfoV31` | It branches on a Mailjet `ErrorCode` or error text. A branch on the type or on `StatusCode` moves, as the Rewrite section says |
| `MessageID` or `MessageUUID` stored for a webhook handler or a status read | Always, when a handler or the message API uses it |
| `MessageID` or `MessageUUID` logged or stored for the app's own use | PostHog's message id is a string. `MessageID` is a number: a site that stores it where only a number fits, such as an integer column, or passes it on where callers expect a number, stays, and the reason is `stores the numeric MessageID`. Otherwise use PostHog's message id |

## Templates

A site that sends `TemplateID` moves by bringing the template into the code, as `template-to-code.md` says. The check needs the template's content, because the code has only its number. `account.md` says how to get it. A site that sets `TemplateLanguage: true` with its own `Subject`, `TextPart`, and `HTMLPart` moves the same way, with no content to get: the code renders that content before the send, where Mailjet rendered it after. Either way, the send sets the rendered `subject`, `html`, and `text`.

Without `TemplateLanguage: true`, Mailjet reads no `{{...}}` or `{% ... %}`, so the content goes out as it is written, and the moved send renders none of it. Mailjet's v3 docs fill `[[var:name]]` from `Vars` without `Mj-TemplateLanguage`, so render a `[[var:...]]` tag with the site's values either way, and note it in the plan row when `TemplateLanguage` isn't set: the v3.1 docs don't say whether Mailjet filled it then.

Mailjet's template language, in the code:

| Mailjet | In the code |
|---|---|
| `{{var:name}}`, `{{ var:name }}`, `[[var:name]]` | The value of `Variables`, escaped in the HTML part (see below). A boolean prints as `true` or `false`, as Mailjet's loop example shows, whatever the language prints. A value the site leaves out is a template error |
| `{{var:user.first_name}}` | The nested value, the same way. A left-out step of the path is a template error |
| `{{var:name:"there"}}`, `{{var:name:there}}`, `[[var:name:"there"]]` | The value, or `there` when the site leaves the value out. `""` is a value: it prints as nothing, and the default doesn't replace it. The docs don't say what `null` does: use the default for it, and note it in the plan row |
| `{% if var:a %}…{% elseif var:b %}…{% else %}…{% endif %}` | A branch that tests each value for Mailjet's truth, below, in order. `var:a:default` in a test uses the default when the value is left out. A left-out value without a default is a template error |
| `=`, `==`, `===`, `!=`, `<>`, `>`, `<`, `>=`, `<=` | The same comparison: `=`, `==`, and `===` all test equal, and `!=` and `<>` not equal. When the code can pass a number on one side and a string on the other, the docs don't say how Mailjet compares them, so the template stays |
| `and`, `or`, `xor`, `not`, and parentheses | The same logic. `xor` is true when exactly one side is true |
| `+`, `-`, `*`, `/`, `div`, `mod` | The same arithmetic: `/` divides with decimals, `div` keeps the integer part, and `mod` is the remainder. Spaces count: `var:x - 1` subtracts, and `var:x-1` is a value named `x-1` |
| `{% for item in var:items %}…{% endfor %}` | A loop over the list in order, or over the values of an object in the order the code put them in. A loop over a left-out value is a template error |
| Inside the loop: `{{ item }}`, `{{ item.name }}`, `{% for x in item.list %}` | The current item, its field, or a loop inside it. Mailjet has no index, first, or last value, and a `{{var:name}}` inside the loop still reads the send's value |
| `{% set name = value %}`, then `{{ name }}` | A local value in the code, set where the template sets it and changed where it sets it again. A value the site passes under the same name doesn't replace it |
| `Upper(x)`, `Lower(x)`, `Capitalize(x)` | The value in upper case, in lower case, or with its first letter in upper case and the rest as it is |
| `Round(x, n)`, `Int(x)` | The number rounded to `n` decimals, or its integer part. The docs don't say how a value halfway between rounds: round it away from zero, and note it in the plan row |
| `FormatNumber(format, n)`, `FormatNumberLocale(format, n, locale)` | The number written with the format: `0` is a digit always shown, `#` a digit shown only when it counts, `,` the thousands separator, and `.` the decimal point. `FormatNumber` uses `en_US`, `,` for thousands and `.` for decimals, as does `en_GB`. `fr_FR` uses a space for thousands and `,` for decimals, as the docs show `1 000,00`. Any other locale keeps the template on Mailjet |
| `UrlEncode(x)` | The value encoded for a URL. The docs don't say whether a space becomes `+` or `%20`: use `%20`, and note it in the plan row |
| `Escape(x)` | The value escaped as HTML, wherever it stands |
| `{{mj:contact.email}}`, `{{mj:contact.local_part}}`, `{{mj:contact.domain}}` | The `to` address, the part before its `@`, and the part after it |
| `{{mj:sender.email}}`, `{{mj:sender.local_part}}`, `{{mj:sender.domain}}` | The `from` address and its parts, the same way |
| `{{mj:template.ID}}`, `{{mj:template.name}}` | The template's number and name, written as they are |
| The template's `Headers.Subject`, or the site's `Subject` | The send's `subject`, rendered with the same language and no escaping |
| The template's `Html-part` | The send's `html`. `MJMLContent` is not used: the HTML part is already rendered from it |
| The template's `Text-part` | The send's `text`, with no escaping. An empty `Text-part` sends `html` only. The docs don't say what text Mailjet made from the HTML for a template with `IsTextPartGenerationEnabled`: note it in the plan row |
| The template's `Headers.From`, `Headers.Reply-to` | The send's `from` and `replyTo`, as the "Fields" table writes `From` and `ReplyTo` |

**Escaping.** Mailjet's docs never say it escapes a value, and its `Escape` function is there to escape one, so Mailjet inserted each value as it is. In the HTML part, a value the code builds as HTML itself goes in as it is, under the rule of `template-to-code.md`. Escape every other value, and note each one that carries text from a user, a form, or another service in the plan row. Never escape a value in the text part or the subject, unless the template passes it through `Escape`.

**Mailjet's truth.** The docs show `false` as false, and `true` and any other string as true, `"false"` included. They don't say what `0`, `""`, `null`, an empty list, or an empty object do. A test of a value alone, such as `{% if var:coupon %}`, that the code can pass as one of those keeps the template on Mailjet. A comparison, such as `var:count > 0` or `var:coupon != ""`, moves. Write the test out in the code, as `template-to-code.md` says.

**Template errors.** Mailjet checked the template language after it took the call, and the call answered as for any send. A left-out value without a default was a template error: Mailjet blocked the email, with a `blocked` event and the error `error in template language`. Since October 2025, a value that the template's variable schema declares renders as empty or `false` when the send leaves it out, and the email goes out, while a value it doesn't declare still blocks it. The docs don't say how to read that schema, so these files can't tell whether such a send went out. So a value without a default that the site can leave out keeps the template on Mailjet, and the reason is `<name> can be missing`. A site that always passes it moves. With `TemplateErrorDeliver: true`, Mailjet sent the email anyway: the site moves, the left-out value renders as nothing, and the plan row notes it, because the docs don't say what Mailjet printed in its place. `TemplateErrorReporting` mailed the error to an address: the report names that address, so the person knows those copies stop.

- **What keeps a template on Mailjet.** A tag Mailjet fills from the account, in any part: `[[UNSUB_LINK_EN]]` and every other `[[UNSUB_LINK...]]`, `[[UNSUB_ALL_LINK_EN]]`, `[[WORKFLOW_EXIT_LINK_EN]]`, `[[PERMALINK]]`, `[[SHARE_...]]`, `{{mj:unsub_link}}`, `{{mj:share_...}}`, and any other `[[...]]` tag without `var:`. A value only Mailjet holds: `{{segment:...}}`, `HasOpenedSince`, `HasClickedSince`, and any other `mj:` value, such as `mj:contact.ID`, `mj:contact.name`, or `mj:sender.name`. A function the table doesn't name. A header in `Headers` other than `From`, `Subject`, and `Reply-to`.
- **Contact properties.** `{{data:name}}` and `[[data:name]]` print a contact property stored at Mailjet, which the code doesn't have, so they keep the template on Mailjet. They move only when the person names the value of the app that the property holds, such as a first name the app stores and copies to Mailjet, and the code at the site can read it: it then prints that value, or its default, or nothing when the app has none, never a template error. Note it in the plan row.
- **Images.** Images uploaded to Mailjet's gallery or editor have URLs on a subdomain of `mjt.lu`, such as `https://<id>.mjt.lu/tplimg/...`. The docs don't name the host, so treat any image on a Mailjet host as one. Keep them, and list them, as `template-to-code.md` says.
- **The site's fields and the template's settings.** The template's `Headers` are defaults: a `From`, `Subject`, or `ReplyTo` that the site sets replaces the template's, as Mailjet did. A `From` or `Reply-to` header that holds the template language keeps the template: the docs say only the subject takes it. A `Reply-to` header with a name keeps it, as the "Fields" table says for `ReplyTo`.
- **Tracking.** A site brought into the code follows "Tracking" above, like any other site.

### Templates made in PostHog

Only for a template the person asks to make in PostHog, as Step 3 says. The person makes it from the Mailjet template and gives you its template ID, and makes it transactional once a verified sender covers its address, as Step 3 says. Until they give the ID, the site stays on Mailjet.

An email that carries a login code, a reset link, or another secret needs its PostHog template marked sensitive: PostHog then keeps no copy of each sent email's body or filled-in subject, and a clicked link keeps only the site's address. Templates are not sensitive by default.

A site that sends `TemplateID` without `TemplateLanguage: true` gets no `{{...}}` or `{% ... %}` filled in. Its template moves as it is, apart from each `[[var:...]]` tag, which converts as the table below says, with the site's `Variables` as `templateData`, and the plan row notes it, as "Templates" says for the code. A template that holds `{{` or `{%` keeps the site on Mailjet: Mailjet sent them as written, and PostHog's Liquid would read them. A site whose template has no `[[var:...]]` sends no `templateData`.

With `TemplateLanguage: true`, Mailjet's template language becomes Liquid in the PostHog template. Values move under `variables`, and each name keeps its case:

| Mailjet | PostHog |
|---|---|
| `{{var:name}}`, `[[var:name]]` | `{{ variables.name }}` |
| `{{var:user.first_name}}` | `{{ variables.user.first_name }}` |
| `{{var:name:"there"}}`, `{{var:name:there}}`, `[[var:name:"there"]]` | `{{ variables.name \| default: 'there' }}` |
| `{% if var:paid %}…{% elseif var:due %}…{% else %}…{% endif %}`, when `paid` and `due` are booleans | `{% if variables.paid %}…{% elsif variables.due %}…{% else %}…{% endif %}` |
| `{% for item in var:items %}{{ item.name }}{% endfor %}`, when `items` is a list | `{% for item in variables.items %}{{ item.name }}{% endfor %}` |
| `{{ item }}` inside `{% for item in var:items %}` | `{{ item }}` |
| `==`, `!=`, `>`, `<`, `>=`, `<=`, `and`, `or` in a condition | The same |
| The template's `Subject` header, or the site's `Subject` | The PostHog template's subject, with the same conversions |

Write the `\|` above as a plain `|`. The table escapes it.

- Liquid treats `0`, an empty string, and an empty list as true. Read what the site sends for each value an `if` or `elseif` tests alone. A value that is not always a boolean, `null`, or missing keeps the template on Mailjet. A comparison, such as `var:count > 0`, converts as it is.
- Inside a loop, the loop's own name reads the current item: `{{ item.name }}` stays `{{ item.name }}`, never `{{ variables.name }}`, and `{{ item }}` stays `{{ item }}`. Mailjet has no bare name that reads the item: a `{{var:name}}` inside the loop still reads the send's value, and becomes `{{ variables.name }}`.
- Mailjet's `for` also walks the values of an object, and Liquid's `for` doesn't. A loop over a value that is not always a list keeps the template on Mailjet.
- PostHog's Liquid escapes HTML in every value. When the code passes a value that holds HTML, such as a rendered block or a link tag, or a default in the template holds HTML, such as `{{var:name:"<b>friend</b>"}}`, the template stays on Mailjet.
- `{{data:...}}`, `{{mj:...}}`, and `{{segment:...}}` read data stored at Mailjet, so a template that uses them stays on Mailjet.
- Any function, such as `Upper`, `Lower`, `Capitalize`, `Round`, `Int`, `FormatNumber`, `FormatNumberLocale`, `UrlEncode`, `Escape`, `HasOpenedSince`, or `HasClickedSince`, keeps the template on Mailjet. So do `{% set %}`, the operators `=`, `===`, `<>`, `xor`, `not`, `div`, `mod`, and arithmetic.
- A value without a default that the site can leave out keeps the template on Mailjet, as "Template errors" says above, unless the site sets `TemplateErrorDeliver: true`: Liquid prints nothing for it, where Mailjet may have blocked the email.
- Liquid's `default` also replaces an empty string and `false`, and Mailjet prints its default only when the value is not set. When the code can pass `false` for such a value, the template stays on Mailjet. When the code can pass an empty string, the email shows the fallback. Note it in the report.
- The PostHog template carries its own sender, reply-to address, and subject. A site that sets `From`, `ReplyTo`, or `Subject` next to `TemplateID` moves only when the value is the same in every send, and the person puts it into the PostHog template. Otherwise it stays.
- A template site follows "Tracking" like any other site, and stays where it says. When it moves, the tracking fields are dropped.

## Webhooks

Mailjet's Event API stops getting events for a site that moves. PostHog records the events of a moved send on the person it names with `distinctId`, when engagement capture is on:

| Mailjet event | PostHog event |
|---|---|
| `sent` | `$workflows_email_delivered`: Mailjet's `sent` means the receiving server took the email |
| `bounce` | `$workflows_email_bounced` |
| `spam` | `$workflows_email_blocked` |
| `open` | `$workflows_email_opened` |
| `click` | `$workflows_email_link_clicked`, only for a template made in PostHog that is not marked sensitive. PostHog treats a send in the code form as sensitive: its links go out as they are, and it counts no clicks |
| `blocked` | none. PostHog refuses the send instead, such as with `recipient_suppressed` |
| `unsub` | none |

PostHog also records `$workflows_email_sent` when it sends, which has no Mailjet event.

PostHog's events carry no Mailjet `MessageID`, `Message_GUID`, `CustomID`, or `Payload`. A site whose events a handler matches by message id, by `CustomID`, or by `Payload` stays on Mailjet. For every other handler, such as one that matches by `email`, the report tells the person which events it handles, which PostHog events take their place, and that a webhook destination in PostHog (Data pipelines, then Destinations) can post them to an endpoint. The handler itself keeps working for the sites that stay. Never change it.

A site whose emails a `click` handler acts on moves only to a template made in PostHog that is not marked sensitive, since a send in the code form counts no clicks. Otherwise it stays, and the reason is `its clicks feed a webhook handler`.

## Calls that change the suppression list

The import takes hard bounces and spam reports, as `account.md` says. Mailjet records both itself, and these files know of no API call that adds one. A call that deletes a contact may remove its spam report: treat it as a call that removes an address, as Step 5 says. A call that unsubscribes a contact from a list, or sets `IsExcludedFromCampaigns`, changes a list the import leaves out, so it is not one of these calls.

## Rewrite

How a site that moves is written with PostHog's SDK. Step 7 says when to use each part, and the rewrite file for the site's language has the client and the send.

**The PostHog client.** Set `migratedFrom: 'mailjet'` on the client that Step 7 configures, when its client options take it.

**The call.** The Mailjet send becomes one PostHog send. Build its fields from the one message the site built, with `Globals` merged in:

- Node.js `mailjet.post('send', ...).request({ Messages: [msg] })`, Python `send.create(data={'Messages': [msg]})`, Ruby `Mailjet::Send.create(messages: [msg])`, PHP `$mj->post(Resources::$Email, ['body' => ['Messages' => [$msg]]])`, and a raw HTTP body: the fields of `msg`.
- Go `SendMailV31(&mailjet.MessagesV31{Info: []mailjet.InfoMessagesV31{msg}})`: the fields of `msg`. A `*mailjet.RecipientV31` becomes its `Email`, with its `Name` as for `From`.
- .NET `TransactionalEmailBuilder`: each `With...` call sets the field of its name. A `MailjetRequest` with `SendV31.Resource`: the fields of its one message.
- The v3 Send API: `FromEmail` and `FromName`, `To` or the one `Recipients` entry, `Subject`, `Text-part`, `Html-part`, and the other fields by their v3 names.

**HTTP.** A raw request to `/v3.1/send` or `/v3/send` becomes the SDK's send in that language, as "The call" says. A request or Mailjet client with its own deadline keeps it, as Step 7 says under "Set up the client". These are the site's own deadline:

- On a raw request: `signal: AbortSignal.timeout(5000)`, axios or got `timeout`, `requests.post(..., timeout=5)`, httpx `timeout=`, Guzzle's `'timeout'`, Faraday's `timeout`, Ruby `Net::HTTP`'s `read_timeout`, a Go `http.Client` `Timeout` or a context with a deadline, .NET's `HttpClient.Timeout`, and curl's `--max-time` or `CURLOPT_TIMEOUT`.
- On Mailjet's client: `timeout` in Node.js's client `options`, such as `new Mailjet({ apiKey, apiSecret, options: { timeout: 5000 } })`; Python's `timeout=` on `send.create(...)`, or on `Client(...)` from `mailjet-rest` 1.7.0; PHP's `$mj->setTimeout(...)` or `addRequestOption('timeout', ...)`, or the timeout of an HTTP client the code gives its `Client`; Go's `http.Client` with a `Timeout` given to `SetClient`, or `mailjet.WithContext(ctx)` on the send; and .NET's `Timeout` on the `HttpClient` that `MailjetClient` takes, such as one set in `AddHttpClient<IMailjetClient, MailjetClient>`. Ruby's gem takes no timeout through `Mailjet.configure` or a send's options; a `Mailjet::Connection` that the code builds itself with `read_timeout` sets one in the gem versions whose connection reads it, such as 1.7.
- A client's default that the code never set, such as Python's 60 seconds, PHP's 15, or .NET's 100, is not one.
- A connect limit set apart from the request's keeps the site, as Step 7 says. On Mailjet's clients that includes PHP's `setConnectionTimeout`, a `Mailjet::Connection`'s `open_timeout`, and a `(connect, read)` pair given to Python's `timeout=`. PHP's `connect_timeout` of 2 seconds, which the client sets when the code doesn't, is a default, not the site's.
- Mailjet's own retries count with the deadline. Python's client from `mailjet-rest` 1.8.0 retried a send up to three times, and a Node.js client with `maxRetries` in its `options`, as `sdk-reference.md` says, retried a failed or timed-out connection that many times. Such a site keeps its timeout for each request and the same number of retries, through the retry option the rewrite file names under "A deadline", instead of none.
- Only some versions read node-mailjet's `maxRetries` and a gem connection's `read_timeout` and `open_timeout`; every other option above works in the versions named with it. Read the installed version's source, such as node-mailjet's `Request` code under `node_modules` or the gem's `connection.rb`. When it doesn't read the option, the site never had it. When you can't read the source, the site stays, and the reason is `mailjet client version not checked`.

A request that a caller can cancel, such as a `signal` a caller passes in or an `AbortController` it aborts, a Go context, or a .NET cancellation token, keeps it only where the PostHog send takes the same cancellation, as Go's `Send(ctx, ...)` and .NET's `SendAsync(..., cancellationToken)` do: pass it there. Otherwise the site stays, as in Node.js, whose send takes no signal, and the reason is `the code can cancel the send`.

**The fields.**

- `From: { Email: 'hello@mail.example.com', Name: 'Example' }` becomes `'Example <hello@mail.example.com>'`. A name that holds a comma, a quote, or another special character goes in double quotes, such as `'"Acme, Inc." <hello@mail.example.com>'`, with each quote inside it escaped. A `From` without a `Name` becomes the bare address.
- `To` becomes a bare address. A list with one entry becomes that entry. When a helper takes a list of recipients and every caller passes one address, change the parameter to one address and update the callers. Never send one email per address in a loop.
- `TextPart` becomes `text`, and `HTMLPart` becomes `html`, rendered first when the site sets `TemplateLanguage: true`.
- `ReplyTo: { Email }` becomes `replyTo` with the bare address.
- `TrackOpens` and `TrackClicks` are dropped, and the send gets no `captureEngagement` for them, as "Tracking" says.
- A send with rendered content gets a `templateKey`, as Step 7 says.

**Templates brought into the code.** The site renders the email from `Variables`, as "Templates" says, and sends `templateKey`, the rendered `subject`, `html`, and `text`, and the `from` and `replyTo` that the site sets, or else the template's `From` and `Reply-to` headers. It sends no `templateId` and no `templateData`. A site with `TemplateLanguage: true` and its own content renders that content the same way before the send. A site that picks its `TemplateID` from a map, such as one template per locale, brings each template in it into the code, and picks the email the same way: it moves only when every one of them moves. A left-out value renders as "Template errors" under "Templates" says.

**Templates made in PostHog.** The site sends `templateId` with the template ID the person gave, and `templateData` with the site's `Variables`. It sends no `templateKey`, `subject`, `html`, `text`, `from`, or `replyTo`: the template holds them. A site that picks its `TemplateID` from a map, such as one template per locale, sends each template in it: it moves only when every one has a PostHog template ID, and the map then holds those IDs.

**Errors.** Keep the site failing the same way it did, and never widen a catch: a catch of one error class or one status becomes a catch of PostHog's error that checks for the same kind of error, and raises or returns every other error as before. A branch on Mailjet's answer to an invalid send, a `400` or a message with `Status: 'error'`, becomes a branch on PostHog's error name `validation_error`, never on a status code, as Step 7 says. A branch on another status, such as `429` or `401`, reads PostHog's status code. A branch that tries again or waits on `429` also checks for a code other than `quota_limited`: PostHog answers a used-up quota with `429` and that code, and a retry doesn't clear a quota. A network error that is left after PostHog's retries comes back as PostHog's error with the code `network_error`. Where Mailjet's network error went past the old branch, let PostHog's go past the new one.

- **Node.js.** `posthog.emails.send` never throws on an API error: it answers `{ data, error }`. Where `.request()` threw into a `catch`, throw from the error so the same `catch` runs: `if (error) throw Object.assign(new Error(error.message), { statusCode: error.statusCode, name: error.name, code: error.code })`. `err.statusCode` keeps holding the HTTP status, and a network failure, which has none, has `err.code` `network_error`, so a branch on `err.statusCode === 429` still takes only that status. A check of `err.statusCode === 400` becomes a check of `err.name === 'validation_error'`. A read of `err.ErrorMessage`, `err.originalMessage`, or `err.response` becomes a read of `err.message`.
- **Ruby.** PostHog's SDK raises too. A `rescue Mailjet::CommunicationError` becomes a `rescue` of the PostHog error the rewrite file names, and a read of Mailjet's `e.code` becomes `e.status_code`: PostHog's `e.code` is its own error code, not the HTTP status. A `rescue` of one subclass becomes a `rescue` of the PostHog error that checks for the same kind of error, and raises every other error again: `Mailjet::BadRequest` checks the name `validation_error`, and `Mailjet::Unauthorized` checks the status code `401`. Where the site also checked the answer's `Status` for a refused address, that check becomes a `rescue` that checks the name `validation_error`.
- **Python from `mailjet-rest` 1.8.0.** The SDK raised on every error, as PostHog's does, so a site that catches nothing keeps raising, and a `result.status_code` check after the call saw only successes: keep the code after it as the success path. A catch of `ApiError` took every error, and becomes a catch of the PostHog error the rewrite file names. A catch of `MailjetApiError` took the statuses 400, 401, 403, and 404 only: it checks PostHog's error name `validation_error`, or the status code 401, 403, or 404, and raises every other error again. A catch of one subclass checks the same kind and raises every other error again: `ValidationError` checks the name `validation_error`, `MailjetAuthError` the status code 401 or 403, and `DoesNotExistError` 404. A catch of `ApiRateLimitError` never ran, since the client retried a 429 and then raised a plain `ApiError`: the site stays, and the reason is `catches ApiRateLimitError`. A catch of `MailjetNetworkError` checks the code `network_error`. A read of `e.status_code` reads PostHog's status code, and a read of `e.response_body` or the error's text reads its message. The client retried a 429, 500, 502, 503, or 504 up to three times before it raised. Write the send as the rewrite file says, with the retries PostHog's SDK makes itself, and add no retry loop around it. The plan row notes that Mailjet's client retried a 500, 502, or 504, so that the person knows such an error may now reach the site's handling sooner.
- **Python before `mailjet-rest` 1.8.0, PHP, and .NET `PostAsync`.** The code read Mailjet's status: `result.status_code`, `$response->success()`, `getStatus()`, `IsSuccessStatusCode`, or `StatusCode`. PostHog's SDK raises or throws instead. Put the send in a `try`, and catch the PostHog error the rewrite file names. A failed status, such as `status_code != 200` or `!$response->success()`, becomes that catch, and it takes the branch the status check took. A branch on `400` checks PostHog's error name `validation_error` in the catch, and a branch on another status, such as 429, checks PostHog's status code. The catch handles every other error the way the old code handled a status it didn't branch on. Mailjet's SDK raised its network errors past the status check, so the catch raises PostHog's error again when its code is `network_error`. In PHP, Mailjet's SDK answered every failed status itself and let only Guzzle's network exceptions through. So around its call, a catch of `GuzzleException`, `TransferException`, or Guzzle 6's `RequestException` checks the code `network_error` and raises every other error again. A catch of `ConnectException` alone, or of Guzzle 7's `RequestException`, took one kind of network failure, so the site stays, as Step 7 says. A catch of `BadResponseException`, `ClientException`, or `ServerException` never ran: drop it. A read of `result.json()`, `result.text`, `getBody()`, or `GetErrorMessage()` for the error becomes the error's message. In Python from 1.7.0, a 401 raised `MailjetAuthError` past the status check too: a status branch on 401 never ran, so drop the 401 from it and keep the branch for every other status it checks, and the catch also raises PostHog's error again when its status code is 401, and a catch of `MailjetAuthError` checks the status code 401 and raises every other error again. In Python before 1.8.0, a catch of Mailjet's `ApiError` around the send took only network failures, and from 1.7.0 a 401: it checks the code `network_error`, or from 1.7.0 the status code 401, and raises every other error again.
- **Python, every version.** A catch of only `TimeoutError` or only `CriticalApiError` took one kind of network failure, so the site stays, as Step 7 says.
- **.NET `SendTransactionalEmailAsync`.** Mailjet answered an invalid send in `Messages` and threw `MailjetServerException` only for an answer without `Messages`, so the two took separate paths. PostHog's SDK throws for both, so its `catch` keeps them apart: for the name `validation_error`, it runs what the check of `response.Messages[0].Status` ran, or what "A site that read no result" says when the site didn't check it, and for every other error, what `catch (MailjetServerException)` ran, with `HttpCode` read as PostHog's status code. A `MailjetServerException` handler that checks `HttpCode` 400 took an invalid send that Mailjet answered without `Messages`, which PostHog's `validation_error` can't tell from one answered in `Messages`: the site stays, and the reason is `can't tell Mailjet's invalid-send paths apart`. A network error went past both before, so the `catch` throws again when the code is `network_error`.
- **Go.** PostHog's `Send` answers an error value too, always a `*posthog.EmailError`. Keep `if err != nil`: it took Mailjet's network errors too. A type switch or `errors.As` reads `*posthog.EmailError` with `errors.As` instead, and keeps each branch. `*mailjet.APIFeedbackErrorsV31` is Mailjet's answer to a `400` or a `403`, so its branch checks the name `validation_error` or the status code `403`. `*mailjet.ErrorInfoV31` is any other status, so its branch takes every PostHog error whose name is not `validation_error`, whose status code is not `403`, and whose code is not `network_error`, and a check of its `StatusCode`, such as 429, reads PostHog's `StatusCode`. Every other error goes on as before.
- **Raw HTTP whose client answers a failed status as a response.** These are `fetch`, `requests`, `httpx`, Ruby's `Net::HTTP`, Go's `net/http`, PHP's `curl_exec`, `curl` without `--fail`, Guzzle with `'http_errors' => false`, .NET `HttpClient` without `EnsureSuccessStatusCode()`, and a throwing client with an option that turns the throw off, such as axios's `validateStatus` that accepts a failed status, or `throwHttpErrors: false` in got or ky. A call to `/v3.1/send` raised on a status only where the code checked it, such as `!res.ok`, `raise_for_status()`, or `resp.StatusCode >= 300`. That check becomes PostHog's error, as for Python above. The HTTP client raised its own error on a network failure. When the old catch took that too, such as `except requests.RequestException` or a `catch` around `fetch`, the new catch takes `network_error` too. When it took only the status error, such as `requests.HTTPError`, raise `network_error` again. PHP's `curl_exec` raised nothing on a network failure: it returned `false`, and `curl_getinfo` gave the status `0`. So a check that the status `0` meets, such as `!== 200` or `< 200`, took a network failure too, and the catch takes `network_error` the same way. A check that `0` doesn't meet, such as `>= 300` or `>= 400`, let a network failure go on as if the send worked: the catch logs `network_error` and goes on. A check that only `curl_exec` returned `false` took only the network failure, so the catch runs its code for `network_error` alone, and handles every other error as the site's status check did, or logs it and goes on when the site checked no status.
- **Raw HTTP whose client throws on a failed status.** These are `axios`, `got`, `ky`, Guzzle, Faraday with `raise_error`, and .NET `HttpClient` followed by `EnsureSuccessStatusCode()`, each without an option that turns the throw off. The call failed on every API error and every network failure, as Mailjet's Node.js SDK does, whether the code read the answer or not. Keep that: every PostHog error fails the site. In Node.js, throw from `error` as the Node.js bullet says. In Python, Ruby, PHP, and .NET, PostHog's SDK raises on its own. A catch of the client's error becomes a catch of PostHog's error that takes the same failures. Guzzle's `GuzzleException` or `TransferException`, Guzzle 6's `RequestException`, and `Faraday::Error` took network failures too. A catch of .NET's `HttpRequestException` follows the ".NET, every client" bullet below. Guzzle 7's `BadResponseException` took failed statuses only, so that catch raises PostHog's error again when its code is `network_error`; `ClientException` also checks a 4xx status code, and `ServerException` a 5xx one, and each raises every other error again. Guzzle 7's `RequestException` took some network failures, such as a failed receive, but not a failed connection, its `ConnectException`, and a catch of `ConnectException` alone, in Guzzle 6 or 7, took only a failed connection. Each of these Guzzle catches keeps its site, as Step 7 says for one kind of network failure. A read of the client's status in that catch, such as axios's `err.response.status` or got's `err.response.statusCode`, reads PostHog's status code, and a branch on `400` reads PostHog's error name `validation_error`. Never log the error and go on here.
- **.NET, every client.** Mailjet's `MailjetClient` and a raw `HttpClient` let `HttpClient`'s exceptions through: `HttpRequestException` for every network failure but the timeout, which comes as a `TaskCanceledException`. When the site keeps a deadline, as "HTTP" says, the send takes it as a cancellation token, whose timeout still throws past the new catch, as Step 7 says for .NET: a catch of `HttpRequestException` becomes a catch of PostHog's error that takes the same failures of the send, and the site moves. It takes `network_error`, and the statuses of the send that raised `HttpRequestException` before: every failed status after `EnsureSuccessStatusCode()` on the send's answer, or only those a status check of the code threw it for, such as 5xx. It throws every other error again. When the same `try` also covers another call that throws `HttpRequestException`, keep that handler for the other call and add PostHog's catch next to it. A site without a deadline of its own that catches `HttpRequestException` and not `TaskCanceledException` took one kind of network failure, so it stays, as Step 7 says.
- **Any language.** A check of `Messages[0].Status` for `error` becomes a check of PostHog's error name `validation_error`, in the language's form above.
- **A site that read no result.** Mailjet's Python SDK before 1.8.0, its PHP SDK, .NET `PostAsync`, and a raw HTTP client that answers a failed status as a response raise nothing on an API error, apart from Python's 401 from 1.7.0, so a site that read neither the status nor `Messages[0].Status` went on after every refused send. PostHog's SDK raises instead. Put the send in a `try` that catches the PostHog error the rewrite file names, raises it again when its code is `network_error`, or in Python from 1.7.0 when its status code is 401, and otherwise logs it and goes on. In Node.js, such as a `fetch` whose answer the code never read, PostHog's send answers `{ data, error }` and throws nothing, so read `error` instead of catching: log it and go on, and throw it when its code is `network_error`, as `fetch` rejected on a network failure. PHP's `curl_exec` didn't raise on a network failure either: it returned `false`. A site that never checked that went on after a network failure too, so its moved site also logs `network_error` and goes on. With .NET `SendTransactionalEmailAsync`, which threw on every error but an invalid send, the `catch` logs and goes on only for the name `validation_error`, and throws every other error again. PostHog raises `validation_error` for it, and for other invalid sends that the gem raised on, so the name alone can't tell them apart. A Ruby site that rescues nothing checks the recipient's address before the send, and logs and skips the send when it isn't a valid address, as the gem went on. Around the send, `rescue PostHog::EmailError => e` logs and goes on only when `e.code == 'recipient_suppressed'`, and calls `raise` for every other error. Note each site that got a new `try` or `rescue` in the report.
- PostHog refuses a send to a suppressed address with `recipient_suppressed`, where Mailjet took it and blocked it later. When the site throws, retries, or reports a failure on any error, handle `recipient_suppressed` before that branch the way the site handled a send that went out: log it and go on. A suppressed send has no message ID: when the code after the send uses the ID for more than a log line, such as returning it to its callers or storing it, the site stays, and the reason is `uses the message id of a suppressed send`, unless its callers already handle a send without an ID. Note each site that got this branch in the report.

**The answer.** The message id of a moved send is PostHog's. Code that logged `MessageID` or `MessageUUID`, or stored it for the app's own use, takes PostHog's message id instead, where "Code around the send" lets the site move.

**The Mailjet client.** Keep the Mailjet client, its import, and its configuration while any site or other call still uses them. When nothing uses them, remove the import and the client, and keep the package and its keys: the person removes them after the cutover.
