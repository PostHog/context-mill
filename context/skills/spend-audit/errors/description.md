# Spend audit — error tracking

Find exception volume a few noisy issues produce. Read `exceptions_by_issue`
and `exceptions_total` from the `measure-volumes` handoff. Grep the code for
`capture_exceptions|captureException|capture_exception`, `before_send|beforeSend`,
`error_tracking`, `autocapture_exceptions`, `ignore_errors|ignoreErrors` when
it is connected.

| Check id                        | Condition                                                                                                 | Finding                                                                                                                                                                                                                                                                                                                        |
| ------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `errors-noisy-issues`           | The top issue holds ≥ 30% of exceptions, or the top five hold ≥ 60%, and the issue is not actionable (a network timeout, an extension or bot error, a known third-party script, a `ResizeObserver` or chunk-load noise) | `saving`, `error_tracking`/`exceptions`, `before` = `exceptions_total.exceptions`, `after.low` = `before - sum(top noisy issues)`, `after.high` = `before - sum(top noisy issues) / 2`. `fixed_in: pr` when the init is in the code: `code_change` = drop those exception types in `before_send`. Otherwise `fixed_in: notebook`, `settings_path: /project/<project id>/settings/project-error-tracking`, `setting: "Add a suppression rule for <types>"`. Tradeoff: a real regression in that type is suppressed with the noise; name the issue ids so the user can judge. |
| `errors-dev-hosts`              | `exceptions_by_host` measures exceptions from clearly non-production hosts, matched as `events-dev-hosts` in the events skill matches them | Same shape and rules as `events-dev-hosts`, `error_tracking`/`exceptions`, `before` = exceptions from those hosts, `after` = 0..0, `fixed_in: pr`. When host volume cannot be measured: `unpriced`, `effort: code`, `fixed_in: notebook`. Measure with `exceptions_by_host`: `SELECT properties.$host AS host, count() AS exceptions FROM events WHERE event = '$exception' AND timestamp > now() - INTERVAL 30 DAY GROUP BY host ORDER BY exceptions DESC LIMIT 20`. |
| `errors-no-issue`               | `without_issue` is ≥ 20% of exceptions (exceptions with no `$exception_issue_id`, so no issue groups them) | `unpriced`, `effort: code`, `fixed_in: notebook`. When the code captures exceptions by hand, `code_change` = pass the `Error` object, not a string. |
| `errors-rate-limit`             | A single issue produced ≥ 10,000 exceptions in one day (`SELECT toDate(timestamp) AS day, properties.$exception_issue_id AS issue_id, count() AS n FROM events WHERE event = '$exception' AND timestamp > now() - INTERVAL 30 DAY GROUP BY day, issue_id ORDER BY n DESC LIMIT 10`) | `unpriced`, `effort: setting`, `fixed_in: notebook`, `settings_path: /project/<project id>/settings/project-error-tracking`, `setting: "Suppress or rate limit <issue>"`. The browser SDK already limits exceptions per type per client; a burst this size comes from many clients, so the fix is a suppression rule, not a client setting. |
| `errors-fine`                   | None of the above                                                                                         | `passed`. |

Only exceptions already in the project count. Never propose turning exception
capture off.
